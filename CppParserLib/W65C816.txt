C++ for the W65C816
===================

A plan for a second target for the C++ compiler: the W65C816S.  The first target is the
65C64 (CPP65Generator.txt, IR.txt).  Written 2026-10-25; nothing here is built yet.
Decisions marked QUESTION are the user's to make; each has a recommendation.


Why the W65C816 is a poor fit for C++
-------------------------------------

C++ (and C) compilers assume things the W65C816 doesn't have:

- One accumulator.  A, X and Y are not general registers: arithmetic is only in A, X and
  Y only count, index and compare.  Every binary operation is load A, operate with
  memory, store A.
- 16 bits at most.  int, long, pointers and size_t of 32 bits are two operations each,
  with the carry between them.  No multiply or divide at all.
- Mode bits.  A is 8 or 16 bits (m) and X/Y 8 or 16 bits (x).  An immediate's size
  depends on the mode at that point, so the assembler must know it, and code that
  mixes char and int switches modes with rep and sep.
- Banks.  Addresses are 24 bits but the program counter wraps within its 64KB bank, a 16
  bit add doesn't carry into the bank byte, the stack and direct page are in bank 0,
  and absolute data addressing uses the data bank register (DBR).
- No 24 bit pointer register.  A far pointer can only be followed through direct page
  ([d] and [d],y) or with long absolute addresses fixed at assembly time.
- Signed comparison: cmp doesn't set v, so signed < needs sbc and the n xor v trick.
- No indirect long call.  There is jml [a] (from a fixed bank 0 address) but no jsl
  through a pointer, so function pointers and virtual calls need a trick.
- Interrupts can arrive in any mode with any D and DBR.

The 65C64 was designed as a C++ target (32 bit registers, pseudo registers, mul and div),
so the generator's direct path doesn't translate.  The IR path does: its instructions are
target independent, and everything above is the back end's (and the linker's) problem.


What is kept
------------

- The parser, preprocessor and all of the generator's C++ (CCPP65Generator: types,
  classes, templates, overloads, conversions, temporaries, destructors, vtables,
  mangling, init/fini tables).
- The IR (IR*.cpp): types already include i8 and i16, address spaces (far, near, zero)
  and ptradd inbank were put in for this target (IR.txt "W65C816").
- The mid level passes: CIROptimiser, CIRInliner, CIRLiveness (not 65C64 specific).
- The object format, linker and library (CAsm65Object, CAsm65Linker, CAsm65Library):
  sections, symbols, relocations, dead section removal and COMDAT have no 65C64 in them.
- Libc65's C sources, including softfloat.cpp (the bit exact C reference) and string.cpp.
- CFast65C816 (fast emulator) and CW65C816 (cycle exact simulator) to run and cross check.
- The test corpus: TestIR65Backend's IR programs, the TestCPP65 projects (MD5, sorts,
  MersenneTwister, FloatHelper, SQuaternion), TestLibc65, TestBaseLib65, TestStandardLib65.

What is not kept: the generator's direct path (about 280 places write 65C64 instructions
inline) and CIR65Backend.  The W65C816 goes through the IR only: a function the IR front
end can't write is an error on this target ("... is not supported on the W65C816 yet").
That makes the IR front end's remaining 3.3% (arguments needing copy constructors,
temporaries with destructors, operators on objects, new[] with destructors, &f, member
pointers) part of this work, which is also IR.txt step 7 (remove the direct path).

Another Claude session is removing the generator's direct code now (2026-10-25), so
closing those gaps is its work, not this plan's.  This plan waits for it where it
touches the generator (see Order of work).


Proposed model (the "large model", like WDC's -DLARGE)
------------------------------------------------------

Types (QUESTION 1):

	char 8, short 16, int 16, long 32, long long 64, float 32, double 64
	pointers, function pointers, size_t, ptrdiff_t: 32 (24 bit address, top byte 0)

int 16 is what the hardware is; 32 would make every int operation two.  But BaseLib and
StandardLib were written with 32 bit int, and some code may keep values over 32767 in an
int.  Recommendation: the sizes come from a target description (needed anyway), int is
16 by default and a target option makes it 32, so a failing BaseLib test can be checked
both ways.  size_t is 32 because BaseLib's size and malloc need more than 64KB.
Libc65's stdint.h/stddef.h/limits.h become per target (int32_t is long here).

Code and calls (v1): every function is called with jsl and returns with rtl, and globals
are reached with long addresses (lda $123456 / lda $123456,x).  DBR isn't used, so it
doesn't matter what an interrupt or mvn leaves in it.  The user's earlier ruling (near
calls inside a linker object, far at its boundaries) is v2: once it all works, calls
within an object become jsr / rts (the linker already keeps an object's code in one
bank) and an object's own globals become DBR relative.  The user (2026-10-25): "Start
with large data, far calls.  We'll try and compile to an automatic mixed model": the
compiler and linker choose near or far for each call and each piece of data themselves,
so v1 is all far and the mixed model is the goal of step 7.

Frame (QUESTION 3): the direct page is the frame.  A function's prologue is

		phd						; the caller's D
		tsc
		sec
		sbc #frame size
		tcs
		tcd						; D = S: locals are d, the arguments are above them

and its epilogue the reverse then rtl.  Locals, spilled temporaries and the arguments
(above the saved D and the 3 byte return address) are all direct page operands, so:

- a far pointer in a local is followed directly: lda [p],y (no copying it somewhere first)
- every addressing mode works on them: inc d, asl d, bit d, adc (d),y, pei (d) to push one
- each function has its own D, so pseudo registers need no saving across calls, and an
  interrupt's C handler sets its own D (the start up's IRQ stub problem goes away)

Costs: about 20 cycles of prologue and epilogue, a cycle more per direct page access when
the frame isn't page aligned (DL != 0), and frames over 256 bytes need their far part
addressed through a pointer.  The alternative is a fixed direct page of pseudo registers
(callee saved, as the 65C64's [$80 + W]) with locals stack relative (d,s): cheaper calls,
but d,s only works with lda/sta/adc/and/cmp/eor/ora/sbc and (d,s),y is near only, so far
pointers in locals would always be copied to the direct page first.  Recommendation: the
frame as direct page (as far as I know WDC's compiler does the same).

Calling convention:

- m and x are 16 bit (rep #$30) on entry and exit of every function, and at labels.
- Arguments are pushed last first, each in 16 bit units (a char takes 2), and the caller
  removes them.  Constants push with pea, direct page values with pei.
- Results: 8 and 16 bit in A, 32 bit and pointers in A (low) and X (high), 64 bit and
  objects through a hidden pointer as on the 65C64.
- this is the first argument (pushed last).
- Variadic arguments as on the 65C64 (float as double); va_arg stays Libc65's macro.
- A, X, Y and the flags may change; D, DBR, S and the mode are kept.

Bank 0 (the user, 2026-10-25): "all that is allowed in bank zero is the stack and direct
page variables.  Place no code there."  The hardware still needs the vectors at
$00FFE4-$00FFFF, and an interrupt starts in bank 0 (the vectors are 16 bits, PBR becomes
0), so bank 0 also holds the vector table and one 4 byte jml stub per vector (reset's
included), placed with .section ..., at address.  The linker (SetBankSize) refuses any
other section there.

Pointers: far (4 bytes, 24 bit address, top byte 0).  The user (2026-10-25): far pointers
are stored in 32 bits with the top 8 bits ignored, so as not to switch between 8 and 16
bit mode; they are loaded and stored as two 16 bit words.  The compiler keeps the top
byte 0 so == and != need no mask (Assembler816Syntax.txt rulings).  Following one: put it in the frame
(it usually already is) and use [d] / [d],y.  The address of a local is bank 0: D + offset.
A ptradd is 24 bit (adc low 16, then adc #0 on the bank byte) unless inbank, then 16 bit.
Later (v2) the near and zero address spaces let a pass make pointers 16 bit where it can
show where they point.

Indirect calls (function pointers, virtual calls): there is no jsl through a pointer, so
push the return address and the target, then rtl:

		phk						; return bank
		per Return - 1			; return offset
		(push target bank, push target offset - 1)
		rtl						; "returns" into the target
	Return:

or a runtime routine R_CallFar that does the same.  Vtables hold 4 byte entries.

Runtime (W65C816 assembly, R_ names as now): 16 and 32 bit multiply, unsigned and signed
divide and remainder, 32 bit shifts by a variable, 64 bit operations, R_CallFar, memcpy
and memset (mvn needs its banks in the instruction: a byte loop through [d],y first, mvn
from code written into RAM later).  Floats: softfloat.cpp compiled for the W65C816 first
(correct, slow); a hand written softfloat816.asm later, as softfloat.asm was for the
65C64.


Steps
-----

Each step ends with every 65C64 suite still passing, so the 65C64 doesn't regress.

1.	A target description.  CCPPTarget (in CppParserLib) holds what is target specific
	outside the back end: type sizes (CPP65Type's 4s become the target's), predefined
	macros (__W65C816__), the ABI's few places in the IR front end (narrow results
	widen to int, which is i32 on the 65C64 and i16 here), how data is written (.long
	for a pointer becomes the target's), the start up, thunks and runtime routines.  The
	65C64 is the first CCPPTarget and produces exactly the same assembly as now.
	Libc65's headers get __W65C816__ blocks.

	Done 2026-10-25 (CPPTarget.h/.cpp, SCPPTarget): int's size, the predefined macro,
	whether results widen to 32 bits, whether the generator may write functions itself,
	the bank size and the stack top.  CCPP65Builder::SetTarget (before anything is
	added) picks the configuration, the defines, the generator's target, the assembler
	(CAsm816Assembler) and the linker's bank size; CCPP65Generator::Init takes the
	target.  Types: int is the target's (2 bytes), long a 4 byte type of its own
	(CCPP65Types::Long), the usual arithmetic conversions take the wider type, and an
	int literal that doesn't fit int is long.  int and short are the same type on the
	W65C816 (types compare by size), as int and long are on the 65C64.  The IR front end
	widens a pointer's index to the pointer's size and generates with CIR816Backend;
	implicit default constructors and destructors go through it too (they have no
	definition: no member initialisers).  On the W65C816 everything else the generator
	would write as 65C64 code is an error: functions the front end can't write,
	globals that need code to construct, this adjusting and virtual call thunks,
	implicit copy constructors.  The start up (AppendStartUp816): the reset vector and
	a jml stub in bank 0, native mode, S, D = 0, jsl _main, stp with main's result in
	A; the init and fini tables aren't walked yet.  The runtime: R_Pure and the R816_
	routines the unit used, as COMDAT sections (AppendRuntime816).  Libc65: the 32 bit
	types (int32_t, size_t, ptrdiff_t ...) are long on both targets, limits.h's int is
	per target.  Tests: TestCPP816.cpp (C++ programs built for the W65C816 and run on
	CFast65C816, some in lockstep).

2.	A W65C816 assembler (Assembler65Lib, CAsm816Assembler: WDC's syntax, QUESTION 4)
	writing the same CAsm65Object.  Relocations gain a shift so a field can be the bank
	byte (^label) and a check that a 16 bit address is in the bank it is used in.  The
	assembler tracks m and x from directives (.a8 .a16 .i8 .i16, or LONGA/LONGI) to size
	immediates, and warns when rep/sep and the directives disagree.  The linker learns
	bank placement: a section never crosses a bank, sections can be pinned to bank 0
	(vectors, start up, interrupt stubs), and the image can have a load address that
	differs from the run address (for the ROM machine, step 8).  Tests: encoding of
	every opcode and mode (checked against CW65C816's instruction table), and a few of
	Assembler65Lib's feature programs rewritten for the W65C816 (Sieve, Queens, Base64),
	run on CFast65C816.

3.	A test context: CAsm816Memory (a flat 16MB for tests, CFast65C816 behind it, host
	files and results as CAsm65Memory has them), a start up for tests, and lockstep with
	CW65C816 for compiled programs as Asm65Lockstep does for the 65C64.

4.	CIR816Backend, naive: every temporary in the frame, every operation through A at 16
	bits, i32 and i64 split into 16 bit pieces by a legalisation pass, mul/div/float as
	runtime calls, rep/sep only around 8 bit loads and stores, signed comparisons with
	sbc and n xor v, far pointers through [d],y.  What both back ends share (block order
	and loop rotation, phi copies as parallel copies, frame layout, assembly text) moves
	into a common CIRBackend rather than being copied.  Tested with TestIR65Backend's IR
	programs, which are target independent IR: the same programs run on both targets
	and must give the same results (TestIR816Backend).

	Done 2026-10-25 (CIR816Backend, IR816Backend.h/.cpp; tests TestIR816Backend.cpp):
	every integer and pointer instruction, phis, calls (direct, through a pointer,
	variadic, thiscall), 64 bit results through a hidden pointer, frames past the
	direct page's 256 bytes (through X).  Multiply, divide and remainder are runtime
	routines written in IR (R816_Mul16 ... R816_SRem64) that the back end itself
	compiles (GenerateRuntime).  Each test program runs on CFast65C816 (some in lockstep
	with CW65C816) and must give the expected result and the 65C64's.  Not done: floats
	(they need softfloat.cpp compiled for the W65C816, step 5).  Not shared yet with
	CIR65Backend (another session is changing it): Binding and GenerateGlobal are copies.

	2026-10-29: R816_Mul16 and R816_Mul32 now add byte products looked up in Garth
	Wilson's multiplication table (Libc65/MathTbls/MathMult.asm, MathMult; plan in
	Libc65/MathTbls/MathTables.txt), skipping zero bytes and zero high halves.  Every
	816 build that multiplies must link MathMult: CCPP65Builder::AddMathTables(Libc65
	directory) adds it as a library (TestCPP816, TestProject65, TestLibc65Context do),
	and TestIR816Backend links it itself.  Cycles per call, old loop -> table: 16 bit
	174-259 (was 128-848), 32 bit 252-745 (was 312-2803).  R816_UDiv16 and R816_URem16 use the
	reciprocal slice MathInvert (Libc65/MathTbls/MathInvert.asm, linked by AddMathTables
	too); R816_UDiv32/URem32 jump to them when both operands are under 65536.
	2026-10-29, the runtime's calling convention (user chose operands in scratch):
	R816_Mul16/32 and R816_UDiv/URem16/32 take a at D + 15 and b at D + 19 in the
	caller's scratch bytes (IR816_SCRATCH_ARGUMENT_A/_B) and run on the caller's D,
	using D + 1 to D + 14 too; nothing is pushed or removed.  The signed divides (IR,
	using udiv/urem) and the 64 bit routines are still pushed.  Choosing routines from
	compile time bounds (an UpperBound in the back end, R816_Mul32x8) was tried and
	removed: -0.19% wasn't worth a second UpperBound (user, 2026-10-29).  R816_Mul32
	checks b < 256 at run time instead (a's bytes times b): -0.26%.

	2026-10-29, from a sprite drawing test (TestCPP816Sprites, SpriteProject):
	- A mul by a constant is shifts and adds when they cost less than the call
	  (CIR816Backend::ExpandMultiplies, the constant's signed digits Horner's way);
	  constant shifts move a byte at a time a word along (ShiftConstant).
	- An itoptr of ptrtoi p plus an offset is ptradd p, offset, and an itoptr of
	  ptrtoi p is p (CIROptimiser, both targets): no top byte mask after casts.
	- Small functions are inlined across a project's units on the W65C816
	  (CIRImports): each unit's small functions with external linkage that refer
	  to no symbol are kept after it is compiled, the inliner looks for callees
	  with no body there, and a unit that called one before it was kept is
	  compiled again at the end (CCPP65Builder::CompileUnits).

5.	C++ end to end: the runtime routines, the start up, Libc65 for the W65C816
	(softfloat.cpp, string.cpp, stdlib.cpp...) and closing the IR front end's gaps.
	Then the TestCPP65 projects and TestLibc65 run on the W65C816, compared with the
	65C64 and native results.
	Done so far (2026-10-25): the target description (CPPTarget.h: int, pointer and bank
	sizes, stack top, whether the direct generator is used); the start up (reset stub in
	bank 0, the init table's R_Initialise routines, main, __RunAtExit when linked, the fini
	table last first); globals' constructors, destructors and non constant initialisers
	written by the IR front end (CCPP65IRFrontEnd::GlobalRoutine); __builtin_clz/ctz/
	popcount; L literals are long.  All of Libc65 compiles for the W65C816 and
	"TestLibc65 816" passes everything (106361), on CFast65C816.  Libc65 and BaseLib fixes
	for a 16 bit int: string.cpp's words, the heap bounds, rand's state and RAND_MAX + 1 are
	uint32_t, INT32_C/UINT32_C are long, TrueMallocator and FindFirstClearBit use
	__builtin_clzl/ctzl on the W65C816.  The tests write their results as longs.
	new Type[count] and delete[] are the IR front end's (the generator's layout), and so
	are operators on objects (member and free operator functions, unary and binary, as
	values, places and conditions).  The TestCPP65 BaseLib projects (MD5, RedBlackTree,
	Sort, MersenneTwister, FloatHelper and Quaternion against native results) and
	new/delete run on the W65C816 (TestCPP816).  Their instruction counts on CFast65C816
	before any optimisation, step 7's starting point: MD5 0.31M, RedBlackTree 11.3M, Sort
	9.4M, MersenneTwister 57.3M (a runtime call for every 32 bit multiply and remainder),
	1000 new int[1000] / delete[] 13.8M.

6.	TestBaseLib65 and TestStandardLib65 on the W65C816.  This is where int 16 meets
	BaseLib (QUESTION 1).
	Done (2026-10-26): "TestBaseLib65 816" and "TestStandardLib65 816" (the shared
	TestProject65 runner, geTestProject65Target; 816 exclusions and minimums) compile all
	of BaseLib, StandardLib and their tests and run them on CFast65C816: TestBaseLib
	384/384, TestStandardLib 161/161.
	Excluded on the W65C816: TestListVariable (more than 16MB), and as too slow for the 4G
	instructions a program gets (they pass when given longer, TEST_PROJECT65_STEPS):
	TestMapStringIntAndPointer, TestSetUnknown, TestMapUnknownUnknown.  The user's ruling
	for int 16: overload sets of 32 bit ints get a 16 bit family under __W65C816__
	(AssertInt, IntToString, CChars and CString::Append, CNumber::Init, Read/WriteInt32
	...), never mixed 16 and 32 bit, and the tests' expected values (and some variables)
	are fixed to what the test means.  The int 16 traps found, all silent:
	- an int passed to ReadInt32/WriteInt32 picks the 16 bit overload: 2 bytes of a 4
	  byte file field (object readers, dist to root, test classes' Save and Load)
	- *(int*) and sizeof(int) for 4 byte data (the serialised object's type tag, the
	  index tree node header, FastMemcpy/Memset/MemcpyBackwards words, since removed)
	- uint16 and unsigned short promote to unsigned int: u16 - 1 is 65535, not -1
	  (FatClusterCache's loop never ended), TypeConverter, CalculateOffset, TextParser
	- uint8 << 16 or more; seeds, counts and sizes cast to int (CRandom::Init and Next,
	  Shuffle, QuickSort/TimSort's element count, malloc(12000 * 6) in a test)
	- multi character literals ('\0MAN') are long; NULL must be pointer sized for
	  varargs (0L); caches bigger than 16MB (Codabase factory)
	A real bug the 816 showed: CNumber::Init("0", whole, decimals) zeroed a default
	sized number over a smaller one (a heap overrun natively hidden by slack).  Also
	fixed: CTextParser::GetFloat lost the sign of "-0.5" (it failed natively too).
	Compiler: objects that aren't trivially copyable pass by the address of the caller's
	copy (Itanium style), condition temporaries, operators and conversion functions on
	objects, casts to classes, anonymous unions, scalar arrays zeroed by a loop, thunks in
	816 assembly, frames over 48KB are an error, Libc65's high heap starts after a
	program past 2MB.  Debugging: TEST_PROJECT65_ONLY=<tests> runs some programs;
	gcHeap.IsValid() between statements finds what corrupts the heap.
	Warnings (2026-10-26, the user asked): the generator has a second CCPPErrors for
	warnings (each token at most once; they don't fail a unit) and the builder collects
	them (GetWarnings; Generate's pszWarnings).  "Integer overflow": a constant int
	expression whose exact value doesn't fit its type (signed, or an unsigned sum,
	product or shift; unsigned subtraction wraps by definition).  "Integer conversion
	overflow": a constant an implicit conversion truncates (initialisers, assignments,
	arguments, returns, globals), unless it fits the target's signed or unsigned range
	(-1 to unsigned, 0xFFFF to a 16 bit int are bit patterns).  They found an enum bug:
	an enum's underlying type is now [dcl.enum]'s (int, unsigned int, long, unsigned
	long, long long; the given one; int for a scoped enum), so TRIERROR = 0xffffffff
	makes TRISTATE 32 bits on the W65C816.  Then 25 more, all fixed: Deflater's hash
	size (1 << 15), NumberInit's and CScratchPad's int sizes (1MB and 6MB were 0),
	FileCopier's int chunk, the index tree iterator's type, and test values.  The
	TestProject65 runner prints the warnings; BaseLib, StandardLib and their tests have
	none on the W65C816.

7.	Make it fast, measured with CFast65C816 cycle counts of the runnable projects:
	- register allocation over A, X and Y (loop counters and indexes in X/Y) with the
	  frame as the second class
	- keeping m and x where they are and removing rep/sep pairs; 8 bit arithmetic for
	  char values instead of widening
	- near calls inside an object (jsr), DBR relative globals, near and zero pointers
	  where a pass can prove them, inbank ptradds
	- inc/dec/asl/lsr/rol/ror and stz on memory, pei/pea, bit, trb/tsb, mvn
	- softfloat816.asm and string816.asm
	- a fixed page for leaf functions without a prologue
	QUESTION 2 decides the order.
	Done so far (2026-10-29), TestBaseLib65 816 from 108G cycles to 48G: string816.asm
	(mvn/mvp patched at run time) and runtime fast paths for multiply and divide;
	temporaries packed into shared places by live ranges with holes; 1 word values kept
	in A from their store to their one load in a block, and some in X (AllocateX); dead
	store and load removal; .relax branches; shifts by a count in X with a word in A;
	pei pushes; byte loads as a masked word unless volatile; and values of two or more
	words used once by the next instruction read into A a word at a time as it goes, in
	chains (CanFuse, WordInA: a load, or and store back is lda, ora, sta per word).  The
	IR side: loop rotation (with a preheader joining several ways in), strength reduction
	of p + i, loop idioms (memset, memmove, strlen, memcmp, memchr, strchr), narrowing,
	and unsigned divides by constants of bounded values as compares.

8.	The real machine: a memory map description (ROM and RAM regions, load and run
	addresses, the bank swap), a ROM image as the link output, a start up in the
	style of the user's startup.asm (copy, swap, zero bss, stack, D, DBR, call main),
	C interrupt handlers (__attribute__((interrupt)): save registers, set the mode and
	D, rti), and the emulator modelling the swap (see the memory notes).


Order of work
-------------

Steps 2, 3 and 4 don't touch the generator: the assembler and linker are in
Assembler65Lib, the test context is new, and CIR816Backend is tested with IR programs.
So they come first, while the other session removes the direct path.  Step 1 edits
the generator (CPP65Type's sizes, data, start up, thunks, runtime) and the IR front end
(the ABI's places), so it waits until that work is committed, or is agreed with that
session first.  Step 5 needs both.  Before editing CPP65Generator*, CPP65Type* or
CPP65IRFrontEnd*, check git status and ListAgents.


Testing throughout
------------------

- IR programs: the same text on both targets, results compared.
- C++ projects and the library suites: the same source natively, on the 65C64 and on
  the W65C816, results compared bit for bit (as FloatHelper and SQuaternion are now).
- Lockstep: compiled programs run on CFast65C816 and CW65C816 together for a while, so a
  difference between the emulator and the simulator shows up as soon as it happens.
- Cycle counts of the projects after each change in step 7, kept in a table.


Questions for the user
----------------------

1.	Answered (2026-10-25): int is 16 bits; "to get a 32 bit int explicitly declare it as
	an int32" (int32_t / int32 are long).  No 32 bit int option.
2.	Answered (2026-10-25): large data, far calls first; then an automatic mixed model.
3.	Answered (2026-10-25): "Which ever will optimise for speed, probably Direct page =
	frame".  The direct page frame first; step 7 measures the other where it may win
	(leaf functions).
