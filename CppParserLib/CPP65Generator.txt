65C64 code generator
====================

CCPP65Generator turns a parsed translation unit (CCPPSyntaxTree) into 65C64 assembly
for Assembler65Lib (syntax in Assembler65Lib/Assembler65Syntax.txt).  It is the first
back end of the C++ parser.  Usage:

	CCPP65Generator	cGenerator;

	cGenerator.Init(&cTree);
	if (cGenerator.Generate(&szAssembly))		//Appends the functions, runtime routines and data.
	{
		...
	}
	cGenerator.GetErrors();						//"line:column: message 'token'" lines.
	cGenerator.Kill();

Libc65 (commonlibraries/Libc65) has the 65C64's standard headers: stdint.h, stddef.h,
limits.h, stdarg.h, string.h, memory.h, stdlib.h, malloc.h, stdio.h, math.h, new,
ctype.h, time.h and assert.h (int and long are 32 bits, size_t is unsigned int).  Give
it to the preprocessor as a system include directory.  string.cpp, stdlib.cpp (malloc
over a heap at 0008:0000 to 000F:FFFF), ctype.cpp, time.cpp, softfloat.cpp and
math.cpp are written in C++ for the generator and compiled with a program as its
other translation units; softfloat.asm is 65C64 assembly, assembled with them
(CCPP65Builder::AddUnit takes .asm units).  There is no clock: time is 0 and clock is -1 (unavailable);
gmtime, localtime (UTC) and mktime use integers only.  stdio is only declared.
exit calls the atexit functions (at most 32, last first) and the fini table, then
_Exit, which stops at once with the status in A; abort is _Exit(EXIT_FAILURE).

The preprocessor's configuration gets the target's macros from
CCPP65Generator::AddDefines: __65C64__, which BaseLib's Define.h and DebugOutput.h use
for the platform (FILE_SEPARATOR, __ENGINE_PRETTY_FUNCTION__, EngineOutput ...).

Generate writes the translation unit as the assembly of an object, for
CAsm65Assembler::AssembleObject and CAsm65Linker (see Several translation units).
GenerateProgram puts the start up (AppendStartUp) in front of it, so one object is a
whole program.  The start up sets S to $1fffff, W to 0 and A, B, X and Y to 32 bits,
calls the init table (each global's R_Initialise, in link order), calls _main, calls
Libc65's atexit functions (a weak reference to __RunAtExit, so only when stdlib.cpp is
linked), calls the fini table backwards and stops.  main's result is in A when the
processor stops.  The start up also defines _Exit.  The
start up's object is linked first so it is at the start of the text, 0001:0000; the
reset vector is left to the loader.

Files: CPP65Generator.cpp (declarations, functions, statements),
CPP65GeneratorExpressions.cpp (expressions, places, constants) and CPP65Type.cpp (types).

The memory map, register widths, argument sizes, W, V and this below are the user's
(2026-10-23), as is cmp setting v like sub.  The rest are my choices.


Memory map (the user, 2026-10-23)
---------------------------------

	0000:0000 - 0000:FFFF	pseudo registers and scratch memory, addressed from W
							(the compiler's temporaries are the first $100 bytes)
	0001:0000				programs start here (code, then data)
	001F:FFFC				the stack starts here and works down

The stack is post decrement (a push stores at S - n + 1 ... S, then S -= n), so the
start up sets S to 001F:FFFF and the first 4 bytes pushed are at 001F:FFFC, 4 byte
aligned.  My reading of "start at 0x1FFFFC, 4 byte aligned": S = 001F:FFFC would put
the first 4 byte push at 001F:FFF9.


Types
-----

	char				1 byte, signed (as MSVC)
	short				2 bytes
	int, long			4 bytes (long is 4 bytes, as on Windows)
	long long			8 bytes (4 byte aligned in classes, as a 32 bit g++)
	float				4 bytes, IEEE 754 single
	double				8 bytes, IEEE 754 double
	long double			a double (as MSVC), but its own type for overloads
	bool				1 byte, 0 or 1
	wchar_t, char16_t	2 bytes, unsigned
	pointers			4 bytes (the address bus is 32 bits)
	enums				int

Values are kept in registers 32 bits wide, sign or zero extended from their type.
A long long is the exception: it is loaded, stored, pushed and operated on with the
register widened to 8 bytes for just those instructions (wth A, 8 ... wth A, 4;
wtth (A, B), 8 around an operator, and Y too for mul and div).  A narrower operand is
widened with wthx.  The signed 64 bit divide is R_DivideSigned64.  A double is held
like a long long (its bits); a float like an unsigned int.


Floating point (the soft float runtime)
---------------------------------------

The 65C64 has no floating point instructions, so float and double arithmetic,
comparisons and conversions call the soft float runtime.  Libc65/softfloat.cpp works on
the values' bits with integers only (it compiles natively too, and was checked bit for
bit against SSE on millions of values).  On the 65C64 its single precision functions
(SoftFloat* and SoftDoubleToFloat) are left out for Libc65/softfloat.asm's, written in
assembly for speed with the same results bit for bit (checked against softfloat.cpp
natively on millions of values; TestLibc65SoftFloat runs a few thousand per function).
A program that uses floating point is linked with both.  Cycles per call on the
simulator for normal operands from 2^-20 to 2^20 (softfloat.cpp's compiled code in
brackets): add 80 (2140), subtract 84 (2230), multiply 64 (2180), divide 85 (4930),
compare 25 (1145), sqrt 134 (16980), from int 39 (590), to int 19 (770), to double 21
(1005), double to float 46 (1110).
The generator pushes the operands like arguments (the right first) and calls:

	SoftFloatAdd Subtract Multiply Divide		(and SoftDouble...)
	SoftFloatCompare							-1, 0, 1, or 2 when a NaN is involved
	SoftFloatFromInt Unsigned LongLong UnsignedLongLong
	SoftFloatToInt Unsigned LongLong UnsignedLongLong	(towards zero)
	SoftFloatToDouble, SoftDoubleToFloat, SoftFloatSqrt, SoftDoubleSqrt

Rounding is to nearest, ties to even, with subnormals, infinities and NaNs.  NaNs
behave as SSE's (and so MSVC's) do: an invalid operation gives the default NaN
(0xFFC00000 for a float), a NaN operand comes back quietened (the first if both are
NaNs), and converting a NaN or an out of range value to an integer gives the most
negative integer.  Negation (flip the sign bit) and tests against zero (mask the
sign bit) are written in line.  Comparisons branch on the compare's result: < is
-1, <= is A + 1 below 2 unsigned, and so on, so every comparison with a NaN but !=
is false.  Constant expressions are worked out by the generator as the target
would (each float result rounded to float), for global data and constant operands.
Variadic arguments of type float are passed as double.  An expression that does
floating point counts as a call for keeping operands in pseudo registers.

Libc65/math.cpp has fabs, sqrt, trunc, floor, ceil, round, fmod, ldexp, frexp and
modf (exact), and exp, log, log10, pow, sin, cos, tan, atan, asin, acos and atan2,
with their f and l forms (the f forms work in double and round, so are correctly
rounded but for double rounding).  The methods are fdlibm's with improvements:

	exp		k ln2/64 + r, 2^(j/64) from a table to 106 bits, e^r - 1 by its series
	log		2^k (1 + j/64)(1 + u), log(1 + j/64) from a table, u to 106 bits
	pow		C99 F.9.4.4's special cases, then e^(y log x) with log x and y log x to
			106 bits (double-double: TwoSum, and TwoProduct by Dekker's split)
	sin cos	x mod pi/2: 33 bit pieces of pi/2 below 2^19, Payne-Hanek (1216 bits of
			2/pi) above; fdlibm's kernels with Taylor coefficients to x^18
	tan		sin over cos, each as two parts, the division's error put back
	atan	below 3/16 its series, else atan(k/8) from a table + atan((a - c)/(1 + ac))
	asin	its series to 1/2, then pi/2 - 2 asin(sqrt((1 - a)/2)) with the root split

The constants (the tables, ln2, pi/2's pieces, 2/pi's bits and the series
coefficients) were worked out exactly with Python integers and fractions, not
copied.  Compiled natively and checked against glibc's long double functions on a
million arguments each (including subnormals, overflow edges, x near 1, and huge
trigonometric arguments such as 6381956970095103 * 2^797, where glibc's own double
cos is several ulps out), every function is within 1 ulp, and correctly rounded for
all but 0.02 to 3.5% of arguments (sin, cos and tan are the 3%).  The test runs a
set of hard arguments on the 65C64 against the same references.


Registers (the user, 2026-10-23)
--------------------------------

A, B, X and Y stay 32 bits wide.  The widths only change where they must: Y is
narrowed to read, write or push a 1 or 2 byte value and set back straight after.
64 bit arithmetic will widen them when long long is supported.

		wth Y, 1
		cpy Y, [13 + V]
		cpy A, Y:s			; sign extend a char
		wth Y, 4

Narrowing a value in a register keeps the registers 32 bits wide:

		and A, 255			; (unsigned char)
		xor A, 128			; (char): flip the sign bit and subtract it
		sub A, 128

An expression's value ends in A.  A binary operator has its left operand in A and its
right in B, a constant (add A, 3) or a pseudo register (cmp A, [4 + W]).

W points at the pseudo registers, like the 6502's zero page and the 65816's direct
page, and is only changed around mul and div (which count in W from 0):

		psh W
		cpy W, 0
		mul
		pul W

When neither operand of a binary operator is simple (a constant or a variable), the
right is worked out first and kept in the next free pseudo register while the left is:

		cpy [0 + W], A
		...					; the left operand
		add A, [0 + W]

Pseudo registers are scratch: a call can use them, so when the left operand calls a
function the right is pushed on the stack instead.  The runtime routines don't use them.

V is the frame pointer.  X is a scratch register (addresses being stored through).


Calling convention
------------------

- Arguments are pushed on the stack last first, each at its own size (the user: a 16
  bit number is pushed as 16 bits), and removed by the caller with add S, bytes.  An
  argument is converted to its parameter's type first.  Arguments are not aligned.
- jsr pushes the return address (4 bytes).
- A function with locals or parameters keeps the caller's V on the stack and points
  V at its frame:

	_name:
			psh V
			sub S, frame
			cpy V, S
			...
	Lreturn:
			add S, frame
			pul V
			ret

- The result is in A (all 8 bytes of it for a long long).
- A variadic function's extra arguments are pushed like the others, after the default
  argument promotions (char, short and bool are int; arrays and functions are
  pointers), so Libc65's va_arg walks up the stack from the last named parameter.
- V, W and S are kept by a call; A, B, X, Y and the pseudo registers may change.

Places from V (they don't move when values are pushed):

	[1 + local + V]						a local
	[1 + frame + V]						the caller's V
	[1 + frame + 4 + V]					the return address
	[1 + frame + 8 + n + V]				the argument n bytes after the first

The frame is the locals, each aligned to its size (4 at most), rounded up to 4 bytes.
Every local in the function has its own place; blocks do not share places yet.
add, sub and cmp can't address memory with V (only W, X and Y), so a local used as a
right operand is loaded into B first.

C++ names are labels with an underscore in front (_main, _gTable).  Members are
_Class__name, constructors _Class__0, destructors _Class__1 and vtables _Class__2;
an overload has __n on the end (_Counter__0__1 is the second constructor), and a
thunk __t and how far it moves this.  A class without a name is the unit's
(Unnamed3), and so are static functions and globals (_Helper): their labels are local
to the unit's object, the others are .global.  C++ names
cannot contain __ or start with a digit, so these cannot clash.  Generated labels are
L and a number, string literals Str and a number, and runtime routines start with R_.


Instructions used for operators
-------------------------------

	+ - & | ^			add sub and or xor
	*					mul (A x B -> Y), keeping W
	/ % unsigned		cpy Y, A / cpy A, B / cpy B, 0 / div (Y / A -> Y, remainder in B), keeping W
	/ % signed			jsr R_DivideSigned (only added when used): divides the absolute values
						and fixes the signs (quotient negative if the signs differ, remainder
						with the dividend's sign)
	<< >> unsigned		shl shr
	>> signed			shr is logical, so a negative value is inverted, shifted and inverted back
	- ~					neg A, A / xor A, -1
	== != < <= > >=		cmp then bras / brac on z or c (unsigned), braso (n, v) (signed)
	&& || !				branches, the right operand only when needed
	pointer + n			n is scaled by the size pointed to (shl, or mul for other sizes)
	pointer - pointer	divided by the size pointed to

There is no branch on n = v, so "branch if signed greater or equal" branches over a bra:

		braso (n, v), L5
		bra L2
	L5:

Loops test their condition at the bottom.  A switch compares the value with each case
in turn.


Supported
---------

- Functions with integer, bool, enum, pointer and reference parameters and results
  (and void).  Default arguments.  Recursion.  Pointers to functions (jsr A).
- Global variables and arrays with constant initialisers, string initialisers for char
  arrays, and arrays sized by their initialiser.  extern declarations.
- Local variables, arrays and references, condition declarations (if (int x = f())).
- Statements: compound, expression, if, while, do, for, switch / case / default,
  break, continue, return, goto and labels (not past objects that need destroying).
- Static local variables with constant initialisers: data labelled S, a number and the
  name (S0_siCalls), local to the unit's object.
- long long and unsigned long long: every operator, conversions, literals, constants,
  returns and switches.
- Variadic calls (see Calling convention).
- new Type(arguments), new Type[count], delete and delete[]: the memory comes from the
  global operator new / new[] and goes back to operator delete / delete[] (Libc65's
  new.cpp, over malloc and free; a program can define its own).  An array of objects
  is constructed first to last; if its class has a destructor its count is kept in the
  4 bytes in front of it, and delete[] destroys the elements last first.  delete calls
  a virtual destructor through the vtable.  Deleting a null pointer does nothing.
  new(address) Type constructs at the address.
- GCC builtins: __builtin_ctz, __builtin_clz, __builtin_popcount (and their l and ll
  forms; ctz and clz use fsbi, and are the width for 0), __builtin_expect,
  __builtin_unreachable and __builtin_trap (stp).
- __func__, __FUNCTION__, __PRETTY_FUNCTION__ and MSVC's __FUNCSIG__ and __FUNCDNAME__
  (as string literal parts).  The pretty forms are "Class::Name", not the signature.
  Adjacent string literals are joined.
- Expressions: all the integer operators, assignment and compound assignment, ++ and --,
  ?:, the comma operator, calls, [] (either way round), * and &, casts (C style,
  static_cast, reinterpret_cast, const_cast, int(x)), sizeof, type traits
  (__is_trivially_constructible ...), enumerators, string literals, placement new.
- Constant expressions (array sizes, case labels, global initialisers, template
  arguments) include enumerators, const int variables, casts, sizeof and type traits.
- Overloaded functions and operators, chosen by the number of arguments (default
  arguments make up the rest) and how well their types match (the same type, then
  integer to integer, then related pointers; a reference matches its type).
- Classes, structs and unions (named or not), multiple inheritance with several
  polymorphic bases, templates: see below.
- float, double and long double: see Floating point.


Not supported yet
-----------------

Each gives an error "... is not supported by the 65C64 generator yet".  Declarations
the generator cannot do are only errors when what they declare is used (see When
code is generated).

- Class operator new and operator delete (the global ones are used), placement new
  with more than an address, new Type[count] with more than one dimension or an
  initialiser list; conversion functions, constructor templates, member class
  templates, explicit and partial specialisations, variadic templates.
- Virtual inheritance.
- Temporary objects that need destroying, in conditions; postfix ++ and -- on
  objects; conversion operators.
- Namespaces, local classes, static locals that are objects or have initialisers that
  are not constant (they would need a first time guard), extern and thread_local
  locals, wide and raw string literals.


When code is generated
----------------------

Like a C++ compiler, the generator only does what is used:

- Classes are laid out when they are first needed whole (an object, sizeof, a member,
  a base).  A class used only through pointers is never laid out.
- Functions defined outside classes and not inline are generated where they are
  defined.  Functions defined in classes, inline, constexpr and template functions are
  generated when they are first called (a queue is worked through after the
  translation unit).  A class's vtable (and so its virtual functions) is written when
  an object of the class is first made.
- Declarations of functions and extern variables are made quietly: if one cannot be
  done (an unsupported type), it is left out and its errors are reported when it is
  called.
- Bodies skipped in system headers are only declarations.
- GetExternals lists the functions and globals that were used but not defined, which
  must come from other translation units.

So a header like BaseLib/ArrayTemplate.h, with everything it includes, compiles as
long as what a program uses is supported.


Several translation units
-------------------------

Each translation unit is one object (Assembler65Lib: AssembleObject, then
CAsm65Linker; see Assembler65Syntax.txt "Objects and linking").  For each unit (a
CProject's, after Process):

	cGenerator.Init(&cTree);
	cGenerator.Generate(&szAssembly);				//One object's assembly.

and one more object for CCPP65Generator::AppendStartUp, linked first (it is a keep
section).  Each function, global, static local, temporary and string literal is a
section of its own named after its label (text._f, data._gTotal, data.S0_siCalls,
data.T0, rodata.Str0) so the linker can leave out what nothing uses
(CAsm65Linker::SetRemoveUnused; CCPP65Builder turns it on).  Generated labels (L5,
Str0, S0_siCalls, T0, R_Initialise3) are local to the object.  Functions and globals
with external linkage are .global; static ones and members of classes without a name
are local.  Inline, template and generated functions, vtables, thunks and runtime
routines (R_Pure, R_DivideSigned ...) are written by every unit that needs them, each
in a COMDAT section (text._A__f, rodata._A__2) and .global, so the linker keeps one
copy.

Runtime routines are resident sections, and so is the start up: CCPP65Builder::SetLazy
loads every other function from a drive when it is first called (see
Assembler65Syntax.txt "Lazy loading").

A global whose value isn't constant, or that is an object, has its own R_Initialise<n>
(and an object its own R_Finalise<n>) in a text section, with its entry in an init (or
fini) section associated with the global's data section.  The start up calls the init
tables in link order and the fini tables backwards, but the linker keeps a global's
entries only when something uses the global: a global nothing uses is not made at all,
even if its constructor does something else.  __attribute__((used)) (or __used__) after
the name keeps it (its data section is keep):

	Registrar gcRegistrar __attribute__((used)) (MakeThing);

TestCPP65RunProject (test/TestCppParserLib) does this for a list of units (each
directory's units share a CLibrary for their include settings), links them with
SetStubMissing and runs the program.  The test names the labels it expects to be
missing (the linker makes them a stp).  TestLibc65 links the Libc65 units it lists as
a CAsm65Library, so only the ones a test needs are linked.  BaseLib code
run this way: MD5 (the RFC 1321 suite), RedBlackTree (with a FreeList stub over
malloc), MersenneTwister (the MT19937 reference sequence) with Libc65's time,
QuickSort, BubbleSort and BinarySearch (with a MemSwp stub), and FloatHelper and
SQuaternion (a value type), against the same calls natively, bit for bit.

BaseLib is the benchmark for how much C++ is supported: on 2026-10-23, 344 of its 390
.cpp files compile without errors (317 before member templates, with 29 crashing on
unnamed classes in class templates).  Most of the rest use pointers to members
(DatasIO.h), need better overload ranking, take the address of an overloaded
function or use variadic templates.


Templates
---------

Class templates are instantiated when they are named with arguments
(CArrayTemplate<int>); their member functions, in the class and defined outside it
(template<class M> M* CArrayTemplate<M>::Get(size iIndex)), are generated with the
arguments when called.  The class's own name inside it is the instance.  Function
templates are instantiated with explicit arguments (IsTrivial<Class>()) or arguments
deduced from parameters declared as T, T*, T** ... or T&.  Non-type parameters and
default template arguments work.  template class Name<Arguments>; generates every
member.

Member templates (template<class T> T Twice(T t) in a class or a class template) are
kept for each class or class template instance and instantiated when called, with
explicit (c.As<short>()) or deduced arguments, the same way as function templates.
They can be static, defined in the class or outside it (template<class T> int
CValue::Size(T* p), and template<class M> template<class N> N SBox<M>::Mul(N n) for a
class template), and called on an object, through a pointer, qualified or unqualified
from another member.  A non-template member function that matches the arguments is
chosen before a member template; one with explicit template arguments always uses
the template.  An unnamed class inside a class template is a different class in each
instance.

Labels: an instance is Name__T and its arguments mangled: _CArrayTemplate__T_i__Add is
CArrayTemplate<int>::Add.  Types are v void, b bool, c char, h unsigned char, s short,
t unsigned short, i int, j unsigned, x long long, y unsigned long long, f float,
d double, e long double, P pointer, R reference, A count _ array, F return parameters
E function, C length name class; constants are L and the value (Ln for negative).


References
----------

A reference is the address of what it refers to, 4 bytes.  Using one loads the
address and works on what it points at.  A reference parameter is passed the
argument's address; a function returning a reference leaves the address in A; a
reference variable or field is bound to its initialiser's address.  The initialiser
must be an lvalue (temporaries are not supported yet).


Operators
---------

Member operator functions are named after their token: operator[] is _Class__opIndex,
operator+= _Class__opAddAssign and so on.  object[index], object op= value and
object = value call them when the class has them (assignment copies otherwise).


this (the user, 2026-10-23)
--------------------------

V is the frame of the function's locals and arguments (S can't be: it moves as values
are pushed).  this is in X.


Classes
-------

Layout: the bases in order, each aligned to its own alignment, then the vtable pointer
(4 bytes, when no base has one: a vtable pointer added to a class with non-polymorphic
bases goes after them), then the fields, each aligned to its size (4 at most).  An
empty base (no fields, no vtable pointer, empty bases) takes no space; an empty class
is 1 byte.  A union's fields are all at 0.  This is the layout of a 32 bit g++ or MSVC
build for these classes (CArrayBlock checked).  A pointer to a derived class is
converted to a pointer to a base by adding the base's offset (not to a null pointer);
the first base is at 0.

Several bases can be polymorphic.  A class shares its first base's vtable pointer (if
that base has one); every other polymorphic base subobject keeps its own vtable
pointer, which points at a secondary vtable laid out like that base's.  The secondary
vtables (the bases' own and their bases' secondary vtables, at their offsets in the
class) follow the class's vtable under its label, and constructors, destructors and
copies set every vtable pointer (cpy A, _Class__2 + 16).  A virtual call always has X
at the subobject of the class whose vtable has the slot, so a secondary vtable entry
for a function of a class further up is a thunk that moves X back first:

	_Both__Kill__t8:
			add X, -8
			jmp _Both__Kill

A function that overrides one in a secondary vtable also gets a slot in the class's
own vtable (as the Itanium ABI does), so calls through the class need no thunk.

Member functions get this in X.  A non-static member function keeps it at the bottom
of its frame (cpy [1 + V], X) and loads X again from there when something else has
used X: a call, a store through a pointer, or a label (code can arrive from anywhere).
Fields are [offset + X], so add, sub and cmp can use them directly.  Callers don't
keep X: it is not preserved by calls.

		cpy A, [9 + V]			; p
		cpy X, A
		jsr _Point__Move		; p->Move(...), not virtual
		cpy A, [0 + X]			; the vtable pointer
		jsr [4 * slot + A]		; a virtual call

Calls through a pointer, through this and implicit member calls are virtual; calls on
an object variable (s.f()) and qualified calls (Base::f()) are not.  A base's member
function is called with X moved on to the base.  A function with
the name and parameters of a base's virtual function overrides it (and is virtual); a
destructor overrides a virtual base destructor.  Pure virtual functions are R_Pure in
the vtable, which stops the processor.

Constructors: the bases in order (from the member initialiser list or their default
constructors),
the vtable pointer, then the fields in order (member initialiser, default member
initialiser, or their own default constructor), then the body.  A class that needs
any of that and declares no constructor gets one written for it.  A class without
constructors can be initialised from {fields}.  Destructors run their body, then
destroy the fields last first, then the bases last first; they set the vtable
pointer to their own class first.  A class gets a destructor when a base or a field
has one.  = default constructors and destructors are written by the generator.

Objects:
- Locals are constructed at their declaration and destroyed last first at the end of
  their block, and by return, break and continue on their way out.  return works out
  its value first and keeps it on the stack meanwhile.
- Globals are zero data, constructed by their R_Initialise before main and destroyed last
  first by their R_Finalise after it (the start up calls the init and fini tables,
  keeping main's result).  Globals nothing uses are left out (see Several translation
  units).
- Assigning and initialising from another object copies it a word at a time through Y
  (or calls the class's copy constructor or operator =).  A copy from a derived class
  keeps the destination's vtable pointer.  A class without a copy constructor whose
  bases or fields have them is copied as bytes, then those parts with their copy
  constructors (the implicit copy constructor).
- An object used as a value is its address (so its type is known).


Objects by value
----------------

An object argument is made in its argument's place on the stack (sub S, size, then
copied or constructed there) and the called function destroys it, as MSVC does.

A function that returns an object has a hidden first argument, pushed after the
others: the address to make its result at.  return value; constructs the value there
and the function returns that address in A, which is the call's value (an object's
value is its address):

	_Flip:							; SPair Flip(SPair p)
			psh V
			sub S, 8				; the local r
			cpy V, S
			...
			cpy A, [17 + V]			; the result address, before p at [21 + V]
			...						; r copied there
			cpy A, [17 + V]			; returned
			...

The caller passes the address of a temporary: every call or operator that makes an
object, and every Class(arguments), has its own place in the frame, worked out
before the function's code (AllocateTemporaries, after the locals so the types are
known).  Outside a function (a global's initialiser) it is data (T0).
Temporaries that need destroying are destroyed at the end of their full expression
(an expression statement, a declaration, a return); elsewhere (a condition) they are
not supported yet.

An object initialised from a call or operator that makes one of its class is made
where it is, not in a temporary and copied (as C++17 requires, so copy constructors
are not called for it): the hidden result address is the object's own, whether it
is a local, a global, a field, the function's own result (return f(x);) or an
argument's place on the stack (g(f(x))).  Class(arguments) initialising an object of
its class constructs it in place too.

Operators on objects call the left operand's member operator, or a free operator
function (declared, a friend, or an instance of a function template, such as
template<class M> SVec<M> operator * (M, const SVec<M>&)): binary operators, unary
+ - and ~, and comparisons (their result is tested).  Friend functions declared in a
class are free functions.
- Static data members are globals (_Class__name), defined outside the class; static
  member functions have no this.
