Thread safety plan for the object system
========================================

Today every part of the object system assumes one thread: Ptrs, froms, the distance walks, freeing, hollows, the
allocator under gcUnknowns.  The apps that have threads (the IDE's code model and build, the emulator runner, the sound
mixer) keep objects off them, and Sculpt's bake can't be shared among cores without "no Ptr is copied on a worker".
This plan makes the object system itself safe to use from several threads.  What is built is said under each step.


What "safe" means (the contract)
--------------------------------
  The object system promises:
    1. Its own bookkeeping (froms, stack pointers, distances, flags, the memory index, weak froms, the allocator) is
       never corrupted, whatever threads do with Ptrs, collections, OMalloc and Get.
    2. An object is never freed while any thread holds a Ptr to it, or while it is reachable from the root.
    3. Freeing stays exact and immediate: when the last thing holding an object lets go, it is freed then (or, for an
       object owned by another thread, queued for that thread: decision 3).
  It does not promise:
    4. That an object's own fields are safe to read on one thread while another writes them.  That is the class's
       business (its own CMutex), as with any data.  This includes the contents of a collection: two threads adding to
       one CArrayObject need a lock of their own, though the froms of what they add are always right.
  One rule for users follows from 2: a thread that uses an object across a point where another thread could let go of
  it holds a Ptr of its own.  `pWindow->mpCanvas->Draw()` through a field, with no stack Ptr, is only safe while
  whatever guards mpCanvas is held.  The single-threaded version of this rule (a Free() re-entering) exists already.
  And one from 4 for a program with a database (step 24f): Flush, and the save of a dirty stored object as it is
  freed, read the object's fields on the thread doing it, so a class whose fields other threads write saves under its
  own lock (in its Save), or the program flushes between jobs.


What is not safe today (survey)
-------------------------------
  Allocation
    A. gcUnknowns allocates from a CMemoryAllocator (its own CGeneralMemory: free lists on CSlabAllocator's 64 KB
       slabs).  No locking anywhere in it.  CUnknowns::miNumElements and mcIterables aren't either.  Objects and plain
       unknowns (UMalloc) share it, so it is reached from outside the object system too.
    B. gcStackPointers: one CFreeList of CStackPointer nodes for every stack Ptr in the process.
    C. Arrays inside objects (the from arrays, collections' storage, CPointerLocations) use gcSystemAllocator, which is
       malloc and safe already.
  CObjects
    D. mcMemory (index tree by OIndex, names), mcWeakFroms, mcClasses (a class is completed lazily at its first
       Allocate), the sequence handing out OIndexes (gcTransientSequence or the connection's), mcSource.
    E. mcRemovalContext.  It is re-entrancy state: a removal started while one is busy is taken for a nested one and
       queued.  A second thread's removal would be queued behind the first thread's as if nested.
    F. muiWalkStamp.  One walk at a time: a walk started while another is under way restamps what it visits (the
       comment on StartWalk says so).  Two threads walking at once would each lose their marks.
    G. Debug validation: with validation on, every from change runs ValidateObjectsConsistency over all of memory.
  Each object
    H. mapHeapFromObjects, mapHeapFromCollections, mpcStackFroms, mpsHub: changed by any Ptr pointing at the object.
    I. miDistToRoot (with the transient CLEARED state during a walk and the HELD_FROM_STACK state) and muiWalkStamp.
    J. muiFlags: 16 bits changed by read-modify-write.  SetDirty runs on every pointer change and is called by users
       (LogicalDirty); the collector sets FREED on the same word.  An embedded object's flags are its container's.
  Pointers
    K. CPointer::PointTo is several steps (add the new from, remove the old, perhaps free).  The copy constructor reads
       the source's mpcObject and then adds a from: between the two the object can be freed by another thread.
    L. Dereference writes: operator-> on a Ptr to a hollow loads the object, remaps every Ptr that pointed at the
       hollow (other threads' stack Ptrs included: one thread writing another's stack) and frees the hollow.
    M. Eviction and Kill of a held stored object go the other way: the object is replaced by a hollow while another
       thread may be inside one of its methods with a raw `this`.
    N. Weak<M>::Get against ClearWeakFroms.
  Freeing
    O. Free() is user code run inside the collector, on whichever thread let go last.  It changes Ptrs (re-enters), and
       it frees native things that belong to a thread: X11, GDI and Vulkan resources, a window.
    P. A user lock held while a Ptr is let go, against a Free() that takes the same user lock: a deadlock by lock order
       as soon as the object system has a lock of its own.
  The stack
    Q. "Held from the stack" is one notion for the process.  ObjectsKill reports stack pointers still alive, validation
       collects stack pointer addresses (ValidateNoStackPointerInside); neither knows about threads.  A Ptr in a job's
       data struct is a Ptr in a non-CObject, which the rules forbid already.
    R. CObjects on the stack (not allocated in Objects) take KillInternal's other branch and reach into the froms of
       heap objects from their destructors.
  Around it
    S. BaseLib globals used on the way: gcConstructors (registered up front, read after: fine if nothing registers a
       constructor once threads run), gcTransientSequence, gcDataOrderers.  gcLogger has its mutex; the __METHOD__ and
       ...ToString scratch pads are thread_local already.
    T. The 65C64 and 816 builds have one thread and no room: all of this must compile to nothing there, and object
       sizes must not change on any target (the size asserts on three targets).
    U. Tests assert exact from orders, counts, distances and sizes.  With one thread nothing observable may change.


The design
----------
  Three levels.  Each is complete and shippable.  Levels 1 and 2 are both to be built (decision 2); level 3 only if
  something needs it.

  Level 1: one lock (correct first)
    One recursive lock for the process (the audit says why not one per CObjects).  Every entry into the object system
    takes it:
      CPointer: the copy constructors, assignment, PointTo, the destructor, Return, Kill, MorphInto.  Never
        Dereference (see hollows below).
      CCollection and the four collections: every method that adds, removes, replaces or clears members, and the
        stack-held collection's construction and destruction.
      Weak<M> and CArrayWeakObject: Get, assignment, Compact.
      CObjects: Malloc, Get, GetPossiblyHollow, Contains, Root, Flush, Discard, Destroy, LoadForward, EvictInMemory,
        Dehollow, Remove, the free-object calls, iteration, the dumps and validators.
      CBaseObject: Kill, SetDirty/LogicalDirty/SetFlag, the stack CObject's destructor path (R).
    Recursive because Free() and Init() run user code that comes back in.  CMutex is not recursive, and gcLogger has
    hand-rolled the same thing (giLoggerLockDepth): step 6 makes that a BaseLib class (CRecursiveMutex: a lock, the
    owning thread and a depth) and the logger uses it.  The object system's is the same over a spinning lock (below).
    What this settles: A (for objects), B, D, E (only the lock's owner can be "nested"), F, G, H, I, J, K, N, R.
    The lock is skipped until the locking is switched on (ObjectsLocking, below).  That is NOT free: see Measurements.
    Done with care (the test is one load and a branch never taken, the locking out of line, nothing at all in
    operator->) it costs about 0.6 to 1 ns on a stack Ptr's copy and drop (14 ns today) and nothing that can be
    measured elsewhere; done carelessly it cost 25% there and 37% on operator->.  On the 65C64 and the 816 the calls are
    compiled out (T); on the hosts they are always built (decision 7).
    The lock is not a CMutex.  A pthread mutex that is fought over puts its waiters to sleep: 12 threads copying Ptrs
    took 5 to 6 microseconds a copy, twenty times less work done than one thread alone.  It spins, then yields.
    What level 1 is good for: threads that seldom touch a Ptr.  At one Ptr copy per 0.8 microseconds of other work it
    holds up to about 4 threads and gets worse after.  It is the base everything else stands on (every writer path
    needs it), not somewhere to stop if workers are to use Ptrs freely.

  Level 2: stack Ptrs without the lock (measured: this is what makes threads worth having)
    Most Ptr traffic walks nothing: a stack Ptr taken to, or dropped from, an object that stays attached to the root
    (FromRemoved returns at once for it today).  Those become readers; anything that changes a heap from, walks, frees,
    loads or evicts is a writer and runs alone, as in level 1.
    A reader marks itself in a flag of its own thread's and looks for a waiting writer (one exchange, about 5 ns); a
    writer raises its flag and waits for every thread's reader flag to drop.  So readers on different threads never
    write the same cache line, and a walk sees stack froms that cannot change under it.
    Where a worker's stack froms are kept is the part that matters.  First tried: on the object, as now, under a small
    lock picked by the object's address.  It scales when threads hold different objects (40 ns flat to 12 threads) and
    not at all when they hold the same one (3.6 microseconds at 12 threads, at one copy per 0.8 microseconds of work):
    the object's list is fought over.  What works: each registered worker keeps its own table of (its stack Ptr, the
    object), and nothing is written to the object.  12 ns a copy and drop on one thread (less than today's 14: no node
    from the free list), 14 to 25 ns on 12 threads, the same object or not.  The thread that called ObjectsInit keeps
    its stack froms on the objects as now, so nothing changes for one thread.
    The cost moves to the writer: "has this object a stack from?" is the object's own list and then a look in each
    worker's table.  It is asked only of objects found detached from the root.  (Built and measured in step 18.  Stack
    Ptrs to unattached objects stay under the lock: unrooted graphs are slow on any number of threads.)
    The dumps, validation and the remap of a loaded hollow's stack Ptrs read the tables too.
    The call sites don't change: step 9 already marks each entry point as a reader or a writer (ObjectsRead / ObjectsWrite
    guards that are the same lock in level 1).
    Allocation leaves the writer side here: OMalloc is allocate (the allocator's own safety), add to mcMemory (its own
    small mutex), then a reader's stack from.  That is when the allocator has to scale.  (Step 21, not built: decision 8.
    Allocating as a reader can't let threads make more objects while every free is a writer's; level 3 is the way.)

  Level 3: a CObjects per thread (only if objects must be BUILT in parallel)
    Levels 1 and 2 serialise every heap pointer change, so threads that build object graphs gain nothing.  The answer
    that scales is no sharing: a worker has its own CObjects (and CStackPointers), builds there, and the finished graph
    is handed to the main CObjects in one step (Adopt: re-register its objects in the other memory index; no copy when
    both allocate from the same thread-safe allocator; OIndexes come from one locked sequence).  Pointers between two
    CObjects stay forbidden and validated.  OMalloc/ORoot would go through a thread_local "current objects" in place of
    gcObjects.
    (Planned in detail and built as step 25: see Level 3 as built.  Decisions 11 to 15 changed "Pointers between two
    CObjects stay forbidden": a worker's objects may point at main objects.)

  Threads register
    The home thread (the one that called ObjectsInit) switches the locking on, ObjectsLocking(true), before any other
    thread touches an object, and off again when the others are done: it is the one thread that can know it isn't in
    the middle of something.  Each other thread then calls ObjectsThreadInit() before it touches an object and
    ObjectsThreadKill() when it has finished.  Registration gives the thread its stack pointer count (a thread_local,
    raised and lowered with every stack from; Debug only), and in level 2 its reader flag and its table of stack
    froms.  ObjectsThreadKill reports stack pointers the thread still has, as ObjectsKill does for the process;
    ObjectsKill and ObjectsLocking(false) refuse while other threads are registered.  In Debug a CStackPointer node
    also records its thread, for the dumps (Q).
    An object system call from a thread that hasn't registered, once the locking is on, is an Error2.

  Which thread frees (O)
    Every CObjects has a home thread (the one that called ObjectsInit).  A batch found dead on another thread is not
    freed there: under the lock it is marked FREED, its weak froms are cleared and it is taken out of the memory index
    (so nothing can reach it: no Get, no Weak, no from of a live object the walks will follow), and it is queued.  The
    home thread frees queued batches whenever it next takes the lock, and from ObjectsCollect() which a tick calls.  So
    Free() always runs on the home thread, window and renderer code needs no change, and freeing is still immediate
    for everything the home thread lets go of itself.  The cost: memory let go by a worker lives until the home thread
    next touches an object.
    What stays on the thread that let go: the walk that finds the batch (it is how the object system knows anything is
    dead, and distances must be right before the lock is released), the FREED marks, the weak froms, the index.  What
    moves: the kill order, the destruction callback, every Free(), the pointer tos and froms coming off, the memory.
    Until the home thread gets to them the dead objects still point at live ones and are still in those objects' froms;
    the walks pass over FREED froms already (a batch whose Free() changes pointers relies on it today).
    A dirty stored object in the batch is saved before it leaves the index, on the thread that let go, or a Get of it
    would load the old one from the database in the meantime (built in step 14).
    (The alternative, freeing on the thread that let go, needs every Free() in WindowLib, the
    native canvases and the renderers to be safe on any thread.)

  The lock order rule (P)
    The object lock is taken before any lock of the user's that a Free() takes; put the other way, don't let go of a
    Ptr that could be the last while holding a lock some Free() wants.  Home-thread freeing removes most of it (workers
    never run Free()).  In Debug the recursive mutex can record that a Free() is running, and a small ObjectsAssertNoFree
    helper lets a class check its own lock isn't taken inside one.

  Hollows, loading and eviction (L, M)
    Without a data connection there are no hollows (ReplaceWithHollow needs a stored object), which is every UI app
    today: operator-> stays a plain load of mpcObject with no lock.
    With a data connection another thread's Dehollow may be rewriting this very Ptr.  Locking in Dereference is ruled
    out by measurement: operator-> went from 1.3 ns to 9.2 ns with the lock on, and even an unused test for it cost
    0.5 ns.  Nothing is added to operator->.  The choices are (a) stored objects are used by one thread at a time
    until the Codabase transaction work decides how CObjects and transactions meet (open there already), or (b) a
    hollow that has been loaded stays as a forwarder while another thread's stack Ptr still points at it (its Dehollow,
    which only a Ptr to a hollow ever calls, takes the lock and answers with the loaded object), so the cost falls
    only on Ptrs to hollows.  (b) was to be designed with the transaction work, and (a) kept until then; (b) was
    designed and built on its own instead (Forwarding hollows, below: step 24), and (a) lifted (24f).
    Eviction is only allowed while no other registered thread is inside the object system or holding a stack pointer
    (checked from the per-thread counts): in practice, between jobs.  Killing a held stored object is refused while
    another thread holds a stack pointer to it or to an object embedded in it (24f).

  Flags (J)
    All flag writes go under the lock in level 1 (SetDirty included).  If SetDirty from users shows up in profiles, the
    dirty bit alone becomes an atomic OR; no layout change is needed for that.

  Handing objects to jobs (Q)
    The caller keeps a Ptr (or the object is rooted) until the job is done and gives the job a raw pointer, or the job
    data is itself a rooted CObject.  A worker that wants to keep something takes its own stack Ptr on its own thread.
    A worker that only reads a graph nobody changes (Sculpt's bake sampling a material) takes one Ptr at the top and
    uses plain pointers below it: no Ptr traffic, no locking, full speed on every core.  This is the pattern to prefer.


The audit (step 8)
------------------
  Every public way into the object system, by what it must hold.  It is what step 9 places guards from and what the
  Debug assertions check.
    W  a writer.  It changes what the object system keeps (froms, distances, flags, the memory index, the classes), or
       frees, loads or saves.  It takes the lock (OBJECTS_WRITE).
    R  a reader.  It only reads what the object system keeps.  It takes the lock in level 1 (OBJECTS_READ); in level 2
       it is one of many at once, shut out only by a writer.
    I  inside only.  Machinery that is public because C++ makes it so: it is only ever reached from a W or an R, and
       asserts in Debug that the lock is held (OBJECTS_INSIDE).
    -  nothing.  It touches only the caller's own object, or what never changes once an object exists (its index, name
       and class), or a collection's own storage, which is the business of whoever uses the collection (the contract).
    H  the home thread alone, with no other thread registered: set-up and shut-down.

  Two rules came out of proving the guards (step 16):
    A way in that only passes what it is given to other ways in has no guard of its own (a pointer's Kill is its
    object's Kill; a Dump is its Print written to the console).  It is listed with the "-"s.
    A way in that reads a pointer out of the object system's own tables (the memory index, a weak reference) and must
    hold the object before the lock is let go does it with the machinery beneath (AssignObjectInside, PointToInside),
    not with another way in.  It then takes the lock exactly once, which is what the test of the guards counts.

  The lock is one for the process (not one for each CObjects): a pointer must be locked before the object it points
  at can be asked which CObjects it is in, and stack pointers and threads are the process's anyway.

  CPointer, Ptr<M>

       operator = (all), PointTo, PointToNull, AssignObject, Return, MorphInto.
       (Level 2: the constructors and destructor of a stack pointer to an object attached to the root are readers.)
       Since step 19 these do their own locking, with no guard: a stack pointer between objects attached to the
       root is changed by a reader, without the lock (PointToReading).
    R  NumStackFroms, NumHeapFroms, NumEmbedded, NumPointerTos, GetDistToRoot, IsDirty.
    I  UnsafePointTo, UnsafeClearObject, AddHeapFrom, SetEmbedding, Load, PointToInside, AssignObjectInside,
       PointToFromOutside, PointToReading.
    -  Kill, LogicalDirty and the Dumps (they are the object's);
       CPointer(), operator -> and &, Dereference, DereferenceArrow (decision 4: nothing is added to them),
       operator !, == and !=, operator bool, IsNull, IsNotNull, IsEqual, IsNotEqual, Object, ObjectPtr, BaseObject,
       This, Embedding, IsEmbeddingAllocatedInObjects, IsHollow, GetIndex, GetName, IsNamed, ClassName, GetClass,
       IsInstanceOfTemplateClass, TemplateClassName; operator + (the class's own AddOperator).

  CWeakPointer, Weak<M>
    W  PointTo, PointToWeak (the other weak reference is read and this one pointed at it in one step), HoldObject
       (the weak reference read and the stack pointer taken are one step, or the object could be freed between them).
    I  Release, ClearWeak, RemapWeak, GetWeak, PointToInside.
    -  operator = (all) and Get, which are those three; IsNull, IsNotNull, Object, This.

  CCollection, CArrayCommonObject, CArrayObject, CSetObject, CIndexObject, CMapObject
    W  Add, AddAll, Set, Insert, Put, Remove (all), RemoveAll, RemoveEnd, RemoveDuringIteration, KillAll, TouchAll,
       Kill, the destructors (a collection on the stack).  (A method that only passes what it is given to another of
       these has no guard of its own.)
    I  ClearPointerTos, BaseNumPointerTos, BaseGetPointerTos, RemovePointerTo, RemapPointerTos, FreePointers, Free,
       Save, Load, GetEmbeddedObject, UnsafeGetObject, UnsafeRemove, Dereference, the member location hooks
       (CanLocateMembers, AddMemberLocations, FreeMemberLocation, IsMemberAt, RemoveMemberAt, ReplaceMemberAt,
       HaveMembersMoved, NumLocatedMembers), RemoveCopies, ValidateConsistency, ValidateMemberLocations,
       GetIndexForTesting, GetUnknownMap.
    -  Init, Get, UnsafeGet, Contains, NumElements, NonNullElements, IsEmpty, StartIteration, Iterate,
       StartIterationPointer, IteratePointer, Sort, EnsureSorted, IsSorted, CalculateIsSorted, IsMustSort, IsSubRoot,
       MakeSubRoot, GrowTo, Dump, PrintSlots.  (What they return is a CPointer, whose own constructor is the guard.  A set that sorts
       itself when it is read is, like any collection, not to be read on one thread while another changes it.)

  CArrayWeakObject
    W  Add, Remove, RemoveAt, Compact, RemoveAll, Get.
    I  ClearWeak, RemapWeak, GetWeak, Move, Save, Load, Free.
    -  Init, NumElements, Contains.

  CRoot
    W  Add (all), Remove (both), RemoveAll, KillAll, TouchAll.
    R  Get, UnsafeGet, GetAll, GetFirst, NumObjects, IsSetHollow.
    I  CreateSet, NullifySet, KillInternal, TestGetSet.
    -  Init, IsRoot, IsSubRoot.

  CObjects, and the functions beside it
    W  Malloc, Get (all), GetPossiblyHollow, Root, Dehollow, Flush, Discard, Destroy (both), LoadForward,
       GetStoredHeapFroms, ForceSave, EvictInMemory, Remove (both), LogicalDirty, FreeObjects, AddFreeObject,
       RemoveFreeObject, ValidateObjectsConsistency, ValidateEmpty, ValidateNoDirty, PrintGraph and
       PrintStackPointers (they mark what they have visited), Collect; OMalloc, ONMalloc, OMallocNoI, ONMallocNoI,
       ORoot, ObjectsFlush, ObjectsDiscard, ObjectsValidate, ObjectsDump, ObjectsCollect.
    R  Contains (both), NumMemoryIndexes, NumMemoryNames, NumDatabaseIndexes, NumDatabaseNames, NumFreeObjects,
       NumWaitingToBeFreed, StartMemoryIteration, IterateMemory (each call: an iteration is not held across calls, so
       it is only right while no other thread allocates or frees), PrintMemoryNames, PrintMemoryUseIteration,
       PrintMemoryUseRecursion, DumpMemoryUseIteration (it writes out the two indexes themselves).
    -  The other Dumps; CFreeObjects' Add, Remove and NumObjects, which are its array's.
    I  FromRemoved, RemoveInKillOrder, ReplaceBaseObject, ReplaceWithHollow, StartWalk, the Allocate... functions,
       GetNamedOrAllocateHollow, AddWeakFrom, RemoveWeakFrom, ClearWeakFroms, MoveWeakFroms, GetWeakFroms, GetMemory,
       GetStackPointers, GetClasses, GetConstructors, GetIndexGenerator, the Test... functions.
    -  Null.
    H  Init, Kill, ObjectsInit, ObjectsKill, AddConstructor, AddSource, the three Set...Callbacks, EnableValidation,
       DisableValidation.

  CBaseObject, CObject, CEmbeddedObject (what a class's own code and its users call)
    W  Kill, Flush, SetDirty, SetStored, LogicalDirty; PostInit (it marks the object initialised and dirty, by
       when its Init may have shown it to other threads); PreInit for an object that has no class yet (an object on
       the stack: its class is completed in classes every thread's objects share); an object on the stack's
       destructor.
    R  PrintFroms, PrintPointerTos, PrintHeapFroms.
    I  What asks an object itself about its froms, its distance or its flags (GetDistToRoot, NumHeapFroms,
       NumStackFroms, HasHeapFroms, GetHeapFroms, CanFindRoot, IsDirty, GetFlags, the Prints and the rest): they are
       what the walks are made of, and a test in each would be paid a million times a walk.  From outside they are
       asked through a CPointer (which is a reader) or with the lock held.
       And everything that changes froms, distances, walk stamps or flags (SetFlag, AddHeapFrom,
       RemoveHeapFromTryFree, AddStackFrom, RemoveStackFromTryFree, the Unlinks, KillInternal, FreeInternal, DoneKill,
       ClearPointerTos, RemapPointerTos, SetDistToRoot, SetWalkStamp, the heap from iteration, the Validates, Allocate,
       EmbedIn, the Save and Load pieces), and the field declarations Class() makes (Pointer, WeakPointer, Embedded,
       Primitive, the Unmanageds, Nes), which run inside the allocation that completes the class.
    -  Destroy (it is CObjects'), the Dumps; Init, PostInit and PreInit for an object allocated in Objects (it is
       known to nobody but the thread making it), GetIndex, GetName, IsNamed, GetClass, HasClass, ClassName, IsRoot, IsSubRoot, IsHollow, IsCollection,
       IsObject, IsEmbedded, GetEmbeddingContainer, GetEmbedding, NumEmbedded, GetObjectsThisIn, GetClasses,
       IsAllocatedInObjects, SerialisedSize, PrintIdentifier.

  CUnknowns is not under the object lock.  It has a lock of its own round its allocator, its count and its iterables
  (step 11): unknowns that are not objects are added and removed with no object system in sight.

  What the audit turned up
    A read that writes.  Getting an element of a collection, or using a pointer, wrote the element or the pointer
    back whether or not it had just loaded a hollow: two threads reading the same element were two threads writing
    it (ThreadSanitizer, in the first threaded test).  They write only what has changed now.
    Switching the lock on.  The plan had a thread's registration switch it on.  It can't: the thread registering
    would be racing the home thread, which may be half way through something it started with the lock off.  The home
    thread switches it on itself (ObjectsLocking(true)), between operations, before any other thread registers, and
    off again when the others have gone.
    ORoot() looks the root up by name every time it is called.  Under the lock it is no worse, but it is a search
    where a pointer would do.
    SetDirty is called by every assignment to a primitive field that changes it.  It is a writer; a class whose
    primitives are written often on several threads will feel the lock.


Measurements (2026-11-17)
-------------------------
  Asked: does this damage what performance the object system has?  A prototype of the guards was built on a private
  copy and timed against the code as it is.  Release, 64 bit, -O3 with LTO, one pinned core, the least of 9 runs, runs
  interleaved; the machine was shared, so differences under about 3% are noise.  ns for each operation:

                                        today   guards, lock off      lock on, one thread    naive guards, off
    stack Ptr copy + drop (rooted)       14.2    14.8   (+4%)          22.0   (+55%)          16.6  (+25%)
    Ptr by value + a method call         15.7    16.7   (+7%)          24.8   (+58%)          18.8  (+15%)
    operator-> + a method call            1.3     1.2                   1.2                    1.9  (+37%)
    field re-pointed (rooted)            64.0    64.1                  67.6   (+6%)           64.7
    OMalloc + free                        789     805   (+2%)           823   (+4%)            789
    OMalloc, array add, remove            801     817   (+2%)           841   (+5%)            835
    build a window tree, per node        1141    1159   (+2%)          1247   (+9%)           1173
    focus across the tree, per move     46675   46686                 46767                  47470
    free the tree, per node               888     935   (noise)         919                    963

  "Naive" is a guard object at each entry point (nested through PointTo), a test in Dereference and a per-thread stack
  pointer count: the first thing written.  "Guards" is one test per entry point with the locking out of line, nothing
  in Dereference, the count left to Debug.  "Lock on" is the spinning lock, never fought over.
  Only the stack Ptr pays: its copy and drop is the one operation short enough for a test to show.  Everything that
  walks or allocates is hundreds of ns and the guard is lost in it.

      one object                   spinning lock        755    821   1041   2321   3825

  What it says: one lock (level 1) is right but does not scale, and a pthread mutex is far worse than a spin; stack
  froms kept on the object don't scale for a shared object whatever the lock; per-thread tables do.  Allocating on
  several threads is slower than on one until allocation leaves the lock (level 2's last part, or level 3).
  Not measured: the writer's side of level 2 (walks asking the workers' tables), anything in Debug, 32 bit, Windows.
  An aside: OMalloc and free is about 790 ns, fifty times a stack Ptr copy.  That is where the object system's time
  goes today, threads or not.  Looked into under The allocator: nearly half of it is glibc.


The allocator
-------------
  The user's decision: "The TrueMallocator exists, see if you can make it faster than malloc and thread safe.  Fall
  back to lock now and measure if not."  It can be: a prototype was built and measured (2026-11-17), so the fallback
  isn't needed.

  Where the time goes first.  OMalloc and free is 15400 instructions (callgrind): 45% of them are inside glibc's
  malloc, realloc and free, called through gcSystemAllocator for the memory index's tree nodes (CIndexTreeMemory::Put
  reallocs them, 28% alone) and the scratch arrays of the distance calculation and the removal; the index itself is
  another 20%, the distance calculation 17%, and the object's own memory (CGeneralMemory under gcUnknowns) 12%, nearly
  all of it CFreeList::GetLastNodeElement.  So the allocator that matters most is the one behind gcSystemAllocator,
  not the one under gcUnknowns.

  What was built (the prototype, 450 lines over CTrueMallocator unchanged):
    An arena for each thread: a CTrueMallocator over 4 MB chunks from the system, another chunk added to the same
    lists when it fills.  Only its thread allocates from it or frees into it, so that path has no lock.
    A block's arena is found from its address: chunks start on 4 MB boundaries and a chunk's header names its arena.
    In front of each arena, a list for each block size: every 16 bytes up to 1 KB, then 16 sizes to each power of two up
    to 64 KB.  The common malloc is a pop and the common free a push.  The lists hold 2 MB at most; past that they are
    emptied back into the arena in turn, so sizes no longer used don't sit there.
    A block freed by another thread is pushed onto its arena's remote list (one compare-and-swap, no lock).  The owner
    takes the whole list back when one of its own lists runs dry, onto its front lists.
    Over 1 MB comes straight from the system.  A thread that ends leaves its arena for the next thread that starts.

  Measured (Release, 64 bit, glibc 2.39, the least of 3 runs), ns for each operation:

    malloc + free, 16 KB                  12.7        22.4             13.2            19.6          4.6
    churn, 2000 live, 16-528 bytes        12.9        21.1             29.0            30.2          4.8
    churn, 20000 live, 16-4112 bytes      76.6        79.2             49.4            54.0         16.1
    10000 x 100 bytes, then free all       8.2        10.8             13.1            20.0          5.0
    realloc doubling, 16 to 4096          23.4        24.0             14.0            15.6         10.6
    realloc + 8 bytes, 8 to 256            7.0         7.2              4.5             8.5          4.6

                                               threads:   1      2      4      8     12
    churn, each thread its own blocks   glibc            20     23     20     21     21
                                        + one lock       48     97    310    766   1200
                                        per thread        8      8     10      8      8
    every block freed by another thread glibc            32     75    114    132    134

                                        per thread       16     40     77    110    112

  CTrueMallocator as it is, or with a lock round it, is slower than glibc for small blocks and does not scale; with
  an arena per thread and the front lists it is faster than glibc in every case measured, from 1.2 to 4.8 times.

  In the object system (the prototype behind gcSystemAllocator, nothing else changed, one thread, the least of 5):
    OMalloc + free 772 -> 576 ns (-25%), OMalloc + array add + remove 801 -> 602, build a window tree 1095 -> 1022 a
    node, focus move 46.8 -> 43.2 us, free the tree 849 -> 782 a node.

  Checked: 12 threads allocating, reallocating and freeing each other's blocks (16 bytes to 4 MB) with their contents
  verified, threads ending and starting again between rounds: no errors.  ThreadSanitizer finds one thing: a thread
  reading the size of a block it holds (realloc of a block from another arena) while the owner sets or clears the
  "block before is free" flag in the same header word.  Harmless on the hardware, a race in the language: the host
  build reads and writes that word as a relaxed atomic (the same instructions).
  Still to do before it is a BaseLib class: Windows (VirtualAlloc for the aligned chunks), 32 bit, chunks given back
  to the system (never, in the prototype), debug names and iteration if anything under gcSystemAllocator needs them,
  IsValid over every chunk, the counts.  Blocks over 1 MB are an mmap each, slower than glibc's if they come often.
  Not measured: long runs (fragmentation), Debug.
  The 65C64 and the 816 keep CTrueMallocator alone, unchanged: the arenas are a class of their own on top of it.
  A caution on the small numbers: a stack Ptr's copy and drop moved between 13.6 and 17.7 ns from one build to the
  next with the same 349 instructions (where things land in memory).  Differences of a nanosecond or two between
  builds are checked by counting instructions, not by the clock.  Counted, the guards add 23 to those 349 (6.6%).

Forwarding hollows (step 24, planned and built 2026-11-18)
----------------------------------------------------------
  What it is for: a program with a database whose threads share its stored objects.  Until it was built decision 4
  kept a stored object to one thread at a time; 24f lifted that.

  The Codabase transaction work and this don't touch.  Every thread here shares one CObjects and its one data
  connection, which is only called with the object lock held (and a CCodabase session takes calls from any thread
  already).  A thread that wants a view of the database of its own (a read-only transaction's snapshot: the open item
  in CodabaseTransactions.txt) wants a CObjects of its own: level 3, step 25, with that CObjects over the thread's
  transaction.

  What happens today, right on one thread.  Using a Ptr to a hollow loads the object (CObjects::Dehollow).  The loaded
  object takes the hollow's place (ReplaceBaseObject: every pointer to the hollow, in objects, on the home thread's
  stack and in any thread's table, is rewritten to the object; weak froms move) and the hollow is freed there and
  then.  With other threads:
    1. Thread B has read a pointer's mpcObject (the hollow) in operator-> and not yet called the hollow's Dehollow,
       which is where a lock can first be taken.  Thread A loads the object and frees the hollow.  B calls into freed
       memory.  The window is a few instructions in Dereference, and nothing can be put there (decision 4).
    2. Two threads using one hollow: the second, once it has the lock, finds the hollow freed (1), or would load the
       object a second time.
    3. A rewrites words that B reads without a way in: B's own stack Ptrs, and the fields and collection elements B
       reads through operator->.  A pointer is written whole by the hardware, so nothing breaks, but it is a race as
       far as the language (and ThreadSanitizer) goes.
    4. A set, and a map's keys, are kept in address order.  A loaded object has a new address, so a load leaves the
       collection out of order and the next read sorts it: a read that writes, and two readers can sort at once.  That
       is why their members are saved as fat hollows: a fat hollow is allocated at the object's size and the object is
       made in place, so the address doesn't change.  But made in place, the object's class (its vtable) is there from
       the start of its load, so a thread that reads the address meanwhile (through a field or an element) calls
       straight into a half loaded object.  With threads a fat hollow can't be loaded in place.

  The design
    A loaded hollow forwards.  Pointers are rewritten as today, so any pointer read after the load gives the object.
    The hollow isn't freed: it is put aside on its CObjects, paired with the object it was loaded as (nothing is added
    to the hollow, whose size the 65 targets assert).  A hollow's Dehollow takes the lock before it reads anything of
    its own, then asks whether it forwards; if it does it answers the object and loads nothing (1 and 2).
    A forwarder is freed once no thread can still be in 1's window.  Each thread counts its reads and the times it
    takes the lock, which it can't do inside the window (the window ends in the hollow's Dehollow, under the lock).  The
    home thread checks as it collects: the forwarders put aside before its last check are freed if every other
    registered thread's count has moved since; those put aside since wait for the next.  A thread that does nothing
    with objects keeps them waiting (a hollow each, nothing more); a thread that ends no longer counts.  With no other
    thread registered, or the locking off, a hollow is freed at once as today: one thread sees nothing new.
    The words a load rewrites are read and written as relaxed atomics on the hosts (3): CPointer::Dereference's read
    of mpcObject, the remap's writes, and the reads of a collection's elements that take no way in.  On x86-64 and
    ARM64 these are the instructions used now (checked by counting operator->).  Plain on the 65C64 and the 816.
    Dereference stops writing back what the hollow's Dehollow answered: the remap has rewritten the pointer already.
    A Debug assertion shows that first; CArrayCommonObject::Dereference likewise.
    The object a forwarder names is alive whenever a forwarder is rightly asked: the pointer B read is the one the
    load rewrote to that object.  A Debug build checks that the object is still in memory under the hollow's index
    when a forwarder answers.

    Sets and maps (4) are decision 10: (a), the user's choice with step 24a's measurements.
      a. Ordered by object index (an embedded member by its container's index, then its place in it).  A load changes
         no order, and fat hollows are retired: every hollow loads into memory of its own and forwards.  The order is
         the order objects were made in, the same on every run and under every allocator (address order broke four
         tests when gcUnknowns changed allocator, step 23).  Costs: a comparison reads both objects' indexes where it
         compared two addresses (the speed to be measured first); and a hollow made for a name alone must have the
         database's index for that name from the start (today the object loaded for it takes the database's, a
         different one, which would move it in a set).
      b. Address order kept, and fat hollows on one thread.  While other threads are registered a fat hollow is loaded
         into memory of its own like any other, the sets and maps it is in are put back in order at once under the
         lock, and a read never sorts.  But an iteration on one thread can see a member move when another thread loads
         one (it is skipped, or seen twice), and no lock of the user's can stop that: a load is somebody's read.

  What doesn't change
    EvictInMemory evicts everything in memory, so it stays between jobs (refused while another thread holds a stack
    pointer).  Evicting part of memory while threads run (the game's paging) needs a design of its own: an object
    another thread is using mustn't be evicted, and the only sign of that the object system sees is a stack Ptr.
    The Kill of a stored object (it leaves a hollow behind for its holders): step 13 refuses it while another thread
    holds any stack pointer.  Narrowed to a stack pointer to that object or one embedded in it.  Killing an object
    another thread is using is otherwise the user's business, as it is for any object.
    Written through (IWT_Yes): no readers, level 1, as now.
    Flush, and the save of a dirty stored object being freed, read the object's fields.  Decision 1 already makes a
    class guard its own fields: a class whose fields are written on several threads saves under its own lock (in its
    Save), or the program flushes between jobs.

  What goes: ValidateStoredOnOneThread, and the Debug rule that leaves a stored object's pointers to writers.

        lock's), and no walk of either system crosses into the other: to a worker's walk the main object is a leaf,
        to a main walk the field is a stack pointer.  A main object pointed at a worker object is refused (validated
        in Debug): a worker's object isn't attached to main's root, and main's walks can't see into the worker.

Decisions (the user's, 2026-11-17)
----------------------------------
  1. The contract: the object system protects itself and lifetimes; a class protects its own fields.
  2. Level 1 first (a spinning lock, not CMutex), then level 2's per-thread stack froms as a planned step.
  3. Free() runs on the CObjects' home thread, queued from other threads.  The thread that disconnects a graph still
     does the walk that finds it dead ("that's as expected").
  4. Threaded programs with a database: stored objects used by one thread at a time and eviction only between jobs,
     for now; forwarding hollows designed with the Codabase transaction decisions.  Nothing is added to operator->.
  5. The allocator: "The TrueMallocator exists, see if you can make it faster than malloc and thread safe.  Fall back
     to lock now and measure if not."  Done as a prototype: faster than glibc in every case measured, and thread
     safe.  See The allocator.
  6. Threads register explicitly (ObjectsThreadInit/Kill); an unregistered thread touching objects is an error.
  7. The half nanosecond is accepted on the hosts: one configuration, guards always built; compiled out only for the
     65C64 and the 816.
  8. (2026-11-18, with step 22's measurements) Step 21 isn't built: allocating as a reader can't let threads make
     and free more objects, and the memory index with a lock of its own is too wide a change for what it gives.
     Level 3 is the way to build objects in parallel.
  9. (2026-11-18, with step 23's measurements, asked twice) gcUnknowns goes onto the new allocator: "Switch anyway",
     for the 16% on OMalloc and free.  The second asking said a tree's build and free would be 17 and 23% slower;
     measured like for like afterwards they are the same and about 3% (step 23 says how the first figures came to
     be wrong).
  10. (2026-11-18, with step 24a's measurements) Sets and maps are ordered by object index, not address: a load
     never changes an order, so fat hollows are retired and the size they were made at leaves the record format.
     Contains costs 4 to 90 ns more and an Add 8 to 41% more, for sets of 10 to 100000.
  11. (2026-11-18, for step 25) A worker's objects may point at main objects, held as the worker's stack pointers hold
     them and made ordinary pointers at Adopt; main objects may not point into a graph that hasn't been adopted.
  12. Adopt(pTop) moves pTop and every object reachable from it that is still the worker's, and returns a pointer to it
     in the main object system.  Anything else the worker made stays with the worker, which carries on building.
  13. A worker's object system has no database: its objects take their indexes from the main object system's sequence
     and are saved when the main one flushes after Adopt.
  14. A name a worker's object has that the main object system already uses is found at Adopt, which then refuses the
     whole graph and moves nothing.  (Not at creation, as Codabase transactions do it.)
  15. The memory index is replaced within step 25, before level 3 is built on it.
