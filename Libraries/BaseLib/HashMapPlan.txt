Why
---

Every map in BaseLib is ordered: CMapBlock and CSetBlock (a sorted array with holding buffers, a node malloced per
element), CRedBlackTree, and the CIndexTree trie.  Nothing gives an O(1) lookup, and BaseLib's FNVHash.h is used by
no table of its own.  So code needing one has written it itself, five times, all open addressed with linear probing
over a power-of-two table, all growing by doubling at half full:

    where                                    key                         value / what it keeps
    CppCompilerLib/NameSet.cpp               text (pointer, length)      set; doesn't own the text
    CppCompilerLib/DefineMap.cpp             text, hash kept on CDefine  CDefine*; Remove (backward shift)
    CppCompilerLib/ASCIIIndex.cpp            text, hash kept on the name dense array of names + int32 table
    CppCompilerLib/IRFunction.cpp:400-470    SIRType + uint64 bits       dense array of constants + uint32
                                                                         table holding index+1; the index is
                                                                         the constant's IRReference
    SupportLib/SFTQuantiser.cpp:100-140      uint32 colour               dense array of counts + key/place
                                                                         tables

And three more work round it with a sorted map keyed by a hash, collisions handled by hand:

    CppCompilerLib/CPPHeaderIndex.cpp:185    CMapLongTemplate keyed by FNV of (file, line, column)
    CppCompilerLib/PPHeaderCache.cpp:283     CMapLongTemplate keyed by FNV of pointers; psNext chains the
                                             headers that share a key ("compare them")
    LogicimLib/ComponentSpriteCache.cpp:493  CMapBlock; a key past MAX_KEY_SIZE has its tail replaced by its
                                             FNV hash and length

Three of the five (IRFunction, SFTQuantiser, ASCIIIndex) have already arrived at the same layout, which is the one
proposed here: the entries in a dense array in the order they were added, and the hash table holding only indexes
into it.

The design proposed
-------------------

1. The layout: an entry array and an index.

        entries   SHashEntry { uint32 uiHash; K key; V value; }  in a CArrayTemplateBase, in the order added
        index     a power-of-two array of Count (size, or lsize), each 0 for empty or an entry's index + 1

   Lookup: hash the key, probe the index linearly from hash & mask; for each full slot compare the entry's uiHash
   first and the key only if the hashes match.  The index is never more than half full (all eight tables use half;
   with 2 or 4 byte slots the room is cheap).  Growing doubles the index and puts each entry back by its kept
   hash: no key is hashed or read again.  The entries array grows by itself as arrays do.

   What this gives:
     - Iteration is the entry array, 0 to NumElements: the order things were added in, the same on every build,
       whatever the capacity.  The compiler's output is proved byte-identical, so an order that depends on the
       table's size would be a trap.
     - An element has an index, which stays its own while nothing is removed: IRFunction's constants need exactly
       that (their index is the IRReference).
     - Write/Read are the entry array's; the index isn't written but built again on Read.
     - On the W65C816 the probing is 16-bit arithmetic and the slots 2 bytes.

2. Removal: the entry is taken out of the index by backward shift (as CDefineMap::Remove does now: no tombstones),
   and the last entry moves into its place in the array, its index slot rewritten.  O(1); no holes, so no
   compaction and nothing to skip when iterating.  The cost: after a Remove the order is no longer the order
   added, and the moved entry's index changes.  Still deterministic.  (Question 2.)

3. Pointers into the map last until the next Put or Remove.  Get returns a pointer into the entry array, which
   moves when the array grows.  CMapBlock's last for ever, as each element is its own malloc; that is what this
   is designed not to do (a malloc per element is the slow part, and on the W65C816 the large part).  Something
   that needs a pointer to last keeps a pointer as the value: CDefineMap already keeps CDefine* from its own
   CMemoryStackExtended.  (Question 3.)

4. The code: one block class compiled once, thin templates over it.  This is BaseLib's way (CMapBlock and
   CMapTemplateTemplate) and keeps the W65C816's code small.

        class CHashBlockBase<BLOCK>     compiled once for CArrayBlock and CArrayLargeBlock (extern template, as the
                                        arrays are).  Entries of a fixed size given to Init (hash + key + value);
                                        knows nothing of their types.  Find(uiHash, pvKey, fEquals),
                                        Put(uiHash, pvKey, ...), Remove, Get(index), NumElements, iteration,
                                        Write/Read, Kill with an optional CDataFree.
        typedef CHashBlock and CHashLargeBlock   (derived classes, not typedefs, so they can be declared ahead:
                                        ArrayTemplatesPlan.txt's reason)

        template<class K, class V, class HASH = SHashOf<K>, class BLOCK = CArrayBlock>
        class CHashMapTemplate          inline; hashes the key with HASH::Hash(const K*) and passes the hash in,
                                        so the hash is inlined and the block calls HASH::Equals only when two
                                        hashes match (rare: one indirect call on a hit).
        template<class K, class HASH = SHashOf<K>, class BLOCK = CArrayBlock>
        class CHashSetTemplate          the same with no value (a value size of 0).

   SHashOf<K> is the default: for an integer or pointer key one FNVMix64 step folded to 32 bits; for a struct,
   FNVHash32 over its bytes (so a struct key must have no padding, or must have its own HASH: SIRType + bits does).
   A caller with its own (SFTQuantiser's colour mix) gives its own HASH.

5. Text keys: a key that is a view, not owned.

        struct SHashText { const char* sz; size uiLength; };   with SHashOfText: FNVHash32 of the text, memcmp

   That is what NameSet, ASCIIIndex and CDefineMap use: the text lives somewhere else (the source file, the
   define's own memory) as long as the map.  A map that owns copies of its text (CHashMapString<V>, the text kept
   in a CMemoryStackExtended beside the entries, freed with the map) is wanted too: the survey's group E (about
   25 text-keyed maps, the assembler's symbol table among them) all copy their keys today.

6. Names.  CHashMapTemplate and CHashSetTemplate by BaseLib's habit (CMapTemplateTemplate, CSetTemplate); the
   files HashOf.h (SHashOf, HashMix32/64, HashBytes, HashEquals), HashText.h (SHashText, SHashOfText),
   HashBlock.h/.cpp, HashMapTemplate.h, HashSetTemplate.h, HashMapString.h.  The interface follows CMapBlock's
   (Init/Kill/ReInit, Get/Put/Remove/HasKey, NumElements, Write/Read, SetDataFreeCallback); keys are given by
   pointer, as CMapTemplateTemplate's are.  Iterating is by index (GetKey(i), GetValue(i)), the entries being one
   array.  Find and PutIndex give an entry's index.  There is no CMapAccess (the PutIntInt family) for it unless
   asked.

Questions (all answered 2026-11-23 as assumed: "Go for it with your suggestions and plan changes")
--------------------------------------------------------------------------------------------------

1. A map, a set, or both?  Assumed: both, the set being the map with no value (one block, two thin templates).
   NameSet is the only set among the eight; the rest are maps (CPointerLocations a multimap).

2. Order after a Remove.  Assumed: the last entry moves into the gap (O(1), no holes).  The other way keeps the
   order added for ever: a removed entry leaves a hole that iteration skips, compacted when holes pass half the
   entries (Python's dict).  That costs a flag or a reserved hash per entry and an index that changes at an
   unpredictable compaction instead of at the Remove.  Of the eight only CDefineMap and CPointerLocations remove,
   and CDefineMap's Dump sorts by name.

3. Pointers that move.  Assumed: Get's pointer lasts only until the next Put or Remove, said in the header, with
   pointers as values where something must last.  The other way is the entries in chunks that never move (as
   CListBlock or CFreeList keep them): pointers last, but Get(index) costs a divide by the chunk size, or a
   power-of-two chunk, and it isn't one array to Write.

4. The hash on the W65C816.  FNVHash32 is a 32-bit multiply per byte, which on the 816 is a library call per
   byte.  Assumed: the kept hash is uint32 on every target (so a map Written on a PC Reads on the 816 and
   agrees), and a 816 program that finds hashing slow gives its own HASH.  The other way is a 16-bit kept hash
   where SIZE_16 (half the entry's hash bytes, a cheaper hash), and the files no longer the same on both.

5. How far does step 6 go?  Assumed: a (the hash-keyed four) and b (the compiler's address-keyed maps, timed)
   are done; c, d and e are done where a timing or a simpler class shows it.  (f became part of c.)

6. Load factor.  Assumed: at most half full, as all eight are now.  Three quarters would halve the index's memory
   (the index is the smaller part: 2 or 4 bytes a slot against the entry) for longer probe runs.

7. A multimap mode (a key with many values, iterated by key) for CPointerLocations?  Assumed: no; it stays as it
   is, being the one table of the eight that is a multimap, and has its own MovePointer and MoveLocations.

Why
---

Code that keeps a queue or a bounded history in an array drops its oldest element with RemoveAt(0), which moves every
other element down.  A ring (push and pop at both ends) is the general answer, but on CArrayBlock it fits badly: a
ring's contents wrap past the end of its memory, which CArrayBlock's growth doesn't know to move, and its used count
would have to be the ring's capacity, so none of the array's own functions (NumElements, Find, Write) would mean
anything.  And CArrayBlock gives its contents up when a realloc fails (found on the W65C816 for the hash map,
above).  So a ring would need memory of its own, as CHashBlockBase has.

But no code found pushes at the front of a queue: every one pushes at the back and takes or drops at the front.  That
is a queue, and a queue fits CArrayTemplate as it is: the elements from a front index to the end are the queue, taking
the front moves the index on, and when the dead elements before it are more than the live ones after it one
RemoveRange moves the live ones down.  Each element is moved at most a few times in all, so taking the front is
amortised O(1), and the elements stay in order in one array, so iterating is indexing.

What it isn't for: speed.  The histories are small (UNDO_LOG_MAXIMUM 1000, UNDO_STACK_MAXIMUM 100,
IDE_NAVIGATION_MAXIMUM 100, IDE_RECENT_EDITS and LOGICIM_NAVIGATION_HISTORY_SIZE 50), so RemoveAt(0) costs little
there; the gain is that each says what it is.  A ring with its own memory is built only if something turns up that
pushes at the front.

The design proposed
-------------------

1. QueueTemplate.h, header only (it is a few lines over CArrayTemplate, which is compiled once already):

        template<class M, class BLOCK = CArrayBlock>
        class CQueueTemplate
        {
        protected:
            CArrayTemplateBase<M, BLOCK>  maElements;   //Elements [muiFront, maElements.NumElements()) are the queue.
            Count                         muiFront;
        public:
            Init, Init(pcMalloc), Kill, ReInit
            M*    Push(void);  M* Push(M* pElement);      //At the back.
            bool  Pop(M* pDest);  bool Pop(void);         //The front, copied out (or not) and gone.
            M*    Front(void);  M* Back(void);            //NULL when empty.
            M*    Get(Count uiIndex);                     //0 the front.
            Count NumElements(void) const;  bool IsEmpty(void) const;
            bool  RemoveBack(void);                       //A history going back (RemoveTail).
            void  RemoveFrom(Count uiIndex);              //Everything from uiIndex to the back (the redo end).
        };

   BLOCK is CArrayBlock (counted in size, MAX_SIZE bytes on the W65C816) or CArrayLargeBlock (lsize), as the arrays'.
   A new element is given its virtual function table (CPostMalloc) but isn't zeroed, as CArrayTemplate's aren't:
   the caller initialises it (the histories all do).

2. Taking the front: muiFront moves on; when muiFront is more than the live elements (and at least 8, so a small
   queue doesn't move on every pop) the live ones are moved down with one RemoveRange(0, muiFront).  An empty queue
   sets muiFront to 0 without moving anything.  So pointers into the queue last until the next Push or Pop, the
   hash map's rule.

3. No maximum in the class: a bounded history is "while (NumElements() >= uiMaximum) { Front()->Kill(); Pop(); }"
   at the caller, which is also where it knows what dropping one costs (the Kill).

4. No Write/Read unless a caller turns out to need it: none of the eight is written to a file as an array.

CArrayBlock keeps its contents when a grow fails (planned 2026-11-23, Q4 answered yes; done 2026-11-24)
=======================================================================================================

Where it is: steps 1 to 4 built and committed 2026-11-24.  TestArrayGrowFails.cpp (TestBaseLib) is the failing
mallocator (CTestFailingAllocator) and the tests of steps 1 and 3; against the old ArrayBlock.cpp it fails (Add gave a
pointer when it couldn't grow).  TestHCP65Lib hadn't run when it was committed (stopped for low memory): it runs once
over this and the steps after it.

Why
---

CArrayBlockBase<SIZE>::SetArraySize is where every array (CArrayBlock, CArrayTemplate, CChars, and the rest built on
them) gets its memory.  When it must grow and can't, it throws the array's contents away:

  - a failed Realloc: mpvArray is set to the NULL it gave and the counts to 0.  The contents are lost and the old
    memory leaks (realloc leaves it allocated when it fails);
  - past MAX_SIZE where size is 16 bits (SIZE::CheckSize): Overflowed() frees the array, "as if out of memory"
    (ArrayTemplatesPlan.txt).

And it returns nothing, so the functions that grow an array (Add, AddGetIndex, InsertAt, InsertNumAt, InsertBlock...,
AddNum, GrowToAtLeastNumElements, Resize, Copy, SetUsedElements and their templates' forms) can't tell, and go on to
use memory that isn't there.  The hash map's test found this on the W65C816, where memory runs out before MAX_SIZE,
and CHashBlockBase was given memory of its own because of it; CQueueTemplate, built on CArrayTemplate, has it still.


What is there now (read 2026-11-23)
-----------------------------------

  - SetArraySize (ArrayBlock.cpp:232) is called from SetUsedElements (188) and ten other places (339, 429, 470, 707,
    767, 1509, 1514, 1526 and those through SetUsedElements); Overflowed() from five (254, 309, 333, 423, 1631).
  - No test makes a grow fail: TestBaseLib has no mallocator that can be told to fail, and nothing tests Overflowed.
  - Shrinking (SetArraySize to fewer elements) is the policy memory's "CArrayBlock releases memory" says to leave
    alone; a shrink whose realloc fails can keep the bigger memory it has.


The design proposed
-------------------

1. SetArraySize returns bool.  When it can't grow (a realloc that gives NULL, or past MAX_SIZE where size is 16
   bits) it changes nothing and returns false: mpvArray, miNumElements, miUsedElements and miChunkSize are as they
   were.  A shrink whose realloc fails keeps its memory and its new count, and returns true.  Overflowed() no longer
   frees: it says so (gcUserError in debug, as now) and SetArraySize returns false.
2. Each function that grows passes the failure on in the way it already has for no memory: a pointer it gives is
   NULL, an index ARRAY_ELEMENT_NOT_FOUND (or the large one), a bool false.  Functions that return nothing (Push(M*),
   Copy, InsertBatch) leave the array as it was; where a caller needs to know, a bool form is added.
3. Nothing else changes: chunk sizes, the shrink and free policy, what an array writes to a file.
