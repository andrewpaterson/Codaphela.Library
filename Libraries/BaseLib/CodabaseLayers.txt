Codabase Layers
===============

Design notes for layered Codabases and for freeing objects before they are flushed.  Discussed 2026-11-05.  Nothing here is implemented yet.


What Codabase is for
--------------------

Codabase must serve three uses, often at the same time:

  - Virtual memory for objects.  A game running in limited RAM pages changed parts of its world (say the map) out to disk and back in.  No transactions and no write-through are needed for this.
  - A document store.  The initial game level, saved by the artist who made it.  The game never changes it.
  - A fully transactional (ACID) database, changed only at transaction boundaries.  See CodabaseTransactions.txt.

Today only the tests use a database-backed CObjects.  Every application (LogiCim, HCP65 emulator, tester, IDE, WindowInputTester) calls ObjectsInit() with no data connection and saves in its own formats.


Free before flush (decided)
---------------------------

A dirty object is flushed before it is freed.  Freeing never discards changes to an object that can still be reached from the database.

Only real garbage (objects nothing in the store can reach any more) may be dropped without saving.  Whether garbage is ever deleted from the database is still to be checked.

Stored objects (decided 2026-11-06, implemented): an object read from or written to the database is marked stored (OBJECT_FLAGS_STORED).  An object loaded by name alone has no path to the root (its holders are only in the database), so Flush saves a dirty stored object whether or not it can find the root, and CObjects::RemoveBatch saves dirty stored objects before freeing them.  Objects that never reached the database are freed without saving, as before.  CObjects::EvictInMemory saves every dirty object that is stored or can find the root before it frees them (decided 2026-11-06).  ObjectsKill does not save: ObjectsFlush or ObjectsDiscard (marks everything clean) must come first, and Kill reports any object Flush would save that is still dirty (CObjects::ValidateNoDirty, decided 2026-11-06).

A database can be opened read-only (the document store as the game sees it).  A read-only database refuses writes.  What happens to a refused write is still open; the options were:
  1. Fail when the object is marked dirty (earliest, points at the code making the change).
  2. Fail at flush or free and discard the change.
  3. Keep the dirty object in memory (cannot be freed).
  4. Allow changes in memory only; a freed dirty object loses its change.
With layering (below) the game never writes to the read-only level database, so a refused write should only happen on a bug.


The three stores in the game case
---------------------------------

  - Initial game database.  Unchanging.  Opened read-only.
  - Virtual memory database.  Writable, discarded on shutdown.  Holds exactly the objects changed since the level was loaded (only dirty objects are flushed into it; clean objects are freed and reloaded from the level).
  - Save game database.  Its own database (decided 2026-11-05), written by serialisation; see "Save games" below.


Layered connection (decided 2026-11-06)
---------------------------------------

A stack of layers that CObjects sees as one CDataConnection (chosen over CObjects holding a list of connections).  Existing code to build on: CWriteTransaction already reads its own records first and falls through to its CCodabase, with removals as tombstones (bRemoved).  The external object sources (CObjectsSource) cannot hold the databases: they are found by name only (dehollowing by OIndex never looks in them), the native converter gives what it reads new OIndexes, and nothing is written to them.  The layering lives below CObjects (BaseLib / Codabase) so that "flush before free" stays "write to the connection".

  - Reads go to the top layer first and fall through to lower layers.
  - Writes (including flush before free) go to the top writable layer.
  - The writable layer is a separate second CCodabase, not a spilling write set.
  - The same OIndex in two layers: the first (top) layer wins.
  - The layered connection owns one writable sequence (CObjects already takes one CSequenceConnection, separate from its CDataConnection; a CCodabase has none).  When the layers open, it starts above every lower layer's highest OIndex, so a new object never hides a lower layer's object.  Needs: a way to raise a CSequence's next index, and each read-only layer reporting its highest OIndex.
  - Sub-sequences (decided 2026-11-06): a CSequence can reserve a block of indices (written to its file at once, never handed out by GetNext).  A sub-sequence hands out indices only from one reserved block and fails when it runs out.  When a level is released its sequence reserves a block for the game; the game's writable sequence is a sub-sequence of that block, so the virtual memory layer and save games number inside it.  A later update to the level continues the level's own sequence above the block and cannot collide with anything a save game created.  Saves of the same level can share the block: only one save is ever layered over a level.  The level records its reserved block(s).
  - Deletes in a top layer are tombstones ("did not exist"), so a deleted lower-layer object does not reappear.  CodabaseVersions chain entries already have a "did not exist" entry.
  - Names resolve top down, with tombstones for removed names.

The virtual memory layer needs no durability (no Begin/End brackets, no fsync).

  Use                     Layers (top first)                                  Top layer at the end
  Game                    virtual memory (writable, not durable) -> level     discarded at shutdown
  Artist editing level    level (writable)                                    -
  Transaction             write set (spillable) -> base                       commit merges into base; abort drops it


Lookup order (decided 2026-11-06)
---------------------------------

An object is looked for in:
  1. Memory.
  2. The writable database.  A changed object is written here and keeps its OIndex.
  3. The read-only database(s).
  4. The external object sources (CObjects::GetFromSources).

An object keeps its OIndex wherever its changed copy is written: references to it held in a read-only database cannot be updated.


Database ID in the OIndex (dropped 2026-11-06)
----------------------------------------------

Decided 2026-11-05 and dropped 2026-11-06 as not worth it: the top 8 bits of an OIndex would have held the ID of the database that created the object.  Because an object keeps its OIndex when its changed copy is written to the writable database, the ID could only ever say where an object was created, and the lookup order above finds objects without it.  An OIndex stays a plain CSequence counter.

What the ID also gave: new objects created in different databases (the virtual memory layer, a save game, a level updated after release) had OIndexes that could not collide.  Now the first layer wins when two layers hold the same OIndex.


Save games (decided)
--------------------

A save game is a serialisation into its own database.  Decided 2026-11-05:
  - What is saved comes from reachability, not from marking objects.  The game keeps a list of named roots (for example one per player or per world region); saving walks the object graph from each of them.
  - References to unchanged level objects are acceptable, even desirable.  An unchanged object from a read-only database is written as a reference (its OIndex), not copied.
  - Changed and new objects are copied in full: objects in the virtual memory layer and objects dirty in memory.  A level object the player changed (an opened door) is in the virtual memory layer and is copied.
  - Only reachable objects are saved, so garbage never reaches a save.

Proposed with it (not yet decided):
  - Transient pointer fields (say M_TransientPointer(name) in Class()) that the walk never follows, for runtime-only state such as caches and UI.  They load as NULL and are rebuilt.
  - Loading a game needs no replay.  The save database becomes a read-only layer: virtual memory (writable, empty) -> save game (read-only) -> level (read-only).  The next save walks the roots again, picking up changes from both the virtual memory layer and the previous save layer and dropping anything no longer reachable.

Consequence: saves depend on level OIndexes staying stable.  Editing a level must never renumber existing objects; updating a released level may add objects but not rewrite existing ones.


Dirty detection (idea, not decided)
-----------------------------------

Managed fields (M_*) and Ptr assignments mark objects dirty themselves.  Unmanaged fields (U_*) need SetDirty by hand.  Proposal: hash each object's U_* fields (known from Class()) when it is loaded or saved; at flush and at free, re-hash objects that are not marked dirty and treat a mismatch as dirty.  Fallback: a debug-only check that catches missed SetDirty calls.


Open questions
--------------

  - What a read-only database does with a refused write (options above).
  - Whether new objects in a read-only session are an error, or allowed until one has to be written.
  - Whether write-through (IWT_Yes) becomes "autocommit per change".
