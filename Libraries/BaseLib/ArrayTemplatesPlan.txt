The macro-made array classes as templates (plan, 2026-11-15; the user's answers the same day)
==============================================================================================

The intent (the user, 2026-11-15): turn the classes a macro makes, ARRAY_BLOCK and the rest, into templated classes
that work on ordinary 32 and 64 bit targets as well as the 16 bit W65C816.

Where it is: the questions the plan started with are answered (under "Answered", the user's rulings and what was
found).  Done 2026-11-15, all five steps: every family is a template written once (CArrayBlockBase<SIZE>,
CArrayTemplateBase<M, BLOCK>, CArrayTemplatePrimitiveBase<M, TEMPLATE>, CArrayCharBase<PRIMITIVE>, CCharsBase<STRING,
TEXT>) in its own .h and .cpp, the macros and .inl files are gone, and nothing got bigger or slower but for one 65C64
difference the user ruled insignificant (step 4).  Left: building it with MSVC (on Windows).


Why
---

BaseLib has five families of classes that are each written once and made twice, by #including their text between
ArraySizeNatural.inl (or ArraySizeLarge.inl) and ArraySizeUndef.inl:

    written as                  natural (counted in size)      large (counted in lsize)
    ARRAY_BLOCK                 CArrayBlock                    CArrayLargeBlock
    ARRAY_CHAR                  CArrayChar                     CArrayLargeChar
    CHARS                       CChars                         CLargeChars
    ARRAY_TEMPLATE<M>           CArrayTemplate<M>              CArrayLargeTemplate<M>
    ARRAY_TEMPLATE_PRIMITIVE<M> CArrayTemplatePrimitive<M>     CArrayLargeTemplatePrimitive<M>
    ARRAY_HEADER                SArrayTemplateHeader           SArrayLargeTemplateHeader

They are templates in what they do and macros in what they are.  The HCP65 IDE's index, Rename, Find Usages and
every refactoring see code a macro made as having no source of its own, and refuse it (the IDE's Refactorings.txt,
T6, and its RefactoringQuestions.txt, 48).  As real templates they are ordinary source to all of those, and T6
needs nothing built for it.

The design proposed
-------------------

1. A size policy: a small struct for each of the two variants, with everything the macros vary.

        struct SArrayNaturalSize
        {
            typedef size    Count;
            static const size   Max = MAX_SIZE;             //a constant on every target: (d)
            static const size   NotFound = ARRAY_ELEMENT_NOT_FOUND;
            static const bool   CheckSize = (true where SIZE_16, else false);

            static void* Copy(void* pvDest, const void* pvSource, size uiBytes);    //memcpy16 on the 816, memcpy
            static void* Move(...);  static void* Set(...);  static int Compare(...);  static void Swap(...);
        };
        struct SArrayLargeSize { typedef lsize Count; ... memcpy and the rest ... };

   The five functions are inline and only forward.  The policy's names are to be the house's: this is a sketch.

2. Each family written once as a template with the policy as a parameter (the last, for those that have M):

        template<class SIZE> class CArrayBlockBase : public CMalloc, protected SArrayHeaderBase<SIZE> { ... };
        template<class M, class SIZE> class CArrayTemplateBase : public CArrayBlockBase<SIZE>, protected CPostMalloc<M> { ... };

   ASIZE becomes typename SIZE::Count, ARRAY_MEMCPY becomes SIZE::Copy, #ifdef ARRAY_CHECK_SIZE becomes
   if (SIZE::CheckSize) (a constant the compiler folds), and so on.  The text is otherwise what the .inl has.

3. The old names kept, by a class of each name that derives from the template and adds nothing:

        class CArrayBlock : public CArrayBlockBase<SArrayNaturalSize> {};
        class CArrayLargeBlock : public CArrayBlockBase<SArrayLargeSize> {};
        template<class M> class CArrayTemplate : public CArrayTemplateBase<M, SArrayNaturalSize> {};

   Not a typedef: a typedef can't be declared ahead ("class CChars;"), and these are, in many headers.  A derived
   class keeps every one of those as it is.  What it costs: a function of the template that takes or gives its own
   type (TakeFrom(ARRAY_BLOCK* pcSource), Copy(ARRAY_TEMPLATE<M>*)) takes or gives the base, which a CArrayBlock is,
   so calls compile; one that gives a pointer to its own type gives the base's, which isn't a CArrayBlock*: each
   such function has to be looked at.  CHARS_NATURAL (the large CChars naming the natural one) becomes an ordinary
   name or a second parameter.

4. The code stays compiled once.  ArrayBlock.cpp and Chars.cpp instantiate the templates explicitly
   ("template class CArrayBlockBase<SArrayNaturalSize>;" and the large one), and the headers declare them
   "extern template", so no other file compiles their bodies.  This is what keeps compile time where it is (the
   816's code size is safe either way: (b)).  MSVC, g++ and the CPP65 compiler all honour it: (a).

   What extern template leaves out, on every compiler: the functions defined outside the class without inline
   or constexpr.  Those defined in the class are inline and still compiled by each unit that calls them, as
   they are now; so ArrayBlockCode.inl's and CharsCode.inl's functions stay defined outside the class, without
   inline, and the few short ones in the class stay in it.  A member template of the class (ArrayTemplate.inl
   has none that matter) isn't instantiated by "template class" and is compiled where used.


Answered (2026-11-15)
---------------------

  a. Do the CPP65 compiler's W65C816 and 65C64 code generators honour explicit instantiation and extern template?
     The user's ruling: yes, they must; where they don't, the compiler is fixed.  What was found: "template class
     X<A>;" already generated every member; "extern template" was parsed and ignored, so each unit compiled the
     bodies again (correct, only slower); "template int f<int>(int);" was an error.  Now (CppCompilerLib,
     CCPPUnit::ExplicitInstantiation, ExplicitFunctionInstantiation, IsInstantiatedElsewhere):
       - extern template class X<A>; a unit doesn't generate X<A>'s functions defined outside the class that
         aren't inline or constexpr: their labels are externals.  Those defined in the class, and the
         constructors, destructors and vtables the compiler writes, are still generated by the unit (COMDAT, as
         before).  [temp.explicit] 10.
       - template int f<int>(int); and template int f(int); generate the function template's instance; extern
         template ... of either makes it an external, unless the template is inline or constexpr.
       - An explicit instantiation after an extern one in the same unit generates (Instances.cpp includes the
         header with the extern declarations, then instantiates).
       - The explicit instantiation's functions are still COMDAT sections, so a unit without the extern
         declaration that makes its own copy links (the linker keeps one).  A library unit (linked only when
         used, as BaseLib's are) that holds the instantiation is linked for the labels the others use.
       - The IDE's checks and the index (the semantic pass) check every function as before.
     Not done (not needed by this plan): explicitly instantiating one member ("template void X<int>::f();", an
     error as before); a function template overloaded by another of the same name picks the first.
     Tests: TestCppCompilerLib's TestCPP65GeneratorExternTemplates (the externals a unit is left with),
     TestCPP65GeneratorExternTemplateProject and TestCPP816ExternTemplateProject (Input/CPP65/
     ExternTemplateProject: a size policy of this plan's shape, extern in Counter.h, instantiated in
     Instances.cpp, used by Main.cpp; run on both targets, and on the 816 with Instances.cpp a library unit).
  b. Without (a), are the duplicates folded, and what happens to the ROM's size?  Answered by reading: every
     template instance (and inline function) is written in a COMDAT section and the linker keeps one, so the
     ROM never held duplicates; the cost was only compile time.  With (a) the units don't compile them at all.
  c. Must the text compile under g++ and MSVC?  The user's ruling: Codaphela must compile under both g++ and MSVC.
     So the converted text follows the rules both take: "typename SIZE::Count" wherever a type depends on the
     policy, and "this->miUsedElements" (or "using CArrayBlockBase<SIZE>::miUsedElements;" in the class) for every
     member of a base that depends on a template parameter: MSVC finds them without, g++ doesn't.
     ExternTemplateProject is written that way and builds with g++ -std=c++14 -Wall -Wextra -pedantic with no
     warnings, and its Main.o leaves every non-inline instance function (and the vtables) undefined.  MSVC
     can't be built on Linux: each step is built with MSVC on Windows too (by the user or a Windows session)
     before it is called done.
  d. Is "static const size Max = MAX_SIZE;" in a struct a constant to the 816 compiler?  The user's ruling: it
     should be, and if it isn't that is a gap to fix.  It wasn't, on either target, and is fixed:
       - As a constant (an array size, a template argument, a case label), a static const member wasn't one,
         even SNarrow::Max; SIZE::Max wasn't found at all.  CCPPUnit::Constant now takes a static const member
         initialised in its class, by its class, by a template parameter bound to its class, or in its class,
         worked out with the bindings of the class that declares it.
       - As a value (if (SIZE::Check), switch (SIZE::Max), STwice<7>::Value) it was loaded from memory, from a
         label nothing defines when the member has no definition outside the class (and SIZE::Max didn't bind at
         all).  Its value is now the constant (CCPPUnit::IsConstantMember, in CCPP65TypeChecker::IdExpression and
         the IR front end), so it needs no definition, as in C++.  Its address or a reference to it still does.
       - A static member is now the variable of the class the name means (CCPPBinder::BindName): each instance
         of a class template has its own, under the template's one symbol, and the first instance's was taken.
     Tests: TestCPP65GeneratorStaticConstMembers and TestCPP816StaticConstMembers, and ExternTemplateProject.
  e. Who names ASIZE, ARRAY_BLOCK and the other macros outside BaseLib's array files?  The user's ruling: all the
     repositories are checked out under ~/Codaphela, so work it out, and make sure the full test sweep compiles
     (the matrix of the memory note "Run all tests scope").  Found 2026-11-15, searching every .h/.cpp/.inl/.c of
     all the repositories for ASIZE, ARRAY_BLOCK, ARRAY_CHAR, CHARS, ARRAY_TEMPLATE, ARRAY_TEMPLATE_PRIMITIVE,
     ARRAY_HEADER, CHARS_NATURAL, ARRAY_SIZE_MAX, ARRAY_NOT_FOUND, ARRAY_MEM*, ARRAY_CHECK_SIZE and the
     ArraySize*.inl names: only the 19 files of the five families (ArrayBlock, ArrayChar, Chars, ArrayTemplate,
     ArrayTemplatePrimitive, and ArraySizeNatural/Large/Undef.inl).  Outside them they are named only in comments
     (CppCompilerLib's CPPIndex.cpp and CPPIndex.h, HCP65-IDE's IDEConvertMacro.h) and in TestCppIndex.cpp's
     test of a class a macro names, which defines its own ARRAY_BLOCK and stays.  Users name the classes
     (CChars, CArrayTemplate<M>, ...), which the derived classes keep.  Search again before step 5 deletes the
     macros, and build the whole sweep after each step.
  f. CArrayBlock's shrink and free behaviour.  The user's ruling: it stays how it is, unless keeping it becomes a
     massive task to maintain; if it does, stop and ask.  The conversion changes what the classes are written as,
     not what they do, so it is expected to stay as it is for free.

What the session that does this needs to know
---------------------------------------------

  - Build Release x64.  Before a Release x64 build or suite run, see whether another session is running and tell
    it (the CppCompilerLib session builds the same outputs); Debug x64 never clashes.  On Linux, build in a
    private build directory and run suites from a private copy of the test folder (other sessions share the
    tree and the suites' Output folders).
  - The suites to run are the user's list, not every project found: ask, or see the memory note "Run all tests
    scope".  The *65 suites are run for this work, because it is about the 816; for ordinary feature work they
    aren't.  Every step builds the whole sweep (e), since every library uses these classes.
  - MSVC and g++ both have to take the text (c): typename and this-> everywhere a template needs them.
  - Sources have LF line endings and vcxproj files CRLF.  Don't write scripts that contain backslashes through a
    shell heredoc: write them to a file.
  - House style: Hungarian prefixes, the library's own primitive types (size, uint32), tabs, the banner comment
    over each function.  On the 816, hot arithmetic is in size or int, not int32 or int64.
  - Commit without a Co-Authored-By line, through a temporary index, leaving nothing staged; don't push.
  - The HCP65 IDE's refactorings exist now and could do some of this text's moving, but they refuse macro-made
    code, which is what this is: this conversion is by hand.
