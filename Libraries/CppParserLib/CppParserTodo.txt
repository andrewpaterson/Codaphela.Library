C++ Parser To Do
================

What is left after the preprocessor, tokeniser, parser and highlighter were written (2026-10-21).  In order of priority.  Goal: highlighting first, then refactoring, then compiling to a VM that is not written yet.

The first back end, a 65C64 code generator (CCPP65Generator), was started on 2026-10-23.  What it supports, its calling convention and what is left are in CPP65Generator.txt.  It works out the types it needs itself; item 2 below would let it share them with the highlighter.


2. Expression types and member resolution
-----------------------------------------

The first part of the semantic pass, and the next thing to do.

Today the highlighter cannot tell what p->x refers to.  It marks x as "member", which is hundreds of identifiers per file.  Knowing the type of each expression fixes that, and refactoring and compiling need it anyway.

Steps:
  - Build a table of types: built-ins, pointers, references, classes, typedefs, enums.
  - Give every expression a type.
  - Look up names after ".", "->" and "::" in that type, including base classes.
  - Add a sweep check that counts the "member" highlight spans that remain.

Overload resolution and template instantiation come after this.


3. Name-lookup gaps in the parser
---------------------------------

Small.  Some could be done along with item 2.
  - "using Base<M>::x;" declarations that name members of a template base class.
  - Field names inside offsetof(...).
  - goto labels.  The highlighter guesses them now instead of looking them up.
  - Qualified member calls inside templates, such as pvM->CBaseObject::CompleteClass(this) in StandardLib/Classes.h.


4. Show the highlighting somewhere
----------------------------------

Right now the highlighting is only spans checked by tests.
  - A small HTML export would be the quickest way to see it on real files.
  - Colouring code in the WindowLib text components is the real use, but needs coloured text spans first, which CTextArea does not support.

6. C++ compliance: preprocessor and tokeniser to C++17, code generators to C++14
-----------------------------------------------------------------------------------

Notes only (2026-11-07), not started.  Found by reading the code; nothing was built or run, so check each item against the code before relying on it.  The parser calls itself C++14 and the preprocessor defines __cplusplus as 201402L.  "C++14 compliance" for the generators includes the C++98/03 that is still missing, not only the C++11 and C++14 features.  Almost all of the generator work is in the shared front end (CPP65Generator*, CPP65TypeChecker, CPP65IRFrontEnd*); CIR65Backend and CIR816Backend only see IR, except for exceptions.  Sizes are relative: S, M, L, XL.

Already done in the preprocessor and tokeniser: __has_include and __has_include_next, _Pragma, __VA_ARGS__ (with the ", ##" comma rule), digit separators, binary literals, hex floats (0x1p-3 pp-numbers, read by strtold), u8 character literals, digraphs and alternative tokens, and no trigraphs (C++17 removed them).

A. Preprocessor and tokeniser to C++17
  - A1 (L, the only structural item) Raw string literals.  The preprocessor reads source a line at a time and splices backslash-newlines.  A raw string can span lines, must not be spliced, and can hold ", //, /* and #.  PreprocessorLineTokeniser and PreprocessorParser must see R"delim( and scan to )delim" across lines, undoing splices inside it.  Check that PPBlock and PPHeaderCache cope with a token that spans lines, then remove the error at CppTokeniser.cpp:706.  IsStringPrefix (Preprocessor.cpp:563) already knows the R prefixes.
  - A2 (S) User-defined literal suffixes (10_km, "x"_s): keep the suffix on number, character and string tokens instead of "Invalid integer literal suffix" (LiteralHelper.cpp, CppTokeniser.cpp).  operator "" itself is B17.
  - A3 (M) Extended identifiers.  PreprocessorParser.cpp:302 treats bytes of 128 and over as white space, and IsIdentifierStart (Preprocessor.cpp:2273) is ASCII only.  UTF-8 and \u / \U in identifiers, both spellings the same identifier, and through # and ##.
  - A4 (S) __has_cpp_attribute is always 0 (Preprocessor.cpp, "Attributes, builtins and features are not known").  C++17 wants fallthrough, nodiscard and maybe_unused 201603L, deprecated 201309L, noreturn and carries_dependency 200809L.
  - A5 (S) Define __STDCPP_DEFAULT_NEW_ALIGNMENT__.  __cplusplus: see the decisions below.
  - A6 (S-M) u, U and L literals: UTF-8 source to UTF-16 / UTF-32 code units.  u8'x' must be one code unit.
  - A7 (S) Test <:: : with <: a digraph, X<::Y> must still be < then :: (the C++11 rule).  Not seen in the code.

B. Code generators to C++14

B-1. C++98/03 still missing
  - B9a (S-M, do first: it is silently wrong) Bit-fields.  The parser keeps the width (CCPPSyntaxInitDeclarator::mpcBitField) but nothing in the generator reads it, so bit-fields are probably full fields with no truncation.
  - B2 (XL) Exceptions: throw, try / catch, function-try-blocks, unwinding through destructors and temporaries, noexcept calling std::terminate, new throwing bad_alloc, dynamic_cast<T&> throwing bad_cast.  try is parsed but not a case in CCPP65IRFrontEnd::StatementOf, and throw is not lowered.  Needs exceptional edges in the IR, the optimiser respecting them (SSA, inliner, dead stores), and unwinding in both back ends.  setjmp-style unwinding chained through V is probably cheaper to build on these processors than tables, at a cost for each try.
  - B3 (S-M) typeid and std::type_info.  dynamic_cast<T*> already finds an object's type info.
  - B4 (L) Virtual inheritance.
  - B5 (S-M) Static locals with initialisers that are not constant, and static local objects (a first time guard).
  - B6 (M-L) const (and volatile) in SCPP65Type.  const is on declarations now, not types ("as types do not" in CPP65Generator.txt).  Overloads, deducing const T and forwarding need it, so do it before B10.
  - B7 (L) Templates: SFINAE, template template parameters (also an error in the parser, CppParserClasses.cpp:722), dependent names looked up at the point of instantiation, partial ordering of function templates, constructor templates, member class templates, explicit specialisations of members.
  - B8 (M) Overload resolution to [over.match].  It is a simplified ranking now.  = delete is parsed (CPPFB_Delete) but does not make a call an error.
  - B9 (M, many small items) Class operator new and delete, placement new with more than an address, new[] with more than one dimension or an initialiser list, postfix ++ and -- on objects, operator-> that returns an object, conversion functions to classes and references, pointers to overloaded member functions, reference variables and fields bound to temporaries (and the temporary's lifetime; const reference parameters take them), wide strings.
  - Delegating constructors: CCPP65IRFrontEnd::ConstructorStart has no case for a member initialiser naming the constructor's own class.  It may be skipped silently rather than reported.  Test it.

B-2. C++11
  - B10 (L) Rvalue references as a type of their own: && is made a & now (GetDeclaratorType; rechecked 2026-11-08: item 103 of CppParserLibIssues.txt says what works), with T&& deduced so arguments can be passed through (ForwardedType).  Reference collapsing, deducing forwarding references as the standard does, & and && overloads, implicit move constructors and assignment (and when they are deleted), xvalues, ref-qualified members.
  - B11 (M) auto variables (an error at CPP65Generator.cpp:2636) and decltype (its specifier is never made a type).
  - B12 (L) Lambdas: the parser (CppParserExpressions.cpp:665), closure classes, captures by value and by reference and this, and the conversion to a function pointer when nothing is captured.  A closure is a class, which the back ends already do well.
  - B13 (L) constexpr functions and literal classes.  constexpr is only inline now, and Constant (CPP65GeneratorExpressions.cpp:781) does integers without calls.  C++14's relaxed constexpr allows loops and assignment, so running the IR at compile time (an IR interpreter) may be better than growing the tree folder.
  - B14 (M) Packs everywhere: base lists, initialisers, template arguments and member initialisers, sizeof..., nested packs.  Only args... in a call's arguments works now.
  - B15 (M) std::initializer_list and list initialisation: a constructor taking one is preferred, narrowing is an error.
  - B16 (S) Range-for lowering.  It is parsed but not a case in StatementOf.  Free begin and end need B1.
  - B17 (M, many small items) Alias templates (CPP65Generator's TemplateDeclaration handles classes and functions only), delegating constructors, nullptr_t, unions with members that have constructors, the noexcept operator and specifications, operator "" functions, raw and Unicode strings in generated code, thread_local (static storage on a single threaded target), extern locals.
  - B18 (S) Check enum class: scoped lookup and no implicit conversion to int.

B-3. C++14 (small once B-2 is done)
  - Generic lambdas (operator() a member template: B12 and B7), init-captures, auto f() and decltype(auto) (B11), relaxed constexpr (B13), variable templates, [[deprecated]] warnings, sized deallocation.

B-4. Language support headers
  - Even without the rest of the library: <initializer_list>, <typeinfo>, <exception>, <cstddef> (nullptr_t), <type_traits> (over the __is_ intrinsics that exist), and move and forward from <utility>.  Libc65 has only <new>.

Decisions for the user
  - __cplusplus: it says what the whole compiler implements, so 201703L would tell headers C++17 is there when the generators are C++14.  Suggested: 201402L by default, a CConfig setting for 201703L.
  - Exceptions: strict compliance needs them.  A documented mode without them (as many embedded compilers have) would remove the largest item.
  - The library: only the B-4 headers, or the whole C++14 library, which is a separate project of about the same size again.

Compliance can only be measured by tests: add a test file for each item as it is done, in TestCppParserLib.
