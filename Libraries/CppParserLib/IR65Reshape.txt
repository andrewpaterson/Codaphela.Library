Reshaping the 65C64 back end toward the W65C816's
==================================================

The 65C64 back end (CIR65Backend) and the W65C816 back end (CIR816Backend) share almost no
code line for line, but they do the same jobs: the duplication is in behaviour.  The 65C64
one grew as one 5,346 line file whose stages talk through member state; the W65C816 one is
split by concern (IR816Places, Instructions, Flow, Frames, Runtime, Lines, Peephole,
DeadStores).  The user's ruling (2026-11-05): the 65C64 back end is to be shaped toward the
W65C816's.  Written 2026-11-05.

The text passes are the one place the W65C816's shape isn't clearly the better one: the
65C64's decoded CIR65Code with its label table is arguably tidier than static functions over
the raw text.  Both follow what A, X and Y hold (CIR65Peephole's values, SIR816Held) and both
thread jumps.


What belongs in shared code
---------------------------

- Block order and loop tests.  OrderBlocks and the back end's RotateLoops (block layout: a
  loop's test moved after its body) don't depend on the target, and the W65C816 has nothing
  like them.  (Not CIROptimiser::RotateLoops: that copies a loop's head, up to 8
  instructions; the back end's moves blocks, and catches the loops the optimiser leaves.)
- Loop steps.  CIR65Backend::SinkToEnd and CIR816Backend::SinkSteps both moved a loop's step
  (p + 1 a phi takes) down past the instructions reading p so the two can share a place,
  with different rules.  Done 2026-11-05: one CIRBackendPasses::SinkSteps (below).
- Use counts.  CIR816Backend::FoldPointers counted uses by hand.  Done 2026-11-05: it takes them
  from CIRFunction::CountUses, keeping its address and shift count tallies.
- Liveness.  CIR816Backend::PackTemporaries ran its own liveness dataflow.  Done 2026-11-05: the
  dataflow is CIRLiveSets (IRLiveSets.h/.cpp), which CIRLiveness and PackTemporaries both fill and
  solve.  The live ranges stay each back end's: the 65C64 defines a result one position after its
  operands (an operand dying there can always share with it: add Y, 1), the W65C816 at the same
  position, sharing only explicit pairs, as it writes multi-word results a word at a time.
- Loop weights.  "8 times more per loop" was CIRLiveness::LoopWeight (depth capped at 5), and
  again inline in CIR816Backend::AllocateX (capped at 4) and the W65C816's align estimate
  (IR816_ALIGN_LOOP_WEIGHT, capped at 3).  Done 2026-11-05: CIRLoops::Weight(depth, cap), each
  caller keeping its cap (AllocateX's 4 keeps a use under IR816_X_BAD's veto).


Steps
-----

1. Split IR65Backend.cpp into files as the W65C816's is split, with an IR65BackendInternal.h
   for what the files share.  Mechanical: the code written is the same.
2. The frame's members into one SIR65Frame, as SIR816Frame.  The code written is the same.
3. The instructions not written in their turn written by their consumer, as the W65C816's
   fused ones are (the user chose the full W65C816 shape over a same-output tidy up,
   2026-11-05).  Reading both back ends showed the W65C816 also decides in the writing loop
   (CanFuse with mapsFused), and that msInA/msAvailable is mostly a record of what A holds
   (a value just stored from A is still there), which stays.
4. OrderBlocks and the IR rewrites that don't depend on the target into IR passes any back
   end can run.  The code written should be the same.  (Was "drop RotateLoops for
   CIROptimiser's": wrong, see above.)
5. Call split into pushing the arguments, loading registers, the call and the clean up.
6. The shared code above (use counts, liveness hooks, loop weights) for the W65C816.

Loop steps: done 2026-11-05.  CIRBackendPasses::SinkSteps replaces CIR65Backend::SinkToEnd and
CIR816Backend::SinkSteps.  A step p2 = p + q (add, sub, ptradd; p the phi taking p2, either operand
of an add) moves past the readers of p after it: not past a use of p2, not among a call's args (a
read of p there is at the call, so after the call), past the brif's comparison of p.  First tried:
any operand's readers (an 816 test showed it: moving s2 = s + i past i2 = i + 1 keeps i alive, so i
and i2 can't share X), and stopping before the comparison (cost the 816 0.07%: sharing beats fusing).

the same path length (the paths are compiled in, and their length moves the 816's data and so its
page crossings):

Block order on the W65C816: done 2026-11-05.  It runs OrderBlocks with bLoopsTogether (a block's ways out
of its loops searched first, so a loop's blocks stay together; the 65C64 passes false and its code is the
same); MoveLoopTests changes nothing measurable there, so it doesn't run it.  Plain reverse post order cost
it +0.1% on TestBaseLib65 (TimSort's merge +33%): a latch at the end of the function broke PackTemporaries'
phi pairs.  With the pairs weighed by the loop both ends of an edge are in, ties placed heaviest first and
a brif's condition read before the copies: TestBaseLib65 -0.75%, TestStandardLib65 -0.96%.  PackTemporaries
places greedily (in start order, pairs only to partners already placed); coalescing pairs heaviest first
before placing is the fix for the copies left (TestArrayTemplate +0.7%, TestCPP816 MergeLoop 1,198,120 of
its 1,200,000).
