C++ Parser To Do
================

What is left after the preprocessor, tokeniser, parser and highlighter were written (2026-10-21).  In order of priority.  Goal: highlighting first, then refactoring, then compiling to a VM that is not written yet.

The first back end, a 65C64 code generator (CCPPUnit), was started on 2026-10-23.  What it supports, its calling convention and what is left are in CPP65Generator.txt.  It works out the types it needs itself; item 2 below would let it share them with the highlighter.


2. Expression types and member resolution
-----------------------------------------

The first part of the semantic pass, and the next thing to do.

Today the highlighter cannot tell what p->x refers to.  It marks x as "member", which is hundreds of identifiers per file.  Knowing the type of each expression fixes that, and refactoring and compiling need it anyway.

Steps:
  - Build a table of types: built-ins, pointers, references, classes, typedefs, enums.
  - Give every expression a type.
  - Look up names after ".", "->" and "::" in that type, including base classes.
  - Add a sweep check that counts the "member" highlight spans that remain.

Overload resolution and template instantiation come after this.


3. Name-lookup gaps in the parser
---------------------------------

Small.  Some could be done along with item 2.
  - "using Base<M>::x;" declarations that name members of a template base class.
  - Field names inside offsetof(...).
  - goto labels.  The highlighter guesses them now instead of looking them up.
  - Qualified member calls inside templates, such as pvM->CBaseObject::CompleteClass(this) in StandardLib/Classes.h.


4. Show the highlighting somewhere
----------------------------------

Right now the highlighting is only spans checked by tests.
  - A small HTML export would be the quickest way to see it on real files.
  - Colouring code in the WindowLib text components is the real use, but needs coloured text spans first, which CTextArea does not support.

  - Instantiate every BaseLib template class in a test, to catch bugs the parser cannot see yet.  That is how the CArrayTemplateEmbeddedPrimitive bugs were found.

       Virtual inheritance, as the user chose (question 9), Itanium style:
       - Layout: a class's own part is its non-virtual bases (each only its own part), its vtable pointer (a class with a
         virtual base always has one) and its fields.  The virtual bases follow, each once, in the order of a depth-first
         left-to-right walk with a virtual base after its own (CCPPClass::macVirtualBases, also the order they are made).
         A class as a non-virtual base takes its own part's bytes (miOwnBytes); a complete object all of them.
       - Vtables: before each part's header (offset to top, type info) the offsets from the part's subobject to each of
         its class's virtual bases, the first nearest.  A class with a first non-virtual base at 0 shares its vtable
         pointer, and its virtual bases start with that base's, so the base finds its offsets in the class's part.  A
         virtual base's part has the final overriders from every class on the paths to it, each called through a thunk
         that moves this to its class.  A class's vtable (all its parts) is written for the class as a complete object.
       - Reaching a virtual base from a pointer: the vtable pointer, then the offset in its part's header; a path
         through a virtual base is that and then the non-virtual part below it (CCPP65IRFrontEnd::BaseAddress).
       - Constructors and destructors of a class with virtual bases are written twice: the complete one (its label as
         now, so vtables and calls that make whole objects are as they were) makes the virtual bases first and destroys
         them last; the base one (label and __B) takes a hidden pointer after this to its VTT entries (Itanium's VTT, cut
         down): its construction vtable (the class's parts as the class has them, but its virtual bases where the
         complete object puts them, and its own overriders), then the entries of its direct non-virtual bases that have
         virtual bases (CCPPUnit::VTTEntries).  A complete class's VTT (_C__4) is its vtable, then the entries of each
         base its constructors and destructor make with a base version, non-virtual then virtual (CCPPUnit::VTTIndex);
         the construction vtables are _C__5_<offset>_<Base>.  So while a base is made or destroyed its virtual calls,
         typeid and dynamic_cast are its own and its virtual bases are where they are.
       - Classes without virtual bases are as they were, so nothing that compiles now changes.

    14. sizeof's type is std::size_t ([expr.sizeof] 6): on the W65C816 Libc65's size_t is unsigned long (4 bytes, as
        an object can be more than 64KB), but the compiler's sizeof is an unsigned int, 2 bytes.  They are different
        types now, so a template or overload sees sizeof(x) as an unsigned int and a size_t as an unsigned long, and an
        object over 64KB has its size cut.  Make sizeof an unsigned long there, as the standard says (every
        sizeof(a) / sizeof(a[0]) loop bound and BaseLib's size arithmetic is then 32 bit unless the constant is folded
        narrow, which costs code and cycles), or keep it 16 bits and make Libc65's size_t unsigned int on the W65C816
        (objects over 64KB can't be sized, as now)?
        The user, 2026-11-18: "make Libc65's size_t 16-bit", though it limits what malloc can be asked for, and asked
        whether the 32 bit allocation should then be the special case, as CTrueMallocator::MallocWithin (memory that
        doesn't cross a bank) is the special case now.  Proposed (waiting for the user's word on the open points):
        - size_t is unsigned int and ptrdiff_t int on the W65C816, as sizeof already is; malloc, calloc, realloc and
          the string functions take and give 16 bit counts.  memcpy16 and the other 16 bit ones (stringW65C816_16.asm)
          become memcpy and the others, and today's 32 bit bodies (stringW65C816.asm) get a suffix: malloc32, calloc32,
          realloc32, memcpy32, memmove32, memset32, memcmp32, memchr32, strlen32 (the suffix as memcpy16's is now).
          BaseLib's lsize paths call them: CSystemAllocator::Malloc and Realloc (lsize) on Libc65, and the copies of
          lsize bytes.  Where an lsize reaches a size_t is found with the narrowing warning on in the *65 compiles.
        - malloc's blocks never cross a bank: the heap is a CTrueMallocator region per 64KB bank, so no block can, and
          Malloc stays constant time (MallocWithin walks every block when the first found doesn't fit, so making it the
          ordinary path would lose that).  The kernal's bOneBank allocation is then plain Malloc.
        - malloc32 of more than a bank takes whole adjacent banks, as the kernal's KernalTakeHeapBanks does for its main
          heap; a bank goes back when its blocks are all free (IsRegionFree, RemoveRegion, as the kernal does).  The cost
          is up to 64KB less one rounding a large allocation up, and banks the small heap holds can't be taken whole.
        - Open for the user: the suffix (malloc32 and memcpy32, or an l prefix as BaseLib's lsize); whole banks for large
          allocations, or one TLSF region that crosses banks for them (less rounding, more fragmentation); whether the
          16 suffixed names stay as aliases.  The labels with a size_t parameter change again on the W65C816 (m to j).
