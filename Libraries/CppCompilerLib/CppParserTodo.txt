C++ Parser To Do
================

What is left after the preprocessor, tokeniser, parser and highlighter were written (2026-10-21).  In order of priority.  Goal: highlighting first, then refactoring, then compiling to a VM that is not written yet.

The first back end, a 65C64 code generator (CCPPUnit), was started on 2026-10-23.  What it supports, its calling convention and what is left are in CPP65Generator.txt.  It works out the types it needs itself; item 2 below would let it share them with the highlighter.


2. Expression types and member resolution
-----------------------------------------

The first part of the semantic pass, and the next thing to do.

Today the highlighter cannot tell what p->x refers to.  It marks x as "member", which is hundreds of identifiers per file.  Knowing the type of each expression fixes that, and refactoring and compiling need it anyway.

Steps:
  - Build a table of types: built-ins, pointers, references, classes, typedefs, enums.
  - Give every expression a type.
  - Look up names after ".", "->" and "::" in that type, including base classes.
  - Add a sweep check that counts the "member" highlight spans that remain.

Overload resolution and template instantiation come after this.


3. Name-lookup gaps in the parser
---------------------------------

Small.  Some could be done along with item 2.
  - "using Base<M>::x;" declarations that name members of a template base class.
  - Field names inside offsetof(...).
  - goto labels.  The highlighter guesses them now instead of looking them up.
  - Qualified member calls inside templates, such as pvM->CBaseObject::CompleteClass(this) in StandardLib/Classes.h.


4. Show the highlighting somewhere
----------------------------------

Right now the highlighting is only spans checked by tests.
  - A small HTML export would be the quickest way to see it on real files.
  - Colouring code in the WindowLib text components is the real use, but needs coloured text spans first, which CTextArea does not support.


5. Smaller items
----------------

  - Add a Linux CMake build for TestJavaParserLib, so its tests run after the float128 fix.
  - Instantiate every BaseLib template class in a test, to catch bugs the parser cannot see yet.  That is how the CArrayTemplateEmbeddedPrimitive bugs were found.


6. C++ compliance: preprocessor and tokeniser to C++17, code generators to C++14
-----------------------------------------------------------------------------------

Part A is done (2026-11-15: the "Part A plan" below says how, step by step).  Part B is not started: it has a plan ("Part B plan" below, 2026-11-15, checked by compiling) and its notes (2026-11-07) were found by reading the code; nothing was built or run, so check each item against the code before relying on it.  The parser calls itself C++14 and the preprocessor defines __cplusplus as 201402L.  "C++14 compliance" for the generators includes the C++98/03 that is still missing, not only the C++11 and C++14 features.  Almost all of the generator work is in the shared front end (CPP65Generator*, CPP65TypeChecker, CPP65IRFrontEnd*); CIR65Backend and CIRW65C816Backend only see IR, except for exceptions.  Sizes are relative: S, M, L, XL.

Already done in the preprocessor and tokeniser: __has_include and __has_include_next, _Pragma, __VA_ARGS__ (with the ", ##" comma rule), digit separators, binary literals, hex floats (0x1p-3 pp-numbers, read by strtold), u8 character literals, digraphs and alternative tokens, and no trigraphs (C++17 removed them).

A. Preprocessor and tokeniser to C++17
  All done 2026-11-15: see "Part A plan" below, which replaces the notes on A1 to A7 here where they differ.
  - A1 (L, the only structural item) Raw string literals.  The preprocessor reads source a line at a time and splices backslash-newlines.  A raw string can span lines, must not be spliced, and can hold ", //, /* and #.  PreprocessorLineTokeniser and PreprocessorParser must see R"delim( and scan to )delim" across lines, undoing splices inside it.  Check that PPBlock and PPHeaderCache cope with a token that spans lines, then remove the error at CppTokeniser.cpp:706.  IsStringPrefix (Preprocessor.cpp:563) already knows the R prefixes.
  - A2 (S) User-defined literal suffixes (10_km, "x"_s): keep the suffix on number, character and string tokens instead of "Invalid integer literal suffix" (LiteralHelper.cpp, CppTokeniser.cpp).  operator "" itself is B17.
  - A3 (M) Extended identifiers.  PreprocessorParser.cpp:302 treats bytes of 128 and over as white space, and IsIdentifierStart (Preprocessor.cpp:2273) is ASCII only.  UTF-8 and \u / \U in identifiers, both spellings the same identifier, and through # and ##.
  - A4 (S) __has_cpp_attribute is always 0 (Preprocessor.cpp, "Attributes, builtins and features are not known").  C++17 wants fallthrough, nodiscard and maybe_unused 201603L, deprecated 201309L, noreturn and carries_dependency 200809L.
  - A5 (S) Define __STDCPP_DEFAULT_NEW_ALIGNMENT__.  __cplusplus: see the decisions below.
  - A6 (S-M) u, U and L literals: UTF-8 source to UTF-16 / UTF-32 code units.  u8'x' must be one code unit.
  - A7 (S) Test <:: : with <: a digraph, X<::Y> must still be < then :: (the C++11 rule).  Not seen in the code.

B. Code generators to C++14

B-1. C++98/03 still missing
  - B9a Done 2026-11-13.  Bit-fields: laid out as MSVC does (CCPPUnit::LayoutBitField: a unit of the type's size, a new one for another size, when the bits run out or after a zero width one), read and written through their place (SCPP65IRPlace::psBitField: CCPP65IRFrontEnd::Load and Store), unnamed ones left out of aggregate initialisers, a const reference bound to a copy, no address.   - B2 (XL) Exceptions: throw, try / catch, function-try-blocks, unwinding through destructors and temporaries, noexcept calling std::terminate, new throwing bad_alloc, dynamic_cast<T&> throwing bad_cast.  try is parsed but not a case in CCPP65IRFrontEnd::StatementOf, and throw is not lowered.  Needs exceptional edges in the IR, the optimiser respecting them (SSA, inliner, dead stores), and unwinding in both back ends.  setjmp-style unwinding chained through V is probably cheaper to build on these processors than tables, at a cost for each try.
  - B3 (S-M) typeid and std::type_info.  dynamic_cast<T*> already finds an object's type info.
  - B4 (L) Virtual inheritance.
  - B5 (S-M) Static locals with initialisers that are not constant, and static local objects (a first time guard).
  - B6 (M-L) const (and volatile) in SCPP65Type.  const is on declarations now, not types ("as types do not" in CPP65Generator.txt).  Overloads, deducing const T and forwarding need it, so do it before B10.
  - B7 (L) Templates: SFINAE, template template parameters (also an error in the parser, CppParserClasses.cpp:722), dependent names looked up at the point of instantiation, partial ordering of function templates, constructor templates, member class templates, explicit specialisations of members.
  - B8 (M) Overload resolution to [over.match].  It is a simplified ranking now.  = delete is parsed (CPPFB_Delete) but does not make a call an error.
  - B9 (M, many small items) Class operator new and delete, placement new with more than an address, new[] with more than one dimension or an initialiser list, postfix ++ and -- on objects, operator-> that returns an object, conversion functions to classes and references, pointers to overloaded member functions, reference variables and fields bound to temporaries (and the temporary's lifetime; const reference parameters take them), wide strings.
  - Done 2026-11-13.  Delegating constructors (CCPP65IRFrontEnd::DelegatedConstructor): they were skipped silently.  TestCPP816DelegatingConstructors.

B-2. C++11
  - B10 (L) Rvalue references as a type of their own: && is made a & now (GetDeclaratorType; rechecked 2026-11-08: item 103 of CppCompilerLibIssues.txt says what works), with T&& deduced so arguments can be passed through (ForwardedType).  Reference collapsing, deducing forwarding references as the standard does, & and && overloads, implicit move constructors and assignment (and when they are deleted), xvalues, ref-qualified members.
  - B11 (M) auto variables (an error at CPPUnit.cpp:2636) and decltype (its specifier is never made a type).
  - B12 (L) Lambdas: the parser (CppParserExpressions.cpp:665), closure classes, captures by value and by reference and this, and the conversion to a function pointer when nothing is captured.  A closure is a class, which the back ends already do well.
  - B13 (L) constexpr functions and literal classes.  constexpr is only inline now, and Constant (CPPUnitExpressions.cpp:781) does integers without calls.  C++14's relaxed constexpr allows loops and assignment, so running the IR at compile time (an IR interpreter) may be better than growing the tree folder.
  - B14 (M) Packs everywhere: base lists, initialisers, template arguments and member initialisers, sizeof..., nested packs.  Only args... in a call's arguments works now.
  - B15 (M) std::initializer_list and list initialisation: a constructor taking one is preferred, narrowing is an error.
  - B16 (S) Range-for lowering.  It is parsed but not a case in StatementOf.  Free begin and end need B1.
  - B17 (M, many small items) Alias templates (CPP65Generator's TemplateDeclaration handles classes and functions only), nullptr_t, unions with members that have constructors, the noexcept operator and specifications, operator "" functions, raw and Unicode strings in generated code, thread_local (static storage on a single threaded target), extern locals.
  - B18 (S) Check enum class: scoped lookup and no implicit conversion to int.

B-3. C++14 (small once B-2 is done)

Part A plan (2026-11-15)

    - A7 is already in the code (PunctuatorLength, Punctuators.cpp): only tests are missing.  X<::Y>, a<:::b, <::> and <:: at the end of input, in TestCppTokeniser and through ##.
    - A4: a table for PPSO_HasCppAttribute only, in place of the "not known" branch of CPPPreprocessor.cpp.  fallthrough, nodiscard and maybe_unused 201603, deprecated 201309, noreturn and carries_dependency 200809; the __name__ spellings too; scoped names (gnu::x) stay 0.  The parser keeps them as tokens and ignores them, which conforms.
    - A5: __STDCPP_DEFAULT_NEW_ALIGNMENT__ from the target (a CCPPTarget virtual beside the targets' other defines).  The host's is MSVC's; the 65C64's and W65C816's are what Libc65's operator new guarantees (not read yet).
  Step 2, A6.  Done 2026-11-15 (TestCppTokeniserCharacterLiterals): as below, and a narrow literal's character past 0x7F is its UTF-8 bytes, each a character of the literal, however it is spelled; a numeric escape must fit the literal's type.  Strings were done (CCPPUnit::DecodeStringToken, TestCPP65IR).  Character literals are left: ParseCharacterLiteral (LiteralHelper.cpp) reads a byte at a time, so u'é' in UTF-8 source is two characters.  Decode one UTF-8 sequence for each character of L, u, U and u8 literals (move DecodeUTF8 from CCPPUnit to LiteralHelper so strings, characters and #if share it).  Errors: u8'é' (not one code unit), a u literal that needs a surrogate pair, u8 / u / U literals of several characters.
  Step 3, A2.  Done 2026-11-15 (TestCppTokeniserUserLiterals, TestCPP65IRUserLiterals), not quite as written below:
    - Any identifier after a number that isn't one of the language's suffixes is a user-defined suffix (12q, 1uu), so those are no longer the tokeniser's errors: the generators say user-defined literals are not supported, and B17 will say there is no such operator.  ParseNumberLiteral (LiteralHelper) reads integers and floating literals for the code and #if, with the new errors (an exponent with no digits, a hexadecimal floating literal with no exponent, a digit separator not between digits).
    - The line tokeniser (CPreprocessorLineTokeniser::Quote) makes a string or character one token from its prefix to its suffix; ConvertTokens no longer joins prefixes, and parts a macro from the end of a literal (LiteralBeforeMacro).
    - CCTUserLiteral holds the literal's own token (mpcLiteral) and the suffix.
  As it was planned:
    - Numbers: the pp-number already holds 10_km.  ParseIntegerLiteral says where the suffix starts instead of ILR_InvalidSuffix, and CCPPTokeniser::Floating the same.
    - Strings and characters: "x"_s is a string token then an identifier now.  Join them in ConvertTokens (where prefixes are joined) when the identifier touches the closing quote, and in LexSingleToken for ##.  As g++ does, an identifier that is a macro and does not start with _ is left a token of its own, so "%"PRId64 still compiles.
    - A new token, CCTUserLiteral: the kind, the literal's spelling without the suffix (raw literal operators need it), its value and the suffix's identifier.  The parser takes it as a literal; the generators say it is not supported until B17.  It stays an error in #if.
    - In the same code: bad digit separators (1''0, 1') and joined literals with different suffixes are errors.
  Step 4, A3.  Done 2026-11-15 (TestCppTokeniserExtendedIdentifiers, TestCPP65IRExtendedIdentifiers, TestCPP816ExtendedIdentifiers), with these differences from what is below:
    - A byte of 0x80 or more is a letter to IsCPPNameStart, in the source and in the assembly.  Which characters the language allows is checked once, when the C++ tokeniser makes an identifier (InvalidCPPNameCharacter, CPPNameCharacters.cpp): not allowed, a combining character first, or bytes that aren't UTF-8.  So a stray byte past ASCII in code is that error, not a stray character.
    - Names are not encoded when they are mangled: they reach labels from too many places.  The assembler takes UTF-8 bytes in a label instead (IsIdentifierStart, Asm65Tokeniser.cpp in Assembler65Lib), and the back ends' readers of their own assembly use IsCPPNameCharacter already.
    - The line tokeniser's Respell (was ReplaceLineContinuers) makes a universal character name in an identifier or number its UTF-8.  One that names an ASCII character is not refused.
  As it was planned:
    - Identifiers are UTF-8 inside the compiler.  \uXXXX and \UXXXXXXXX in an identifier are made UTF-8 when the line tokeniser makes the token, so both spellings are one identifier from there on, through # and ## too.
    - IsCPPNameStart and IsCPPNameCharacter (CPPNameCharacters.h) take the ranges of [lex.name] and Annex E, with those not allowed first.  PPNumberLength, IsDigitSeparator, LexSingleToken, EmitPragmaPack and GetDirective use them.
    - Bytes of 128 and over stop being white space (CPreprocessorParser::IsWhitespace).  A UTF-8 byte order mark at the start of a file is skipped (nothing does now).  Any other one outside an identifier, literal or comment is a stray character, which the tokeniser reports (and drops in system headers).  A source with a stray Latin-1 byte in its code compiles now and will not.
    - Forced by this, though it is the generators': a name with bytes of 128 and over is encoded when it is mangled (_uXXXX), so Assembler65Lib sees ASCII labels.

  As it was planned.  It is smaller than the note above says: splices are only removed from a token that has one (ReplaceLineContinuers) and a token's text points into the source, so a raw string needs nothing undone.

Part B plan (2026-11-15, not started)
  The notes on B1 to B18 above were checked by compiling about 190 small programs for the W65C816 with hcp65build, one a feature (Tests/TestCppCompilerLib/ConformanceProbes: probe.py and probe2.py, with what each gave in results.txt and results2.txt).  "Compiles" is all that most of them show: only where a negative array size could prove it was what the code means checked.  This plan replaces the Order above for Part B.

  What the notes had wrong:
    - Namespaces (B1) are done: nested ones, aliases, anonymous and inline ones, using, and argument dependent lookup compile.
    - const is in types (B6) where it could be proved: const overloads of members and of pointer parameters, a specialisation for const T, and the errors for writing through const.
    - These compile already: defaulted functions of simple classes, a variadic function calling itself, variadic class templates, brace initialisation, default member initialisers, inherited and delegating constructors, alignas, explicit conversion operators, member function templates, constructor templates, partial ordering, explicit specialisation of a member.

  What the notes didn't have.  Accepted and wrong, with no error:
    - static_assert at namespace scope is never worked out (a false one compiles); a false one in a function is an unrelated error.
    - A call of an = delete function; an object of an abstract class; a private member used from outside its class.
    - enum class converts to int and compares with it; narrowing in { } is not an error.
  Refused, and should not be:
    - f(nullptr) where f takes a pointer ("No function matches the arguments (void*)").
    - [[maybe_unused]] on a parameter (read as a lambda); sizeof(S::member); f(S{1, 2}); c(1, 2) for an object with operator() in one case.
    - A template's array bound deduced (T (&)[N]), a partial specialisation for T[N], a pointer as a template argument.
    - __is_base_of, __is_convertible_to, __underlying_type and some other type traits.

  Stages:
    0. (S) The probes become a test: each feature a small program run on both targets with the value it must return, and those that must be refused with their error.  What fails today is listed as failing, and every later stage moves entries across.  Compliance is then a number.
    1. (M, many small) The silent wrong accepts and the small refusals just listed.  Access control (private and protected) is enforced (the user).  What it and the enum class rules find wrong in BaseLib, Libc65 and the HCP65 sources is fixed as part of this stage (the user), which is checked by building them and running the Lib65 suites.
    2. (L) B10.  Rvalue references as a type of their own: collapsing, & and && overloads, move constructors and assignment (and the implicit ones, and when they are deleted), xvalues, ref-qualified members.
    3. (M) B11, B16 and parts of B17: auto, decltype, trailing return types, range-for, alias templates, nullptr_t.
    4. (L) B13.  constexpr, by running the IR at compile time (the user): ConstexprPlan.txt, planned on its own.
    5. (L) B12.  Lambdas: the parser, closure classes, captures, the conversion to a function pointer; then generic lambdas and init-captures (B-3).
    6. (L) B7 and B14.  Templates: SFINAE, template template parameters, member class templates, array deduction, packs everywhere and sizeof..., variable templates, the missing type traits.
    7. (M, many small) B5 and B9.  Objects: static locals that need a guard, postfix ++ and -- on objects, operator-> returning an object, conversion functions to classes and references, pointers to overloaded members, temporaries bound to references, new[] with initialisers and two dimensions, placement new with more arguments, ?: on different class types, extern locals, thread_local.  Each is on its own and can go between other stages.
    8. (M) B15 and the rest of B17: std::initializer_list, operator "" functions (which finish Part A's user-defined literals), the noexcept operator.
    9. (L) B3 and B4: typeid, dynamic_cast<T&>, virtual inheritance.  A dynamic_cast<T&> that fails traps (the user), there being nothing to throw until exceptions are decided.  Virtual inheritance stays in the plan and is to be tested thoroughly (the user): diamonds, constructors' order and which constructor makes the virtual base, virtual functions through it, casts each way, pointers to members, and layouts against MSVC's.
    Then, when all of the above is done, come back to the user for: exceptions (B2), and the language support headers (B-4) and how much of the library.

  Why this order: wrong code with no error first; rvalue references before what is built on them (moves, forwarding, the library's move and forward); auto before lambdas; constexpr before the templates that lean on it.  Stages 6, 7 and 9 depend on little and can move.
