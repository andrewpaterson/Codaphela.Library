# 65C64 Back End Design

The 65C64 back end, [`CIR65Backend`], turns a function's [IR](ir.md) into 65C64 assembly.  What it writes, the
registers, the pseudo registers and the calling convention are described for users in
[The 65C64 Back End](../65c64.md) and [Calling Convention](../../65c64/calling-convention.md); this page is for a
programmer who will change it: how it is built, why, and what was measured and thrown away.

Three files beside the code hold more:

- [`CppCompilerLib/CPP65Generator.txt`]: the 65C64 target as a whole, the user's rulings of 2026-10-23 on the memory
  map, register widths, argument sizes, V, W and `this`, the calling convention with register arguments, and the C++
  the compiler supports.  Code comments point at it.
- [`CppCompilerLib/IR.txt`], section "65C64 back end": each part's rules in detail, with the measurements of the day
  each was built.
- [`CppCompilerLib/CodeGenerationHandoff.txt`]: the code generation work of 2026-11-13 and 14 on both processors,
  step by step: commits, cycle counts, the cost table, the experiments rejected, and the user's rulings, which the
  CLAUDE.md files and `ConsolidationPlan.txt` point at.

## Why IR only

The 65C64 had a back end before the IR.  On 2026-10-23 the user asked for the C++ compiler to "emit assembly for
the 65C64", and the generator ([`CCPPUnit`], then called CCPP65Generator) wrote assembly as it walked the syntax
tree: every expression's value ended in A, the right operand of a binary operator in B or a pseudo register, locals
in the frame.  The IR was built beside it by another session from 2026-10-24 (see the [IR design](ir.md)), the
65C64 its first back end behind a switch from 2026-10-25, and the W65C816's back end was IR from its start.

On 2026-10-30 the user asked to "quickly move the 65C64 to use an IR like the 816", and chose IR only, the direct
generator retired, over keeping both (commit be5c48bf0).  The IR's optimiser and a real register allocator halved the
cycles: TestBaseLib65 on the 65C64 went from 26.17G to 13.43G cycles and TestStandardLib65 from 25.94G to 14.61G,
every suite passing.  What the direct generator decided outside function bodies stayed: the calling convention, the
places from V, the labels and their mangling, and the front end's classes, vtables and thunks.  The sections
"Registers" and "Instructions used for operators" of [`CppCompilerLib/CPP65Generator.txt`] still describe the code
the direct generator wrote; read them for the instructions' rules, not for what is written today.

## The parts

The back end was one file of 5,346 lines whose stages talked through member state.  On 2026-11-05 the user ruled that
it be shaped toward the W65C816 back end ([`CIRW65C816Backend`], see [W65C816 design](w65c816.md)): "The 65C64
generator is a tangle mess that needs to be shaped towards the 816 generator."  The two shared almost no code line
for line; the duplication was the same jobs done in two shapes.  The reshape went in three rounds, each changing only
how the code is held, proved by the listings of every suite unit staying the same:

1. 2026-11-05 to 08, `CppCompilerLib/IR65Reshape.txt`: the file split by concern; the frame as one [`SIR65Frame`];
   instructions not written in their turn written by their consumer, as the W65C816's fused ones are; the block
   order and IR rewrites any back end can use moved into [`CIRBackendPasses`]; a call split into pushing, loading
   registers, the call and the clean up; and the shared code below.
2. 2026-11-14 and 24, `ConsolidationPlan.txt` stage 7: each temporary one record, [`SIR65Temporary`], in place of six
   parallel arrays; the jobs as classes of their own, named as the W65C816's are.
3. 2026-11-25, `ConsolidationPlan.txt` stage 8b: the selector writes instructions ([`EIR65Mnemonic`] and operands),
   not text; one [`CIR65Code`] for every pass, run from a list; nothing decoded from text in a compile; source
   markers kept per line ([`CIRLineMarkers`]).

The plan of the first round, `CppCompilerLib/IR65Reshape.txt`, is in the history up to CommonLibraries f98a108e0.

| Class | Does |
|---|---|
| [`CIR65Backend`] | The function as a whole: the passes before code, the order of the rest, the prologue and epilogue, blocks, jumps and their phi copies, the pass list. |
| [`CIR65Places`] | Frame layout ([`CIR65Places::Layout`]) and register allocation ([`CIR65Places::Allocate`]): where each temporary lives. |
| [`CIR65Folds`] | A pointer plus a constant only loaded and stored through, folded into those instructions' addresses (`[8 + X]`). |
| [`CIR65Fusion`] | Which instructions are left for the next one written to write ([`CIR65Fusion::CanFuse`]). |
| [`CIR65Calls`] | A call: arguments pushed or loaded into A, B and Y, the `jsr`, the clean up; runtime calls; the register stub. |
| [`CIR65Selector`] | One IR instruction as 65C64 instructions, told by the others where everything is. |
| [`CIR65Code`] | A function's code as instructions, decoded for the passes ([`SIR65CodeLine`]); a [`CIRBranchCode`] for the shared branch passes. |
| [`CIR65Flags`], [`CIR65Widths`], [`CIR65Peephole`] | Passes over the written code. |

Shared with the W65C816: [`CIRBackend`] (the register argument rule, [`CIRBackend::AssignRegisters`]; phi copies,
[`CIRBackend::ParallelCopy`]; the runtime list, [`CIRBackend::UseRuntime`]; the comparison a block branches on,
[`CIRBackend::BranchComparison`]; multiplies by constants as shifts and adds, [`CIRBackend::ExpandMultiplies`]),
[`CIRBackendPasses`], [`CIRLiveness`] (its dataflow is [`CIRLiveSets`], which the W65C816's packing fills too),
[`CIRLoops::Weight`] (8 times more per loop, each caller its own depth cap), [`CIRMost`] and the four branch passes
over a [`CIRBranchCode`] ([`IRThreadJumps`], [`IRInvertBranches`], [`IRRemoveBranchesToNext`],
[`IRRemoveUnreached`]).

Where the two still differ, they differ for the processors' sake:

- **Folding a pointer plus a constant.**  The 65C64's `[reg + n]` costs nothing more than `[reg]`, so every address
  use folds, the `ptradd` copied next to each load or store ([`CIR65Backend::CopyAddresses`]); the W65C816 pays an
  `ldy` an access, so only a pointer whose every use is an address folds there.  Following chains of them
  (`p + 4 + 8` as `p + 12`, as the W65C816 does) was tried on the 65C64 and dropped: +0.03% on TestBaseLib65, the
  intermediate kept in a register being cheaper than reloading the base from memory at each access.
- **Live ranges.**  The 65C64 defines a result one position after its operands, so an operand dying there can
  always share its home (`add Y, 1`); the W65C816 at the same position, sharing only explicit pairs, as it writes
  wide results a word at a time.
- **Phi copy cycles** are broken through B on the 65C64, through a scratch word on the W65C816.
- **Flags across blocks.**  The 65C64's [`CIR65Backend::FlagsKnown`] lets an `eq` or `ne` block entered only from a
  block that compared the same operands branch on the flags it comes in with.

## How a function is written

[`CIR65Backend::GenerateFunction`], in order:

1. IR rewrites: multiplies by constants ([`CIRBackend::ExpandMultiplies`]), thrown values isolated for exceptions,
   then [`CIR65Backend::AdjustComparisons`] (`x > c` as `x >= c + 1`, so every compare with a constant is
   `cmp x, c`), [`CIR65Backend::PreferSingleBranches`] (a signed compare that would need a branch round a `bra`,
   as the only signed branch is on less, is turned round with its blocks swapped), the block order, loop tests moved
   after their bodies, loads sunk to their use, loop steps sunk past their phi's last reads ([`CIRBackendPasses`]),
   and [`CIR65Backend::CopyAddresses`].
2. Narrow loads only compared found ([`CIR65Places::FindNarrowOnly`]), dominators, liveness, the parameters' places
   ([`CIR65Places::FunctionArguments`]), the frame laid out, and the largest each value can be ([`CIRMost`]).
3. Homes given ([`CIR65Places::Allocate`]) and the body written.
4. With [`CCPPCompileOptions::mbHomeB`], the body written again with B as a home and checked (below).
5. The passes over the code, from the list `gasIR65Passes`, each counted and timed in [`CCPPCompileStatistics`].

Source and place markers go with the lines as they are written ([`CIR65Backend::MarkerLine`]), and
[`CIR65Backend::KeepPrologue`] notes whether the prologue survived the passes, so [`CIR65Backend::DescribeFrame`]
describes the frame for a debugger from what was kept ([`CIR65Written`]), not from the printed text.

## Registers and homes

### What the 65C64 costs

Measured on 2026-11-13 and 14 from a profile and the listings: for the source lines whose code is one instruction,
the cycles divided by the times the line was entered.

| Operand | Cycles |
|---|---|
| Registers only | 1 |
| `[X]`, `[Y]`, `[V]`, `[A]`, `[B]` | 3 |
| `[n]`, `[n + V]`, `[n + X]`, `[n + S]`, a symbol | 4 (5 for a symbol) |
| `[[n]]`, through a pointer in a pseudo register | 6 |
| `add [n], 1`, a step in memory | 6 |
| `psh` or `pul` of a register; of a pseudo register | 3; 5 |
| `mul`, `div` | 1 a step: one for each byte of B ([`CIR65Backend::MultiplyCost`]) |

So a value in a pseudo register or the frame costs 3 cycles more at every use (`IR65_REGISTER_GAIN`), and when this
was measured a third of the instructions run used one.  The W65C816's passes (narrowing, counter divisions, frame
packing) weren't the lever on the 65C64; more register homes were.  The 65C64 back end already had the real register
allocator: it was the 65C64's lack of registers, not its back end, that cost.

### Homes

[`CIRLiveness`] numbers the instructions in block order and gives each temporary its live ranges (with holes, one
per block at most) and a weight: its definition and uses, 8 times more for each loop.  Each phi joins the class of
each value it takes when their ranges don't overlap ([`CIR65Places::Coalesce`]), so most phis need no copies.
Classes are given homes heaviest first ([`CIR65Places::AllocateClass`]), the first that is free for the whole class:

| Home | For a class |
|---|---|
| X | Live across nothing that changes X: a call or a runtime routine. |
| Y | Live across no call, runtime routine, `mul` or `div`. |
| W ([`IR65R_W`]) | As Y, and of pointers and `i32`s only ([`CIR65Places::Fits32BitRegister`]). |
| B ([`IR65R_B`]) | As Y, 32 bits or less, not a parameter, and live across no code that worked in B (below). |
| V ([`IR65R_V`]) | Only in a function that needs no frame; pointers and `i32`s; live across a call, or weighing 3 or more, or V already taken. |
| `[$00]` to `[$7F]` | Live across no call. |
| Where it was pushed | A pushed parameter alone in its class, used at most twice or given none of the above. |
| `[$80]` to `[$FF]` | Weighing 8 or more and the function has no frame yet; or any, in a function with V as a home.  The function pushes those it uses and pulls them before it returns. |
| The frame | Everything else: `[1 + offset + V]`. |

A kept pseudo register costs a push and a pull (10 cycles) and a frame place costs the same to use and nothing to
keep, so a kept pseudo register is only taken where there is no frame yet (0.68% fewer cycles, 2026-11-13), and a
value live across calls goes in the frame when there is one (commit c6d7b7091).

A class's weight leaves out the uses where a pointer in memory costs no more than in a register
([`CIR65Places::DiscountAddresses`]): a load's or store's address (`[[n]]`) and a small step in its own class
(`add [n], 1`).  So in a string loop the bytes get X and Y, not the pointers.  The cost table says a pointer in
memory costs as much as any value, but taking the discount out was 3.2% slower.

### V

V is the frame pointer, kept by every call.  A function that needs no frame ([`CIR65Places::CanUseV`]: nothing laid
out in the frame, no parameter whose address is taken, not variadic) can use it as a third register: it pushes V
first and pulls it last, reads every pushed parameter into a home in its prologue (from S, which hasn't moved yet),
and is frameless.  As calls keep V, it is the one register a value live across calls can have.

V isn't always worth it.  With V a home there is no frame, so whatever would have gone in the frame goes in kept
pseudo registers, each a push and a pull.  [`CIR65Places::PaysV`] weighs what V saves (3 cycles a use of the
classes in it) against `IR65_KEPT_COST` (40, the best across the three suites, 2026-11-13) for each kept pseudo
register it forced; when it doesn't pay, or something still needed the frame, the homes are given again with V the
frame's register, and everything live across calls goes in the frame (`mbFrameOnly`).  A function with calls in a
loop and many values live across them (`CArrayBlock::BinarySearch`) is better off with a frame.

V and W are always 32 bits wide: `wth`, `wthx` and `cpyx` don't take them ([`CIR65Selector::WidthRegister`],
[`CIR65Places::HasWidth`]), which is why they hold only pointers and `i32`s.  With V a home, `[n + V]` is a
pointer's memory, not the function's own, and the passes are told ([`SIR65Frame::bHomeV`],
[`CIR65Code::IsOwnMemory`]) so they don't keep its values (a device register read twice is read twice).

### W

W was first read as the pseudo registers' base: the user's ruling of 2026-10-23 made it a "zero page" pointer, the
pseudo registers written `[n + W]` and W kept 0 at every call and return.  On 2026-11-14 the user ruled that this
"was a misunderstanding around calling the mul instruction": W is an ordinary register a call may change, like X and
Y, and the pseudo registers are `$0000` to `$00FF` whatever W holds.  `mul` and `div` count their steps in W from 0,
so [`CIR65Selector::Multiply`] writes `cpy W, 0` before each, and [`CIR65Peephole`] takes it out where W is 0
already.

The selector and the passes before the last still write and read every pseudo register as `[n + W]`: it is how they
tell a pseudo register from other memory.  The last pass, [`IR65PseudoWithoutW`], writes each as `[n]`.

W can't be an address for `add`, `sub`, `cmp`, `shl`, `shr` or `cpyx` (the user, 2026-10-28), so it is no address
register ([`CIR65Places::IsAddressRegister`]); only a load's or store's `cpy` reads through it as `[W]`
(0.3%, 0.2% and 0.1% fewer cycles).  A pointer in W used anywhere else is copied to B first.

### B

B is where instructions work their second operand, so it can only hold a value across code that doesn't use it, and
only the written code says which code that is.  So the function is written twice:

1. Written without B as a home.  [`CIR65Places::CheckHomeB`] notes the positions whose code writes B.
2. The homes given again with B a home for classes live across none of them, and the code written again.
3. [`CIR65Places::CheckHomeB`] reads the code of each instruction (a chunk, [`SIR65Chunk`]) and fails where a value
   kept in B is lost: written while live across the chunk, read for the last time after B was written, or defined
   part way through.  Those positions are kept out next time and it is written again, at most `IR65_HOME_B_TRIES`
   (3) times, then without B.

32 bit values only gave 1.15%, 1.53% and 3.49%; narrow values added 0.18%, 0.42% and 0.93% more.  The compile-time
cost of writing a function two to four times hasn't been measured.

### What is left in memory

A profile of the three suites on 2026-11-14, each instruction counted exactly: loads and stores of pseudo registers
and the frame were 26% of all cycles, nearly all in functions that call.  Reading a slot again within a block where
it was read already was only 0.89%: the traffic is from too few registers, not from reloading.  After B, 89% of the
weight left out of X, Y and W in TestBaseLib65 is live across a call, `mul` or `div`, which no scratch register can
hold.  The only ways on are registers kept by calls, and those were measured slower (below).

## Instruction selection

- **Values left in A.**  A result only the next instruction uses, and takes from A, is not kept anywhere.  Such an
  instruction is written by its consumer ([`EIR65FusedKind`]): taken from A ([`IR65FU_InA`]), a load read as the
  consumer's memory operand ([`IR65FU_Deferred`]: `add A, [8 + X]`), a narrow load its `sext` widens signed
  ([`IR65FU_Extended`]), or a `udiv` or `urem` its partner gives with the same `div` ([`IR65FU_Paired`]).  A load,
  an operation on it and a store back to the same place are one instruction on memory (`add [4 + X], 1`).  The user
  chose this, the W65C816's shape, over a tidy-up that kept the old one (2026-11-05).
- **Where to work.**  In the result's home when its first operand is there too (`add X, 1`, `shl [4], 2`), in the
  result's register, or in A, with the second operand where it is kept when the instruction can address it (`add`,
  `sub` and `cmp` can't address with V or S, so those go through B).
- **Masks.**  Narrow integers are held extended in 32 bit registers; [`CIR65Selector::StoreResult`] doesn't mask a
  result [`CIRMost::FitsType`] says fits its type.
- **Narrow compares** of a signed `i8` or `i16` are made at their own width (`wtth (A, B), 8`), and with the
  second operand in memory at A's narrowed width rather than through B ([`CIR65Selector::NarrowMemoryOperand`]).
- **Multiply and divide.**  `mul` steps once a byte of B, so a multiplier below 256 has B 8 bits wide; a multiply by
  a constant of a few signed digits is shifts and adds when cheaper.  The optimiser puts an unsigned divide and
  remainder of the same operands together (`ShareDivisions`, told by [`CCPPTarget65C64::ConfigureOptimiser`] that
  the 65C64's `div` leaves the remainder for 8, 16 and 32 bits) and the selector writes both with one `div`
  ([`CIR65Selector::DividePartner`]).  Signed divides call `R_DivideSigned` and `R_DivideSigned64`, noted on the
  runtime list like any routine.
- **Calls** jump to the callee where it is (`jsr _f`, `jsr X`, `jsr [n]`), else through A.  Register arguments follow
  the rule both back ends share; a register function's plain label is a stub that loads them from the stack
  ([`CIR65Calls::RegisterStub`]) for callers that push everything, and the prologue copies the arrived registers to
  the parameters' homes ([`CIR65Backend::StoreRegisterParameters`]).
- **Returns.**  An epilogue of three instructions or fewer (`add S, n` / `pul V` / `ret`) is written at each return
  rather than jumped to, unless preferring size: 0.25%, 0.41% and 0.23% fewer cycles for 0.7% to 1.1% more code.
- **Exceptions.**  A call that may throw is followed by a branch on the carry, and a `ret` reads the carry when the
  program is built with exceptions ([`CIR65Code::SetReturnReadsCarry`]); see `ExceptionsPlan.txt` in the
  [front end design](front-end.md).

## The passes over the code

The selector writes each instruction as simply as it can: A, B, X and Y 32 bits wide before and after every one,
every compare written.  The passes, in `gasIR65Passes` order:

| Pass | Does |
|---|---|
| 65C64StoreLoads ([`CIR65Backend::RunStoreLoads`]) | A value stored then read straight back is taken from the register it was stored from. |
| 65C64Flags ([`CIR65Flags`]) | The flags followed through the code as n and z of a register's value, or what a `cmp` left; a compare the flags already hold goes. |
| 65C64Widths ([`CIR65Widths`]) | The bits of each register really read worked out; each register's width set only before an instruction that needs it, a loop's widths once before it; a copy to A only for a test becomes `tst R, value`. |
| 65C64Peephole ([`CIR65Peephole`]) | What A, B, X, Y and W hold followed through the code; copies of what a register holds go, `cpy W, 0` where W is 0; jumps threaded, a `bra` to a `ret` a `ret`, the shared branch passes. |
| 65C64PseudoWithoutW ([`IR65PseudoWithoutW`]) | `[n + W]` written `[n]`. |

Flags and Widths can't work on a function whose register widths differ between the ways into a line, and leave it as
it is: 46, 54 and 102 functions' runs in the three suites on 2026-11-25.  A loop label's widths are decided once,
before the loop: deciding them again let a stale Y width reach a `jsr` (it crashed TestTextParser, 2026-10-30).

## What the target chooses

[`CCPPTarget65C64`] tells the shared stages what the 65C64 wants:

- **Inlining**, [`CCPPTarget65C64::GetInlineLimits`]: 24 instructions, 48 where the call is in a loop, 96 where a
  profile says it is hot, 32 calls inlined into a function at a time; 4 when preferring size.  Units inline each
  other's functions ([`CCPPTarget65C64::InlinesAcrossUnits`]).  The knee of the measured curve (TestBaseLib65,
  2026-11-13): 16.8% fewer cycles for 18.0% more code against no inlining across units; 16/32/64/24 gave 14.7% for
  8.2%, and the W65C816's 64/128/192/64 19.1% for 42.9%.  Forwarders aren't turned into jumps.
- **The optimiser's passes**, [`CCPPTarget65C64::BuildPipeline`]: the standard pipeline without seven that don't pay
  on a processor with 32 bit registers, a multiply, a divide and indexed addresses: DivisibilityTests,
  ConstantDivisions, MergeAddressPhis, NarrowCounters, NarrowMultiplies, ReduceDivisions and BiasSignedIndices.

| Register arguments in A, B and Y | 7.045G | 17.60G | 36.40G |

## Decisions

- IR only: the direct generator retired for the 65C64 (the user, 2026-10-30), not two back ends kept for it.
- The ABI (the user, 2026-10-23): A, B, X and Y stay 32 bits, widths change only for narrow reads and 64 bit
  operations; arguments on the stack at their own size; V the frame; `this` in X; programs at `$10000`, the stack
  from the top of the first 2MB down.  Details in [`CppCompilerLib/CPP65Generator.txt`].
- `[$80]` to `[$FF]` are kept by calls: a function pushes those it uses (the user, 2026-10-24).
- `add`, `sub`, `cmp`, `shl`, `shr` and `cpyx` address memory with V, X or Y, not W (the user, 2026-10-28).
- The back end shaped toward the W65C816's (the user, 2026-11-05), in full: consumers write fused instructions
  rather than a same-output tidy-up.  The block layout's loop test pass was renamed MoveLoopTests: it moves blocks,
  unlike the optimiser's RotateLoops, which copies a loop's head, and is not a duplicate of it.
- Inlining across units with the measured knee, 24/48/96/32 (the user asked for the knee, 2026-11-13).
- Register arguments (the user, 2026-11-13): `this` stays in X; the first three scalar arguments of 32 bits or less
  in A, B and Y; function pointers and vtables keep the stack entry through a stub, as on the W65C816.
- No register kept by calls (the user, 2026-11-13: measure X kept and Y kept, commit the faster or neither; no change
  to the processor).  Neither: X kept was +0.3%, +1.3% and +1.4% cycles, Y kept +1.5%, +1.3% and +1.0%.  A thiscall
  on another object or a `this` adjusting thunk overwrites X; `mul`, `div`, a third argument and a pointer call's
  stub overwrite Y; and small hot leaves pay the push and pull.  Don't retry without a new idea, such as a register
  that is neither an argument nor `this`.
- W an ordinary register (the user, 2026-11-14: "W is 0 in every call was a misunderstanding around calling the mul
  instruction"): no clears at calls and returns, `cpy W, 0` before each `mul` and `div`; Libc65's `string.asm` and
  `softfloat.asm` no longer keep W.  0.5% fewer cycles on each suite.
- V in a function that has a frame: dropped by the user, 2026-11-14 ("not worth the S management").  Half of the
  instructions run are in such functions and it might give 1 to 2%, but the frame would have to be addressed from S
  with the pushed depth counted at every push and pull, and `add`, `sub` and `cmp` can't address with S.
- Measured and not built, don't do again without a new idea (2026-11-13 and 14): counter divisions (ReduceDivisions,
  +0.76%: the 65C64's `div` is a cycle a step); forwarders as jumps (0.01% of instructions run are a `jsr` then a
  `ret`); dead stores to pseudo registers (1.8M of 3G instructions); no address discount (+3.2%); a load's address
  put in its own X or Y, or a free one, rather than B (+0.19%, 160 of 170 programs slower).
- Below the stop rule (a step goes on only while the next is estimated at 0.2% or more; 2026-11-14): register copies
  at entry (at most 0.3%, the cheap version about 0.1%), widths (largest pattern 0.05%), other copies, other
  branches, constant loads.

## Not done

- Values live across calls stay in memory, and they are most of what is left (26% of cycles are pseudo register
  and frame loads and stores).  Nothing short of a register kept by calls helps, and both tried were slower.
- The cost of writing a function again for B (up to four times) on the compile's time isn't measured.
- B as a home has no test switch to turn it off, as `TEST_PROJECT65_FRAME_V` and `TEST_PROJECT65_ZERO_W` do V and
  W ([`CCPPCompileOptions::mbHomeB`] is on in every build).
- The Flags and Widths passes still leave alone a function whose widths differ between the ways into a line.
- Most of [`CIRMost`]'s gain (1.3% to 2.0% where 0.79% was estimated from facts local to a block) wasn't looked
  into.
- Each processor's passes tried on the other, and the machine passes' order, are `ConsolidationPlan.txt` stage 11,
  not started.
