# W65C816 Back End Design

[The W65C816](../w65c816.md) says what the compiler makes for the W65C816: the model, the calling convention, the
frames and the arithmetic.  This page says why it is made that way, what was measured on the way, and what was
tried and dropped, for whoever changes [`CIRW65C816Backend`] or the W65C816's [`CCPPTargetW65C816`].  The IR it
starts from and the optimiser's passes are [IR Design](ir.md)'s; the 65C64's back end, which shares the register
argument rule, is [65C64 Back End Design](65c64.md).

The plan the target was built from is [`CppCompilerLib/W65C816.txt`]; it stays while its step 7 (the mixed model)
and step 8 (the real machine) are open.  Two finished plans were folded into this page, and are kept only as the
record code and tests cite by step: [`CppCompilerLib/Size16Plan.txt`] (a 16 bit [`size_t`]) and
[`CppCompilerLib/W65C816AlignmentPlan.txt`] (alignment and padding).

## The machine it was designed for

The W65C816 target was first described (2026-10-25) from the start up of a real 65C816 computer, Andre's SFT816,
not the HCP65: 512KB of ROM at bank 0 at reset, copied to RAM, then a write to a register in the bank CPLD swaps
ROM and RAM so the copy runs at the same addresses; the stack at `00:EFFF`, D 0, and WDC's large memory model.  The
user ruled the same day that the exact map doesn't matter, only the ideas of banking and of swapping ROM and RAM:
design for them generically, with a memory map that is configured, never hard coded.

What the compiler and linker took from it:

- **Load address is run address.**  The swap makes them equal, so the linker has no separate load address.
- **Bank 0 holds no code** (the user, 2026-10-25): only the stack, the direct page variables, the hardware vectors
  and one 4 byte `jml` stub per vector, which the hardware needs there because the vectors are 16 bits and an
  interrupt sets the program bank to 0.  [`CAsm65Linker::SetBankSize`] keeps every section inside a 64KB bank and
  refuses any section in bank 0 that isn't placed with `.section name, at address`.
- **The stack top is `$EFFF`** ([`CCPPTargetW65C816::GetStackTop`]) and the start up clears the bss
  ([`CCPPTargetW65C816::HasZeroedBss`]): the SFT816's start up never zeroed it.
- **Interrupts arrive with any D and data bank.**  Every function sets its own D and no code uses the data bank, so
  a C handler would need nothing from the code it interrupted.

Compiled programs run on the test bus ([`CAsm65Memory`] over the fast emulator, and in lockstep with the cycle
exact simulator through [`CAsmW65C816Lockstep`]) and on the HCP65, whose programs start through UserLib's
`UserStart.asm`.  The SFT816's own ROM image, its swap and C interrupt handlers (step 8) were never built.

## The model

The W65C816 goes through the IR only.  The 65C64 generator's direct code wrote 65C64 instructions inline in about
280 places and none of it translates to one accumulator and 16 bits, while IR is target independent: everything
awkward about the W65C816 (the mode bits, banks, no multiply, no call through a pointer) is the back end's and the
linker's problem.  A function the IR front end can't write is an error on this target.

The model is the equivalent of WDC's large model: `jsl` and `rtl` everywhere, globals by long address, the data
bank register unused, pointers of 4 bytes (a 24 bit address and a top byte that is always written 0, so `==` and
`!=` need no mask).  The user's goal (2026-10-25) is an *automatic mixed model*, where the compiler and linker
choose near or far for each call and each datum; the large model was the first step and the mixed model is still
open.

What is target specific outside the back end is in [`CCPPTargetW65C816`]:

| | W65C816 | Why |
|---|---|---|
| `int` | 2 bytes ([`CCPPTargetW65C816::GetIntBytes`]) | The ALU's width (below). |
| Pointer | 4 bytes | 24 bit addresses stored as two words. |
| Bank | `$10000` | Sections never cross one: the program counter wraps in its bank. |
| Frame alignment | 1 | A frame is wherever S is. |
| Object alignment limit | 1 | [Alignment](#alignment-and-padding). |
| Member alignment limit | 2 | [Alignment](#alignment-and-padding). |
| Results widened | No ([`CCPPTarget::WidensResults`]) | The 65C64 returns narrow results as 32 bits; here they stay 16. |
| Subscripts narrowed | Yes ([`CCPPTargetW65C816::NarrowsSubscripts`]) | An index into an array under 64KB is worked out in 16 bits. |
| Inlining | 64 instructions, 128 in a loop, 192 where a profile says hot, 64 calls; 4 when preferring size | Measured below. |
| Across units | Yes ([`CCPPTargetW65C816::InlinesAcrossUnits`]) | Small functions are inlined into other units ([`CIRImports`]). |
| Missing label stub | `$DB` (`stp`) | A call of a label the link didn't find stops instead of running into bank 0. |

## Frames: D is the frame

The user's answer (2026-10-25) was "Which ever will optimise for speed, probably Direct page = frame".  The
prologue saves D, moves S down past the frame and sets D to S, so every local, temporary and argument is a direct
page operand.  The alternative was a fixed direct page of pseudo registers with locals reached stack relative:
calls are cheaper, but `[S + n]` works only with eight instructions and `[[S + n]] + Y` is near only, so a far
pointer in a local would always be copied to the direct page before it could be followed.  With D as the frame a
far pointer is followed where it lies (`lda [[D + n]:24 + Y]`), `inc`, `asl`, `pei` and the rest work on locals,
nothing needs saving across calls, and an interrupt handler sets its own D.

The frame, as [`CIRW65C816Places::Layout`] lays it out ([`SIRW65C816Frame`]), from D + 1 up:

| Bytes | What |
|---|---|
| 1 to 22 | Scratch: a pointer being followed (1), a call's or divide's result and remainder (5), a shift count (13), the runtime routines' operands a (15) and b (19). |
| 23 on | The temporaries (`IR816_FIRST_TEMPORARY`), the most used first, nearest the page's start. |
| | Where an aligned frame past the page keeps S. |
| | The slots (locals whose address is taken, arrays, objects). |
| Top | The words of the arguments that came in registers, pushed by the prologue. |
| Above | The caller's D and the return address (`IR816_LINK_BYTES`, 5), then the pushed arguments. |

A frame of more than 256 bytes has its far part reached through X (`[D + X]`), which is why X allocation is turned
off in such a frame.  A frame of more than 48KB (`IR816_MAX_FRAME_BYTES`) is an error: the stack shares bank 0 with
the direct page.

Two things take the frame away again.  [`CIRW65C816Backend::DropFrame`] removes the frame of a function whose
temporaries were all kept in A or fused: S isn't moved down, and without any `D + n` D isn't even saved.  And a
function that only passes its arguments on to another is a jump to it ([`CIRW65C816Calls::Forwarder`]).

### Aligned frames

A direct page access costs a cycle more when D's low byte isn't 0: about 9.4% of the cycles of the FAT32 benchmark
(2026-10-30).  [`CIRW65C816Backend::AlignFrame`] puts D and S on the page below the frame, copies the arguments up
to it and keeps the old S for the epilogue, which costs up to 255 bytes of stack a call.  The user (2026-10-30):
align only where it is really worth it ("losing a bit of speed might be worth preserving a bit more stack"), never
for a function that can recurse, and frames past the page stay eligible.

- The cost of aligning is 6 cycles, 10 for each argument word copied (words nothing reads aren't), 12 more for a
  frame past the page.
- **Estimated**, the default: the function has a loop, and its direct page accesses, weighted 8 for each loop they
  are in (three levels at most), are at least 3 times the cost.
- **Measured**, when the build has a profile ([`CCPP65Builder::SetFrameProfile`], from [`CAsm65Profile`]): never
  seen recursing, accesses at least 3 times the cost of its calls, and a saving of at least a ten thousandth of the
  profiled cycles.  The profile credits a runtime routine's accesses to the function whose D it runs on.
- Never for a function that may recurse ([`CIRInterprocedural::IsRecursive`] in its unit, or calling itself) or a
  variadic one.  The decision is made in [`CCPP65IRFrontEnd::FinishUnit`], through [`CIRBackend::FinishFunction`],
  once the unit's calls are known.
- A register function is aligned too: the aligned prologue pushes its register words as the plain one does, then
  copies those that are read to the frame's top.

Aligned frames are worth keeping: turned off they cost +4.6% on TestBaseLib65 and +1.8% on TestStandardLib65
(2026-10-31).

## Calls

The rule for register arguments is shared with the 65C64 ([`CIRBackend::AssignRegisters`],
[`CIRBackend::AppendRegisterSuffix`]); [The W65C816](../w65c816.md#register-arguments) gives it.  Why it is shaped
so:

- **The rule needs only the argument sizes**, so every caller works it out alone, and the function's code is at its
  label plus a suffix naming each word's place (`_Add__Fii.ax`).  Before the suffix the linker matched names only:
  non-template members, `extern "C"` functions and return types carry no parameter types, so a caller and a callee
  that disagreed would have linked.  With the suffix they don't (the user asked for that check, 2026-10-31).
- **C linkage too** (the user, 2026-11-03: "the only assembler, linker and compiler that is ever going to see this
  source is this one"): [`memset`], [`strlen`] and the other library calls the optimiser makes are register calls,
  and Libc65's and BaseLib's assembly defines the suffixed entries.
- **Function pointers and vtables keep the stack entry.**  The plain label is a stub that loads the registers from
  the stack ([`CIRW65C816Calls::RegisterStub`]).  It first pushed the stacked words again and called the body; it
  now moves them down to where the body wants them and goes straight on: a comparator called through a pointer went
  from 1,220,702 cycles to 1,177,778 (TestCPP816MergeLoop; 1,087,842 with every argument pushed).  Pointing
  function pointers at the register entry would change what `&f`, vtables, thunks and assembly that takes a
  function pointer mean, and the user closed it (2026-11-14).
- **Cost**: a register word is a load by the caller and a push by the callee (8 cycles; a `pei` is 6), but the
  caller removes nothing after the call (10 to 13 cycles).  The motive was the call overhead measured on
  2026-10-31, about 2.7G cycles of TestBaseLib65's 19.4G: pushes 0.73G, aligned frames' argument copies 0.54G,
  prologues 0.48G, epilogues 0.36G, `jsl` and `rtl` 0.50G.
- [`CCPPCompileOptions::mbRegisterArguments`] false pushes everything, to compare
  (`TEST_PROJECT65_STACK_ARGUMENTS`).

A call through a pointer pushes the return address and the target less one, then `rtl`s into it: the W65C816 has
`jml [a]` only through a fixed bank 0 address, and no `jsl` through a pointer.

### The runtime's conventions

The multiply and unsigned divide routines (`R816_Mul16`, `R816_UDiv32` ...) take their operands in the caller's
scratch bytes (D + 15 and D + 19) and run on the caller's D, using its other scratch bytes; nothing is pushed (the
user chose operands in scratch, 2026-10-29).  The divides leave the remainder at D + 5, so `x / d` next to `x % d`
is one call ([`CIRW65C816Selector::RemainderLeft`], with the optimiser's
[`CIROptimiser::SetDivideRemainders`]).  The soft float routines of `softfloatW65C816.asm` are called at their
frame operand entries ([`CIRW65C816Selector::FrameOperandCall`], when [`CCPPCompileOptions::mbSoftFloatInFrame`]):
the operands stay in the caller's frame and their places go in X and Y, so nothing is pushed or removed
(TestFloatHelper 35.94M to 34.89M cycles).  Because the places are numbers in registers, a function that passes
them keeps its frame.

The routines are Libc65's assembly ([`CCPP65Builder::AddRuntime`]), not text in the compiler (2026-11-06): the
HCP65's maths tables were moved out of ROM to memory loaded from the SD card, so the kernal and the boot program,
which run before the tables are there, need routines without them.  `IRW65C816Runtime-MathTables.asm` multiplies
with Garth Wilson's product table, `IRW65C816Runtime-MathSafe.asm` by shift and add
([`CCPP65Builder::SetMathTables`]).  [W65C816 Runtime](../../hcp65/runtime/w65c816.md) describes them.  The divides
use no table: an unrolled shift and subtract beat the reciprocal table in every case measured (16 / 16 bits 177 to
110 cycles, 16 / 8 358 to 274).  A divide by a constant becomes a multiply by its reciprocal only where
[`CIRW65C816DivisionCosts`] says that costs fewer cycles than the routine.

## Widths: `int`, [`size`] and [`lsize`]

`int` is 16 bits, with no option for 32 (the user, 2026-10-25: "to get a 32 bit int explicitly declare it as an
int32"): 32 bits would make every `int` operation two.  `long` is 32, and Libc65's 32 bit types are `long`.  The
traps this sets for code written for a 32 bit `int` are listed in [Supported C++](../language.md#a-16-bit-int);
every one found was silent, so the compiler warns where it can:

- *Integer overflow* (a constant expression that doesn't fit its type) and *Integer conversion overflow* (a
  constant an implicit conversion cuts), always on; bit patterns such as -1 to unsigned are allowed.
- *Comparison is always true* (or false), from the operands' ranges, always on.
- *Integer arithmetic widened after it may have wrapped*, for `*` and `<<` done in 16 bits then widened.
- *Integer conversion narrows*, any implicit narrowing of a value: off by default
  ([`CCPPCompileOptions::mbWarnNarrowing`]), and how the [`size_t`] change found every count it would cut.

An enum's underlying type follows [dcl.enum], so an enum with `0xFFFFFFFF` is 32 bits here.  BaseLib's overload
sets of 32 bit integers got a 16 bit family under `__W65C816__`, never mixing 16 and 32 bit members, and tests'
expected values were fixed to what each test means (the user, 2026-10-26).

BaseLib's [`size`] is the natural width too, 16 bits, and is [`size_t`], which is `unsigned int`: one type, as on
the other targets.  [`lsize`] is 32 bits for what can pass 64KB.  How this was decided:

- 2026-10-29: [`size`] is 16 bits on the W65C816, unchanged elsewhere, and a new [`lsize`] counts what can be
  bigger.  Each counter was decided on its own, not by a sweep: allocators ([`CMallocator`]), sorts, file reads and
  writes, memory files and caches take [`lsize`].  On hosts the two are one type, so nothing may overload on
  [`size`] against [`lsize`].
- Arrays come in two: natural ones counted in [`size`] ([`SArrayNaturalSize`]) and large ones counted in [`lsize`]
  ([`SArrayLargeSize`], [`CArrayLargeTemplate`] and the others, the user's names).  A natural array is capped at
  64KB of bytes, not of elements, so its index times its element size stays 16 bits; past it, it fails as an
  allocation does ([`CArrayBlockBase::Overflowed`]).  That cap was my design, put to the user and kept.
- 2026-11-18: [`size_t`] is 16 bits too ("32 suffix please.  Whole banks.  Drop 16 suffixes").  [`malloc`],
  [`memcpy`] and the other C functions take 16 bit counts and [`malloc32`], [`memcpy32`] and the others 32 bit
  ones; [`ptrdiff_t`] stays `long`, so a difference of pointers into a block of more than 32KB isn't cut.  Libc65's
  heap is a region per 64KB bank, so no block crosses a bank and [`malloc`] stays constant time; [`malloc32`] of
  more than a bank takes whole banks.
- 2026-11-19 (the user: "Overloads"): a call doesn't name the 32 bit function.  `PrimitiveTypes.h` has, on the
  W65C816, a template of each of [`memcpy`], [`malloc`] and the rest that sends an [`lsize`] (or anything wider
  than [`size_t`]) to the 32 suffixed function, and a [`size_t`] is the C function itself, an exact match.  A new
  call with an [`lsize`] count is right without a sweep to find it.  [`fread`] and [`fwrite`] too.
- The host checks the model with a 32 bit build that defines `BASELIB_SIZE16`, `-Wconversion` warning wherever a
  wider value is narrowed to a [`size`]; it no longer has the W65C816's class sizes since the alignment change, so
  tests have a third branch for those.

With 16 bit counts the inliner copied a small function into every one of 43 calls in [`CTypeNames::Init`] (811
instructions to 12,479).  [`CIRInliner::GrowsWithin`] now weighs all of a caller's copies of a callee against the
one call limit (the user, 2026-11-19): OS.SYS 9,088 bytes and modplay.exe 37,494 bytes smaller than before the
change, for 1.6% more cycles in the size test; leaving calls in loops to the old rule gave back almost none of
them.

## Alignment and padding

The rules are in [Supported C++](../language.md#alignment-and-layout): on the W65C816 `alignof` is 1 for every type
([`CCPPTarget::GetObjectAlignmentLimit`]) and a class's members are padded to 2 at most
([`CCPPTarget::GetMemberAlignmentLimit`]), which [`CCPPClassLayout::LimitedAlignment`] applies as an implicit
`#pragma pack(2)` without going below what `alignas` asks.  Why:

- The W65C816 has an 8 bit data bus: a 16 bit access is two bus cycles at any address, so byte alignment costs
  nothing.  Before, a local's place was D plus an offset with D wherever S was, so `(uintptr_t)&i % alignof(int)`
  could be 1, which C++ doesn't allow; with `alignof` 1 that is right at no cost to any call.  Aligning frames
  instead would have cost about 10 cycles a call.
- Padding stays 2 "for speed" (the user, 2026-11-22): a `char` and its padding byte can be stored with one 16 bit
  store instead of `sep m` / store / `rep m`.  That store was measured and not built: at most 0.004% of a library
  suite's cycles.  Padding to 2 also keeps a class with a wide member a whole number of words, which the FAT
  assembly's word copies rely on.
- The change itself moved the library suites' cycles by -0.03% to -0.22% and their code by -0.01% to -0.05%; what
  it saves is data (a [`CObject`] is 126 bytes for 144).  865 of 2,427 W65C816 class layouts changed; the 65C64's
  2,352 did not.
- A class layout shared with code from another compiler must pad the same everywhere.  The FAT assembly reads
  offsets from `BaseLib/FatW65C816.inc`, which TestBaseLib65 generates with this compiler, and HCP65's emulator
  test reads the kernal's status members one after another.
- [`CCPP65Builder::SetLayoutsFile`] (`hcp65build -layouts`, `TEST_PROJECT65_LAYOUTS`) writes every class's layout
  sorted, so two builds compare with `diff`: it is how the 865 were found.

## Register allocation

The W65C816 has one accumulator, and X and Y only count, index and compare, so the back end's registers are mostly
the frame.  Every temporary starts with a frame place of its own, and the work is in making places shared and
values not stored at all:

- **Shared places.**  [`CIRW65C816Places::PackTemporaries`] works out each temporary's live range with holes
  ([`CIRW65C816LiveRanges`]) and gives temporaries that are never live at once one place.  A result may share its
  argument's place, a call's result its arguments', a load its pointer's and a phi its value's, but only when one
  range ends where the other starts.  Placement tries a pair partner's place first, preferring the pair whose copy
  is in the deepest loop, so a pointer stepped in a loop keeps its place and is stepped there (`inc` in
  place).  -6% and -5% on the two suites (2026-10-29).
- **Values kept in A.**  A one word temporary stored and then loaded once later in its block isn't stored and
  reloaded ([`CIRW65C816Backend::FindSingleUses`] and the peephole).
- **Fused values.**  An instruction whose result's one use is the next instruction isn't written where it is: its
  words go through A into that instruction as it goes, in chains of up to four ([`CIRW65C816Fusion::CanFuse`]), so
  a load, `or` and store back is `lda`, `ora`, `sta` a word at a time.
- **X** ([`CIRW65C816Places::AllocateX`]): one word temporaries kept in X instead of their place, scored by what X
  saves at each use (`tax` for `sta`, `txa` for `lda`, `inx`, `cpx`, `phx`), eight times more for each loop, and
  not for any live across a call, a shift by a count or a runtime routine.  It saved only 1.3% (2026-10-29): the
  hot loops count in 32 bits.
- **Y is not allocated**: `ldy` comes before nearly every access through a pointer.  An `i16` index is put in Y for
  the access instead ([`CIRW65C816Folds::FoldIndices`]: the W65C816 adds Y to all 24 bits), as is a pointer plus a
  constant ([`CIRW65C816Folds::FoldPointers`]).
- **Known words.**  Words that are always 0 are read as the constant ([`CIRW65C816Backend::FindZeroWords`]), an
  `i8` only ever read as a byte isn't masked ([`CIRW65C816Backend::FindLowByteUses`]), and a slot only loaded and
  stored at constant offsets is addressed in place ([`CIRW65C816Folds::FindDirectSlots`]).

Then passes over the code text ([`CIRW65C816Code`]), in order: [`CIRW65C816Backend::Peephole`], the mask, store,
transfer and branch peepholes, [`CIRW65C816Backend::PeepholeRegisters`] (loads of what A, X or Y already hold),
[`CIRW65C816Backend::RemoveUnreadStores`] (stores to direct page words nothing in the function reads), the dead
store passes, and [`CIRW65C816Backend::PeepholeFlowRegisters`] across labels.  A branch round a loop is marked
(`IR816_ROUND`) so [`CIRW65C816Backend::PeepholeBranches`] can make going round one taken branch.

## The speed work

Step 7 of the plan was measured throughout with the simulator's cycle counts of whole library suites
(`TEST_PROJECT65_CYCLES`, the sum over a suite's programs) and with [`CAsm65Profile`]'s reports (per function, per
line and, since 2026-11-06, per call site: [`CAsm65Profile::GetCallSite`]).  The suites' programs changed between
rounds, so each round's numbers compare only with each other.  Compare like with like: a suite run in parallel with
another read about 0.13% higher than alone.  The biggest levers:

| Change | Measured | Date |
|---|---|---|
| `mvn`/`mvp` string routines, patched at run time (the user: code runs in RAM, self-modifying is fine), and the divide fast paths | TestBaseLib65 108.1G to 87.3G | 2026-10-29 |
| Shared places with holes in live ranges | -6% / -5% | 2026-10-29 |
| Inline limits 16/32/24 to 32/64/32, then 64/128/64 with 192 when hot | -3.3% / -5.0%, then -2.0% / -3.5% | 2026-10-31 |
| Narrowed subscripts ([`CCPP65IRFrontEnd::NarrowSubscript`]) | -1.5% / -2.0% | 2026-10-31 |
| The allocator's second level in 16 bits, `__builtin_clz` as `R816_Clz16` ... | -2.9% / -2.6% | 2026-11-06 |
| Cross-unit inlining, `__restrict`, loop counters, exit values (the Tide/Video sprite test) | 69.6M to 19.6M cycles; TestBaseLib65 816 compiles in 32 s, was 19 s | 2026-10-29 |

The work on [`CNumber`] (2026-10-30, TestNumber 70.34G to 52.27G cycles) left instruction choices in the selector
and the peephole passes that every program now gets:

- A word shifted by 8 or more swaps the accumulator's bytes (`xba`) first, and a signed shift right by 15 is
  `asl`, `lda #0`, `adc #$FFFF`, `eor #$FFFF` ([`CIRW65C816Selector::ShiftWordInA`]).
- A signed 16 bit compare of two variables is `sec`, `lda`, `sbc`, `bvc`, `eor #$8000` then `bmi` or `bpl`
  ([`CIRW65C816Selector::SignedLessFlags`]).
- A byte multiply is inlined through the maths tables ([`CIRW65C816Selector::ByteMultiply`]).
- [`CIRW65C816Backend::PeepholeMasks`] drops an `and #$FF` the next one redoes when only carry-safe arithmetic is
  between them; [`CIRW65C816Backend::PeepholeStores`] turns `sta w` / `dec w` / `lda w` into `dec A` / `sta w` and
  `sta w` / `ldy w` into `sta w` / `tay`, dropping the store when nothing reads the word again
  ([`IR816DeadStore`]); [`CIRW65C816Backend::PeepholeTransfers`] moves through one register instead of two
  (`tax` ... `txy` to `tay`) when X is dead after.

Where the cycles were (TestBaseLib65, 2026-10-31): the runtime routines 25.7% (the 32 bit divides about 1.75G), the
allocator 20.7%, calls about 13%.  Each of those got a round of its own.  The profile also found source to fix
rather than code: a memset of a whole cache on every clear (12.2% of TestStandardLib65) and a binary search per
size on every memory set up (7.6%).

Two limits came from a miscompile: inlining a self-recursive function every round grew [`CRedBlackTree::IsValid`]
to 65,613 bytes and the program counter wrapped in its bank.  The linker now refuses code bigger than a bank, the
inliner inlines a recursive callee once per caller, and no function grows past `IR_INLINE_MAX_CALLER` (4096)
instructions by inlining.

## Decisions

- The W65C816 is compiled through the IR only; the direct generator isn't ported (2026-10-25).
- `int` is 16 bits, with no 32 bit option; 32 bits is `long` or [`int32`] (the user, 2026-10-25).
- Large data and far calls first, then an automatic mixed model chosen by the compiler and linker (the user,
  2026-10-25).
- The direct page is the frame: "Which ever will optimise for speed, probably Direct page = frame" (the user,
  2026-10-25).
- Far pointers are stored in 32 bits with the top byte ignored, so there is no 8/16 bit mode switching (the user,
  2026-10-25); the compiler writes the top byte as 0 so `==` and `!=` need no mask.
- The assembler uses Assembler65Lib's style (the user, 2026-10-25).
- No code in bank 0 but the vectors' stubs: "all that is allowed in bank zero is the stack and direct page
  variables" (the user, 2026-10-25).
- The memory map is designed generically, not from the SFT816's details (the user, 2026-10-25).
- BaseLib's overload sets get a 16 bit family under `__W65C816__`, never mixed (the user, 2026-10-26).
- The multiply and divide routines take their operands in the caller's scratch bytes (the user,
  2026-10-29).  Choosing a routine from compile time bounds (`R816_Mul32x8`) was dropped: -0.19% wasn't worth a
  second bounds analysis (the user, 2026-10-29).
- The string routines may modify their own code: the code runs in RAM (the user, 2026-10-29).  They aren't
  reentrant, so interrupt handlers mustn't call them.
- `FastFunctions` were removed from every project: trust the compiler and Libc65 (the user, 2026-10-29).
- [`size`] is 16 bits and [`lsize`] 32; allocators, sorts and file IO take [`lsize`]; large arrays are separate
  classes (the user, 2026-10-29).  [`size_t`] is 16 bits with 32 suffixed functions and banks for big allocations
  (2026-11-18); the 32 bit ones are chosen by overloads (2026-11-19).
- Frames are aligned only where measured or estimated to pay, never for recursion; profile guided optimisation is
  optional (the user, 2026-10-30: "make PGO optional ... but otherwise use the best estimate").
- Register arguments for every function that isn't variadic, C linkage included, with the suffixed label (the user,
  2026-11-02 and 2026-11-03).
- Function pointers and vtables stay on the stack entry, and there are no frameless leaf functions running on the
  caller's scratch bytes: closed, don't offer again (the user, 2026-11-14,
  [`CppCompilerLib/CodeGenerationHandoff.txt`]).  A frameless leaf needs every caller's scratch free at a call,
  which callers with D = S, interrupt stubs and assembly with their own D don't promise.
- Narrow results aren't returned zero extended: the callee would have to mask whatever it didn't know was clean
  (closed 2026-11-14).
- The runtime's tables aren't in ROM, so there are routines without them (the user, 2026-11-06).
- `alignof` is 1 and members are padded to 2 (the user, 2026-11-22); the 16 bit store over a `char` and its padding
  isn't built; the layouts file is a builder option and an `hcp65build` argument, not a configuration attribute; no
  file is meant to pass between a PC and the HCP65 as raw classes (the user, 2026-11-22).
- Measured and dropped, don't repeat without a new idea: keeping values in X or Y across blocks (1% at most); Y as
  an allocated register; ordering blocks so a successor falls through without a profile (-1% on one test, +4% on
  another); guessing that a branch back is taken; replacing a counter test by a pointer test (0.1% to 0.4% slower);
  grouping place pairs before placement (-0.1% but a test over its bound); pairing every wide load with its pointer
  (+0.45%); 32 bit divides by a constant as 64 bit reciprocal multiplies while `R816_Mul64` was a loop (+64%);
  copying whole words while shifting; reciprocal tables for the divides; marking every pointer `restrict` (0.2% as
  an upper bound).
