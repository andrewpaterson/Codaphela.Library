C++14 compliance: where it stands and what is left
===================================================

Written 2026-11-20 for the session that carries this on.  It replaces the to do part of CppParserTodo.txt, which stays
as the record: the questions the user answered and the rulings, which the sources cite by number ("CppParserTodo.txt
question 13"), and what each stage and step did.  Read this file first, and that one when a ruling is cited.


What is aimed at
----------------

The user's rulings, which govern everything below:
  - The compiler (CppCompilerLib: both targets, the 65C64 and the W65C816) is to compile C++14.  "We're aiming for a
    freestanding C++14 implementation first, then the standard libaries afterwards" (2026-11-19).
  - The library: "I don't use the C++ Std Libs, and don't want to include the library with their source code in any
    of my projects.  The problem is LibC already exists and has useful intrinsic (or close to intrinsic methods)."
    So nobody else's library source comes in, and Libc65 is where what is written goes.
  - Exceptions were another session's work (ExceptionsPlan.txt), on master since 2026-11-20 and finished: stages 0 to 9
    behind a build option that is off by default (CppParserTodo.txt question 1), and its stage 10 (the IDE, IR.txt,
    CPP65Generator.txt) the same day.  The Exceptions group (CONFORMANCE_EXCEPTIONS_GROUP) passes all its cases on
    both targets: a change that touches the front end's exception paths keeps it so.  What the sweep finds in the
    exception paths of the front end, or in the Exceptions group, is reported to the user before it is changed.
  - A sweep is measured first and shown as a list; the compiler is changed only for what the user then picks.  A
    decision made while planning is not a go-ahead to build.
  - Questions for the user are asked one at a time, in plain words, and kept in a list while work goes on.
  - Commits have no co-author line, are made by pathspec, and are never pushed: the user pulls and pushes.  Other
    sessions work in the same checkouts at the same time.

What is left, in the order suggested
------------------------------------

A. The clause sweep (agreed with the user 2026-11-20: measured first, shown as a list, then what they pick is fixed;
   to start once the exceptions work has landed, which it did on 2026-11-20; started that day).
   - Clauses 3, 6, 7, 9, 10, 11, 12, 13 and 14 of N4140, then 2 and 16 (lexing and the preprocessor, which have
     tests from Part A and were never gone through by clause).  15 was done by the exceptions work (its 180 cases,
     written paragraph by paragraph); it isn't swept again.
   - How 4, 5 and 8 were done: read the clause paragraph by paragraph; write a small program for each rule that can be
     tested, valid ones that return a number and invalid ones that must be refused; check every one against g++
     first (clauses.py check); run them through the compiler on both targets; give the user the list of what differs,
     worst first (wrong code, valid code refused, invalid code accepted), each with its paragraph.  Going by those
     three clauses, expect more from this than from everything in B.
   - A clause's cases go in Tests/TestCppCompilerLib/Conformance/Clauses/ClauseNN.txt ("How the cases are kept").

   - Clause 3, measured 2026-11-20 (a5c2a7c15): 50 of 85 on the 65C64, 49 on the W65C816, and one case held out
     because it crashed the compiler.  The user, 2026-11-21: "Plan fixes for 1 to 23 then implement that plan in the
     best order.  Clean up and commit with no co author as you go.  Ensure there are tests."  The plan, in the order
     done (item numbers are the list's; each fix's commit names its items; its tests are the clause 3 cases, and a
     new refusal has a valid case beside it):
       1  enum { x = x }; recursed until the stack overflowed: the enumerator is declared after its value is parsed
          (the parser).  The held case goes back into Clause03.txt.
       2  int S::a = k; found ::k: the initialiser of a declarator qualified by a class or namespace is parsed in a
          block whose qualifier is that scope, as a member function's body is (the parser).
       3  Constant initialisation of an object made by a constexpr constructor, a reference to a static object and a
          pointer to one: emitted as data, not run by the start-up code (the unit, with CPPConstants).
       4  alignas(8) on a local on the W65C816: the frame gives the alignment asked (its back end).
       6, 10  Lookup by kind (CCPPScope): in a scope where a class or enum and a variable, function or enumerator
          share a name, ordinary lookup finds the second (the constructors in a class's own scope aren't that); an
          elaborated type specifier finds the first; a name before :: and a namespace alias's or using-directive's
          name consider only namespaces, types and templates, going outward past what isn't one.
       5  A local class using its function's static locals and constants: the binder and the IR front end find the
          enclosing function's variable (its label, or its constant value).
       9  A default argument in a class naming a later member: its tokens are kept and parsed when the class is
          complete, as member function bodies are (the parser).
       11 p->Base::v with Base a member typedef of p's class: the qualifier is looked up in the object's class when
          the context doesn't find a class (the binder).
       12 s.operator double() chooses the conversion function of that type; s.operator I() with I a member typedef
          parses, I being looked up in the object's class (the parser and the binder).
       13 A template's non-type parameter whose default depends on an earlier parameter (CPPUnitTemplates).
       7  switch (int x = f()): the condition's variable is declared and the switch is on it (the IR front end).
       8  goto while a destructible local is alive: the goto destroys what it leaves, what is alive at the label
          staying; a jump past an initialised declaration into its scope stays refused (the IR front end's cleanups).
       14 The harness: a clause case that uses the library's operator new links Libc65's new.cpp, as the Exceptions
          group does.
       15, 16, 17, 18  Declarations that clash in one scope ([basic.scope.declarative] 4): a variable defined twice
          (a redeclaration is the first's variable; extern "C" { int x; } defines), a class defined twice, two
          enumerators or a variable and a function of one name, a block's redeclarations (a for's or a condition's
          variable in the statement's outermost block, a parameter in the function's), a label twice in a function,
          a template parameter's name declared in its template.  C sources keep tentative definitions.
       19 A::A as a type names the constructor: refused.
       20 A block scope extern of another type than the variable it redeclares, and a function declared again with
          another return type, though neither is used.
       21 An allocation or deallocation function declared in a namespace, or static.
       22 A member reached through a class that is still incomplete there.
       23 A constexpr variable whose type isn't a literal type.

B. Gaps that are known.  Each was probed against g++; none is common.
   1. A union's inactive member read in a constant, on the 65C64: accepted where the two members are the same size
      (the constant interpreter keeps bytes, not which member was last given a value).  It is the one case in the
      lists (ConstantInactiveUnionMemberRefused).  The user, 2026-11-20: "no I don't want item 2".  Leave it.
   2. A member template whose parameters are its class's pack and then its own: template<class... B> static int
      Mix(A... a, B... b) in template<class... A> struct Pair.  The call isn't matched ("The number of arguments
      does not match the function").
   3. A partial specialisation, outside the class, of a class template's member variable template (template<class
      C> template<class T> constexpr bool W<C>::same<T*> = true;).  The template itself, in the class or outside
      it, works.
   4. (decltype(f())::k) + 1: read as a cast.  The parser has no types; it decides by the member's name only where
      decltype's operand is the name of a variable or parameter declared with a class's name
      (CCPPParser::DecltypeMemberIsType).
   5. final where nothing uses the class: checked for a class at namespace scope (CCPPUnit::CheckVirtSpecifiers), not
      for one nested in a class or declared in a function.
   6. A name two bases each have, named alone in a member function, where it is a type, a static member or an
      enumerator: not reported (a field and a call are: CCPPBinder::HasOneMeaning).

How the cases are kept
----------------------

Tests/TestCppCompilerLib/Conformance has the tools:
  - Clauses/ClauseNN.txt (Clause05a.txt to Clause05f.txt for clause 5; new clause 5 cases go in Clause05f.txt): the
    clause cases as they are written.  A case is "### Name | expect | reference" and then its source: expect is what
    main returns (the same on both targets and on the host: compare with sizeof, never return one) or REFUSED.
  - clauses.py check: every case through g++.  A case is checked before the compiler is asked to agree with it.
    clauses.py header: writes the cases into TestCppCompilerLib/TestCPPConformanceClauseCases.h, which is generated:
    don't edit it.  A clause new to the test also needs its CONFORMANCE_GROUP line in TestCPPConformance.cpp.
  - lists.py (-why, -write): which cases the compiler doesn't do, and writes that into TestCPPConformance.cpp's
    lists.  Read what changed before committing it: a list that grows is a regression.  (On 2026-11-20 six cases
    went into the lists unseen because the output was cut short.)
  - hostcheck.py and gcccheck.sh: the cases the test exports (TEST_CPP_CONFORMANCE_EXPORT), the hand written ones
    too, against the Microsoft compiler and g++.
The test's own switches (in the environment): TEST_CPP_CONFORMANCE_TRY=<file> compiles and runs one program on both
targets and says what it did, which is how a probe is tried; _LISTS prints the lists; _VERBOSE says why a case
failed; _LISTINGS=<directory> writes the listings.
The hand written cases (TestCPPConformanceCases.h) are edited where they are.


How a change is checked
-----------------------

Before a commit, all of these, on both targets:
  1. TestCppCompilerLib, the whole of it (RunParallel.py -exe <the test> -jobs 12: about two minutes).  0 failed.
  2. The conformance lists unchanged but for the cases the change was for.
  3. TestBaseLib65, TestStandardLib65 and TestSupportLib65: the three libraries compile and their tests pass.
  4. TestLibc65.
  5. The twenty HCP65 projects build (hcp65build <project>.hcp65build -config "Release|W65C816"), where the change
     could refuse or change real code.
A new language rule gets a case, g++ checked, in the clause it belongs to; a new refusal gets a Refused case and a
valid one beside it that must still compile.  Release builds, x64.

On dev7 (Linux) the session before kept its scripts in
/home/r2d2/.claude/projects/-home-r2d2-Codaphela/sweep-clause4-5/ (their paths name a scratchpad that is gone:
change the first lines).  verify.sh copies the checkouts to a snapshot and does 1 to 4 on the copy, so the source
tree stays free for other sessions and for the next piece of work; snapcommit.sh commits the snapshot's files, which
are the ones that were checked; try.sh is TEST_CPP_CONFORMANCE_TRY on one file; hcp65_all.sh is 5.

Things that went wrong and needn't again:
  - CppCompilerLib.vcxproj and its .filters have CRLF line endings; the sources have LF.  A script that rewrites a
    file must keep its line endings (Python: open(..., newline='')).
  - A new source file goes in CppCompilerLib.vcxproj and CppCompilerLib.vcxproj.filters: the CMake builds read the
    project file.
  - A value that depends on the target (sizeof(long), sizeof(int)) can't be a case's result: g++'s differs.
  - An int is 16 bits on the W65C816: a probe that returns 41 * 1000 fails there and nowhere else.
  - The checker (CCPP65TypeChecker) and the IR front end each decide what a program means.  The checker is asked
    first and of every declaration (CCPPUnit::CheckDeclared); where the two disagree the IDE shows a false error.  A
    rule goes in the binder (CCPPBinder) or the unit where both ask it.
