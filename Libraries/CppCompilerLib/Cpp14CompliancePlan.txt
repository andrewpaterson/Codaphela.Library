C++14 compliance: where it stands and what is left
===================================================

Written 2026-11-20 for the session that carries this on.  It replaces the to do part of CppParserTodo.txt, which stays
as the record: the questions the user answered and the rulings, which the sources cite by number ("CppParserTodo.txt
question 13"), and what each stage and step did.  Read this file first, and that one when a ruling is cited.


What is aimed at
----------------

The user's rulings, which govern everything below:
  - The compiler (CppCompilerLib: both targets, the 65C64 and the W65C816) is to compile C++14.  "We're aiming for a
    freestanding C++14 implementation first, then the standard libaries afterwards" (2026-11-19).
  - The library: "I don't use the C++ Std Libs, and don't want to include the library with their source code in any
    of my projects.  The problem is LibC already exists and has useful intrinsic (or close to intrinsic methods)."
    So nobody else's library source comes in, and Libc65 is where what is written goes.
  - Exceptions were another session's work (ExceptionsPlan.txt), on master since 2026-11-20 and finished: stages 0 to 9
    behind a build option that is off by default (CppParserTodo.txt question 1), and its stage 10 (the IDE, IR.txt,
    CPP65Generator.txt) the same day.  The Exceptions group (CONFORMANCE_EXCEPTIONS_GROUP) passes all its cases on
    both targets: a change that touches the front end's exception paths keeps it so.  What the sweep finds in the
    exception paths of the front end, or in the Exceptions group, is reported to the user before it is changed.
  - A sweep is measured first and shown as a list; the compiler is changed only for what the user then picks.  A
    decision made while planning is not a go-ahead to build.
  - Questions for the user are asked one at a time, in plain words, and kept in a list while work goes on.
  - Commits have no co-author line, are made by pathspec, and are never pushed: the user pulls and pushes.  Other
    sessions work in the same checkouts at the same time.

How the cases are kept
----------------------

Tests/TestCppCompilerLib/Conformance has the tools:
  - Clauses/ClauseNN.txt (Clause05a.txt to Clause05f.txt for clause 5; new clause 5 cases go in Clause05f.txt): the
    clause cases as they are written.  A case is "### Name | expect | reference" and then its source: expect is what
    main returns (the same on both targets and on the host: compare with sizeof, never return one) or REFUSED.
  - clauses.py check: every case through g++.  A case is checked before the compiler is asked to agree with it.
    clauses.py header: writes the cases into TestCppCompilerLib/TestCPPConformanceClauseCases.h, which is generated:
    don't edit it.  A clause new to the test also needs its CONFORMANCE_GROUP line in TestCPPConformance.cpp.
  - lists.py (-why, -write): which cases the compiler doesn't do, and writes that into TestCPPConformance.cpp's
    lists.  Read what changed before committing it: a list that grows is a regression.  (On 2026-11-20 six cases
    went into the lists unseen because the output was cut short.)
  - hostcheck.py and gcccheck.sh: the cases the test exports (TEST_CPP_CONFORMANCE_EXPORT), the hand written ones
    too, against the Microsoft compiler and g++.
The test's own switches (in the environment): TEST_CPP_CONFORMANCE_TRY=<file> compiles and runs one program on both
targets and says what it did, which is how a probe is tried; _LISTS prints the lists; _VERBOSE says why a case
failed; _LISTINGS=<directory> writes the listings.
The hand written cases (TestCPPConformanceCases.h) are edited where they are.


How a change is checked
-----------------------

Before a commit, all of these, on both targets:
  1. TestCppCompilerLib, the whole of it (RunParallel.py -exe <the test> -jobs 12: about two minutes).  0 failed.
  2. The conformance lists unchanged but for the cases the change was for.
  3. TestBaseLib65, TestStandardLib65 and TestSupportLib65: the three libraries compile and their tests pass.
  4. TestLibc65.
  5. The twenty HCP65 projects build (hcp65build <project>.hcp65build -config "Release|W65C816"), where the change
     could refuse or change real code.
A new language rule gets a case, g++ checked, in the clause it belongs to; a new refusal gets a Refused case and a
valid one beside it that must still compile.  Release builds, x64.

On dev7 (Linux) the session before kept its scripts in
/home/r2d2/.claude/projects/-home-r2d2-Codaphela/sweep-clause4-5/ (their paths name a scratchpad that is gone:
change the first lines).  verify.sh copies the checkouts to a snapshot and does 1 to 4 on the copy, so the source
tree stays free for other sessions and for the next piece of work; snapcommit.sh commits the snapshot's files, which
are the ones that were checked; try.sh is TEST_CPP_CONFORMANCE_TRY on one file; hcp65_all.sh is 5.

Things that went wrong and needn't again:
  - CppCompilerLib.vcxproj and its .filters have CRLF line endings; the sources have LF.  A script that rewrites a
    file must keep its line endings (Python: open(..., newline='')).
  - A new source file goes in CppCompilerLib.vcxproj and CppCompilerLib.vcxproj.filters: the CMake builds read the
    project file.
  - A value that depends on the target (sizeof(long), sizeof(int)) can't be a case's result: g++'s differs.
  - An int is 16 bits on the W65C816: a probe that returns 41 * 1000 fails there and nowhere else.
  - The checker (CCPP65TypeChecker) and the IR front end each decide what a program means.  The checker is asked
    first and of every declaration (CCPPUnit::CheckDeclared); where the two disagree the IDE shows a false error.  A
    rule goes in the binder (CCPPBinder) or the unit where both ask it.
