CppCompilerLib: consolidation plan
==================================

How the compiler is to be reshaped from five very large classes, full of special cases, into small classes that
each do one job.  Written 2026-11-11, from reading the code and measuring it; nothing here is started.  The library
was CppParserLib until that day.

The rule for every stage (the user, 2026-11-11): the code the compiler writes must work, and ideally is faster.
It does not have to be the assembly written before.  So a stage is free to take the simpler design where the old
one's special cases were only there to be kept, and to let one way of doing a thing replace two that differed.
A stage doesn't add C++ features.


Where it is now
---------------

491 files, 127,000 lines, 3,319 functions.  368 functions are over 50 lines and 101 are over 100.  In the table
the lines are those inside the class's functions.

	Class                Functions   Lines   ifs   What it is
	CCPP65Generator         314      8,909   865   Everything about the C++: 65 fields, 3 friend classes
	CIROptimiser            173      8,438   782   Every pass, 29 fields, the order written out in Optimise
	CIRW65C816Backend       158      6,137   492   Frame, places, instructions, calls, peepholes, runtime
	CCPP65IRFrontEnd        187      5,811   624   Function bodies to IR
	CCPPParser              159      5,496   619   The parser
	CIR65Backend            131      3,484   325   The 65C64's, 30 fields
	CPreprocessor           101      3,174   285   Preprocessor.cpp is 3,557 lines and was never split
	CCPP65TypeChecker        70      2,103   291   Expressions' types
	CCPP65Builder            98      1,296    81   Project, scheduling, linking, listings

The clean-up of 2026-11-04 and 05 split the big files by subject.  The classes were not split: each is still one
class with all its state shared between all its functions, spread over ten files.  That is what is left to do.


What makes the special cases
----------------------------

1. Every decision about an expression is made twice, and some three or four times.

   CCPP65TypeChecker and CCPP65IRFrontEnd walk an expression side by side: 44 of their functions have the same
   name (CallExpression, MemberCall, Construct, Convert, Operate ...).  Each one works out again what the other
   already knew.  CallExpression is the worst: a cascade of a dozen tests (pack expansion, member expression,
   member pointer, qualified by a class, function template, member of this, memcpy, builtin, associated
   namespaces, function pointer, named function) is written out in both, and not in the same order: the checker
   tries a function template before a member and the front end a builtin before a template.  A new special case
   has to be added to both, in the right place in each.  The front end has 165 "Unsupported(__FILE__, __LINE__)"
   exits for things the checker should have settled, asks the generator 285 questions (mpcGenerator->) and calls
   TypeOf again 29 times.  Constant (234 lines) is a third walk, the warnings a fourth, CPP65GeneratorCheck a
   fifth.

2. The C++'s things are structs, and all they can do is in the generator.

   SCPP65Class has 8 flags, SCPP65Function 13, SCPP65Template 4.  Anything asked of one is a generator function
   that takes it as its first argument: IsPolymorphic(psClass), NeedsDestructor(psClass), FindField(psClass, ...),
   AppendClassLabel(psz, psClass, ...).  So the generator has 314 functions and three friends.  A call is resolved
   through twelve ways in (FindFunction, FindNamedFunction, FindAddressedFunction, FindAssociatedFunction,
   FindOperator, FindFreeOperator, FindStaticFunction, FindConversion, FindMemberTemplate, ChooseMemberTemplate,
   ChooseTemplate, GetCallTemplate).  Nine Deduce functions hand the same five arguments to each other.

3. Where the compiler is, is kept in members that are saved and put back by hand.

   mpsBindings is set at 25 places, quiet mode (BeginQuiet, EndQuiet, miQuiet, mbQuietFailed) is
   at 116, and mpsFunction, mbThis, mbStaticLocal, mbCLinkage and mpcPackParameter are the same kind.  A
   function's answer depends on members its arguments don't show.

4. The target is an enum, tested where it matters.

   SCPPTarget has eight numbers.  The rest of what differs between the processors is about 30 tests of
   CPPT_W65C816 in eight files (ten in the builder), InitOptimiser's seven "bW65C816 ?" settings, pairs of
   IR65_INLINE_ and IR816_INLINE_ #defines, szW65C816Only on a builtin, the W65C816's frame in a struct the
   shared front end keeps, and globals: gbIR816RegisterArguments, gbIR816SoftFloatInFrame, gbW65C816Assembly,
   CIRW65C816Backend's static scratch allocator and nine statics on CCPP65IRFrontEnd ("only exact when the units
   are compiled one at a time").

5. Kinds are told apart with GetKind and a cast.

   233 GetKind tests and 333 casts to a syntax class.  The syntax nodes are classes (85
   files) but all they do is print themselves and list their fields.

6. The back ends write text and read it back.

   About 300 places append assembly as text.  The passes after them need to know what a line is, so CIRW65C816Code
   and CIR65Code decode the text again; source positions travel as marker bytes that are taken out and put back
   (CIRSourceMarkers); AlignFrame (254 lines) edits the text a third time.  CIRW65C816Backend has nine passes each
   declared twice (for a CChars and for a CIRW65C816Code), and nine arrays indexed by temporary.

7. The optimiser's passes are functions of one class.

   Optimise calls 32 of them in a row, some behind flags the target set (mbConstantDivisions && ...).  Four
   idiom passes (ReplaceStrchr 211 lines, ReplaceStrlen 146, ReplaceMemchr 129, ReplaceMemcmp 122) each match
   a byte loop for themselves.  ConstantDivisions, ReplaceStrchr and ReplaceStrlen nest eight deep.


The shape to reach
------------------

Eight layers.  A layer uses the ones above it in this list and nothing below.  (CCPPTarget is what the layers
see; the 65C64's and the W65C816's own classes make their back ends and pipelines, so they sit with Machine.)

	Target     CCPPTarget: CCPPTarget65C64, CCPPTargetW65C816, CCPPTargetHost
	Text       CPreprocessor (sources, macro expander, directives, includes), CCPPTokeniser
	Syntax     CCPPParser, the CCPPSyntax classes, CCPPScope, CCPPSymbol, CCPPSyntaxVisitor
	Meaning    CCPPUnit, CCPPTypes, CCPPClass, CCPPFunction, CCPPVariable, CCPPTemplate
	           CCPPBinder, which makes CCPPBound nodes: an expression typed and resolved
	           CCPPOverloads, CCPPDeduction, CCPPDeclarators, CCPPMangler, CCPPWarnings
	Lowering   CCPPLowering (bound nodes to IR), CCPPUnitData (globals, strings, vtables, start up tables)
	IR         CIRModule, CIRFunction; CIRPass and the passes, CIRPipeline; CIRInliner, CIRInterprocedural
	Machine    CIRBackend: CIR65Backend and CIRW65C816Backend, each a frame, places, a selector, calls, its code as
	           instructions, passes over them and a printer
	Build      CCPPBuild, CCPPUnitCompiler, CCPPUnitSchedule, CCPPProgramLinker, CCPPCompileOptions

IR and Machine know no C++, as now.  Text and Syntax know nothing of the target but its macros.  The IDE needs
Text, Syntax and Meaning only: checking is binding without lowering.

The name CPP65 goes from the Meaning layer as its classes are reworked (CCPPType, CCPPClass ...): it serves the
65C64, the W65C816 and the host.  IR65 and IR816 keep theirs.


Measuring
---------

Two things are measured all the way through: the code the compiler writes (does it work, how fast, how big)
and the compiler itself (how long it takes, how much memory).  The code may not get worse without a reason
given in the commit.  The compiler's own time and memory are only watched for now (the user, 2026-11-11): they
are taken at each stage's end and written in Progress, and where a stage's end says they are within the spread,
a miss is written there with its cause and doesn't hold the stage.

What there is already (TestProject65 and the suites):
  - TEST_PROJECT65_CYCLES: each test program's cycles on its emulator.  TEST_SOFT_FLOAT_CYCLES and
    TEST_IR816_RUNTIME_CYCLES: the soft float routines' and the runtime routines'.
  - TEST_PROJECT65_PROFILE and TEST_PROJECT65_PROFILE_REPORT: where a program's cycles go, by function and line.
  - TEST_PROJECT65_COMPILE_STATS: imports missed and stale, units compiled again, header cache hits, lazy
    declarations skipped, loaded and read.
  - TEST_PROJECT65_SERIAL, TEST_PROJECT65_THREADS and TEST_PROJECT65_ONLY=NoSuchTest: a compile alone, on one
    thread (for CPU time) or many (for wall time).
  - TEST_PROJECT65_LISTINGS: every unit's listing, to see what changed.
  - CPP65_PRINT_IR, and VTune on the x64 build (software sampling) for where the compiler's own time goes.

What is missing, and is made in stage 0:
  - The compile's time by phase: preprocess, tokenise, parse, declarations, expressions' types, IR front end,
    inlining, optimiser, back end (writing, and the passes over what is written), assembling, linking.
  - Counters for the things this plan removes, so each stage can show they went: TypeOf calls and those not
    remembered, quiet trials and how many failed, overload resolutions by the way in, pack expansions and the
    nodes they make, Unsupported exits taken (and where), functions whose code CIR65Code refuses, dominators
    worked out, optimiser rounds for each function.
  - Peak memory: the process's, and each workspace allocator's high water mark.
  - Size: each linked program's text and data bytes, and the W65C816's fullest bank.
  - One script that runs the lot and writes one table, so a stage's numbers are taken the same way each time.

How to measure (learned on the compile speed work): CPU questions are measured serially, and old against new
alternately, because other sessions load the machine; wall time only for the parallel build; Release x64; the
old compiler built in a worktree beside the tree so both compile the same sources.

The profile of 2026-11-04 (W65C816 TestSupportLib65, serial, about 100s of CPU) is the picture to check first,
as it says where this plan should pay: generation 56s without assembling, of which the back end 27s
(PeepholeBranches 8.7s, decoding its own text again 6.8s), the optimiser 12.4s (SimplifyCFG 4.8s, full
dominators for RemoveUnreachable 2.1s) and the front end about 12s; parsing about 20s; assembling 15.5s;
preprocessing and tokenising 7.7s.  The type checker has replaced the old expression walk since, so the front
end's share is the first thing to take again.


The order of work
-----------------

Twelve stages, 0 to 11, in the order they are done.  Each says what is done, what is measured before it
starts, and what must be true when it ends.  The plan is run to the end of stage 5, its checkpoint (the
user, 2026-11-11).
Stages 6 to 11 wait: the user comes back then to whether the back ends' code becomes instructions (stage 8) and
whether the 65C64 gets its half of it.  After every stage: the whole proof (below) and a row in Progress at the end of
this file.  Sizes are relative: S, M, L, XL.

Stage 0.  Ground.  (S)

   - TestCppParser.cpp line 268 passes on Windows (the note at the end), so the whole suite runs.  __inline is
     to be a macro on Windows (the user, 2026-11-11), so it is the test that changes: what it expects there is
     "inline".
   - The measuring kit above: the phase times and counters in the compiler behind TEST_PROJECT65_COMPILE_STATS,
     the size and memory figures, and the script.
   - The baseline, written into Progress: the suites' totals; each Lib65 suite's cycles and sizes on both
     processors; the soft float and runtime routines' cycles; compile CPU (serial), wall (parallel) and peak
     memory for the three Lib65 projects on both processors; every counter; the listings kept; and one VTune
     profile of the serial W65C816 TestSupportLib65 compile.
   Ends when: the baseline can be taken again and gives the same numbers (cycles and counters exactly, times
   within what two runs of the same build differ by: that spread is written down too).

Stage 1.  The target is a class.  (S-M)

   CCPPTarget has the sizes SCPPTarget has, and virtual functions for the rest: AddDefines, NewBackend,
   BuildPipeline (at first, the optimiser's settings), GetInlineLimits, AppendStartUp, AppendRuntime, the thunks
   (AppendAdjustThunk, AppendVirtualCallThunk), HasBuiltin, the Libc65 and runtime units a program links, and
   the questions now asked as "is it the W65C816": are zeroed globals bss, are indices narrowed, are units
   compiled again after inlining.  What a back end keeps about a function it wrote (the W65C816's frame) is the
   back end's own, and finishing a function's code (AlignFrame) is a CIRBackend virtual.  The globals become a
   CCPPCompileOptions the builder owns and hands down.  It has a new option: whether speed or size is
   preferred (the user, 2026-11-11: "Start adding an option to prefer speed or size").  Speed is what the
   compiler does today.  Here the option is made, reaches the target, the pipeline and the back ends, and is
   settable from CCPP65Builder, an .hcp65build configuration and hcp65build's command line; its first users are
   the limits that are already numbers: how big a function is inlined (GetInlineLimits) and how many bytes
   memcpy copies in place.  The places that trade one for the other are listed as they are met (multiplies as
   shifts and adds, divisions by constants as multiplies, unswitched and rotated loops, the register entry
   beside each function's stack entry, aligned frames, the table routines) and each is given to the option in
   the stage that reworks it, or in stage 11.  Stage 0's times and counters become a
   CCPPCompileStatistics, one for each unit and added up under the builder's mutex, so they are exact in a
   parallel build too.
   Measure: nothing new before.  The sizes stay fields, not virtual calls: they are read for every type.
   Ends when: CPPT_W65C816 is named only where a target is chosen; preferring speed, the listings are the same
   (this stage only moves code); preferring size, the suites pass and every linked program is smaller or the
   same; compile CPU and memory are within the spread.

Stage 2.  A pass is a class.  (L, mostly moving code)

   Done early because it stands alone in the IR layer, and it gives every later stage its tools: the IR after
   any pass, a wrong pass found by its number, and each pass's time.
   CIRPass has a name and Run.  What passes share is a CIRPassContext: the function, the module, the
   replacements, and the analyses (dominators, loops, liveness, ranges, use counts) worked out when asked for
   and thrown away when a pass says it changed the blocks.  The passes are today's files' groups.  CIRPipeline
   is the list of them, built by the target, in today's order: the W65C816's adds the passes the 65C64 doesn't
   run, and the mb flags go.  The four byte loop idioms share one matcher of the loop's shape.  The longest
   passes are split into finding, checking and rewriting.  The order is not changed here (stage 10).
   Measure before: the optimiser's share of the compile, and how often each analysis is worked out for a
   function.
   Measure after, from the pipeline itself, for each pass on each processor: its time, how many functions it
   ran on, how many it changed, and in which round.  That table goes in Progress: it shows the passes that
   never change anything, those that only do in the first round, and what the rounds after the second cost.
   Ends when: the listings are the same (the order is, and a kept analysis must be the one that would have
   been worked out); the optimiser's time is lower, by about what the repeated dominators cost.

Stage 3.  The C++'s things do their own work.  (M)

   SCPP65Class becomes CCPPClass with FindField, IsDerivedFrom, IsPolymorphic, IsAbstract, NeedsConstructor,
   NeedsDestructor, HasCopyConstructor, IsTriviallyCopyable.  Its bComplete, bLayingOut and bBases are one state
   (declared, bases known, laying out, complete).  Its vtables are a CCPPVtable it owns (the primary, the
   secondaries, their entries and thunks).  CCPPClassLayout lays it out (LayoutClass 170 lines, ClassMember 185,
   the alignment and pack rules).  SCPP65Function becomes CCPPFunction (RequiredParameters, SameParameters,
   Overrides, TakesObject; conversion and operator are kinds, not names to test), SCPP65Variable CCPPVariable,
   SCPP65Template and SCPP65Bindings CCPPTemplate and CCPPTemplateArguments.  Every label is made by
   CCPPMangler.  This is nearly all moving code, and takes about a third of the generator.
   Measure: nothing new; this stage is watched, not profiled.
   Ends when: the listings are the same; compile CPU and memory are within the spread; the generator's
   function count is down by about a hundred.

Stage 4.  The generator's jobs become classes that hold their own state.  (L)

   CCPPOverloads is a set of candidates: add a class's members, a namespace's functions, the arguments'
   namespaces, templates, operators; Choose picks one with the one ranking there is (RankArguments,
   ConversionRank, CompareRanks, QualificationRank); Report says why none matched.  The twelve ways in become
   one.  "int iConstObject = -1" becomes an enum.
   CCPPDeduction is one deduction: the template, the arguments and what is deduced so far are its fields, not
   five parameters.  Matching a specialisation's pattern is a class beside it.
   CCPPDeclarators turns specifiers and declarators into types (GetType, GetDeclaratorType, GetBaseType 160
   lines, GetTypeIdType).
   CCPPContext is where the compiler is: the template arguments, the function, whether there is a this, the
   pack being expanded, and where errors go.  It is entered and left, not saved and restored by hand.  A trial
   (quiet mode) is a context whose errors go to a list that is thrown away; "it failed" is "its list isn't
   empty".
   CCPPUnitData writes the globals, strings, bss and the init and fini tables.
   What is left is CCPPUnit: it owns these, walks the declarations and queues the functions.  No friends.
   Measure before: overload resolutions in a build by each of the twelve ways in, the candidates in each, and
   the same call resolved more than once; quiet trials and how many fail; the front end's time in FindFunction,
   RankArguments and ConversionRank.
   Measure after: the same counts (the same or fewer); what a trial costs, since it now has a list of its
   own (the list is in the context's arena, and a trial that fails must not allocate from the heap).
   Ends when: there is one way in; no member is saved and put back by hand; the suites pass.  The listings may
   differ where two of the old ways in ranked the same call differently: each difference is read, the right
   ranking kept, and a test added.

Stage 5.  A call, a name and a member are resolved once; then the checkpoint.  (L)

   The first half of resolving an expression once (decided 2026-11-11: bound nodes, reached in stages, with a
   checkpoint).  It needs stage 4's context: binding a call has to know where the compiler is.

   CCPPSyntaxVisitor comes first: a virtual for each kind of node, so the binder has no switch on GetKind and
   no casts.  The small questions callers spell out go onto the nodes (an expression without its parentheses,
   a name's template arguments).

   a. Calls.  One ResolveCall holds the cascade.  What it makes is the first bound node, CCPPBoundCall: which
      function and how it is called (directly, through the vtable, through a pointer, a builtin, memcpy in
      place), the object, and its arguments, each with its conversion and the defaults filled in.  A call
      that expands a pack owns its expanded arguments: they are made once for an instance, the syntax tree is
      not rewritten and put back, and the fifty places that read the call node's arguments read the bound
      call's.  The type checker and the IR front end both read it.
   b. Names and members: what an identifier is (a local, a parameter, a global, a field of this, an
      enumerator, a function's address), and which field at which offset.

   While old and new live together a debug check runs both and compares what they chose, over every test and
   the three Lib65 projects.  Where they differ, one of them is wrong today: the binder takes the right one, by
   the standard, and the difference gets a test.

   Measure before: TypeOf calls and those not remembered; the type checker's and the front end's shares of the
   compile (VTune, by class); pack expansions and the nodes they make; which Unsupported exits are ever taken
   in the suites; the lines in the two walkers' call, name and member functions.
   Measure at the checkpoint: the same, and the bound nodes made for a function (the most and the average),
   peak memory, compile CPU, the suites' cycles (a call resolved differently can change them) and the
   disagreements found.
   The checkpoint: the plan stops here and the numbers go to the user.  If the front end's call and member
   functions are short and decide nothing, the suggestion will be that stage 6 goes ahead; if they haven't
   shrunk much, that it is dropped: what is there is the lighter form, and nothing made is wasted.  Memory and
   compile time are part of what is shown, not a condition.  The decision and its numbers go in Progress.

Stage 6.  The rest of an expression is resolved once.  (XL)

   A kind at a time, as stage 5 did calls: operators and conversions; objects (construct, copy, destroy,
   temporaries, and when each is destroyed); new and delete; the rest (about 25 kinds of bound node in all);
   then statements where the binder decides something (declarations, return, switch, range-for).  A bound node
   has its type and whether it is a place, a value or an object in memory.  Every error is found in the
   binder, with its message.

   Then the walkers change their names and their jobs.  CCPPBinder is the type checker grown up.  CCPPLowering
   is the IR front end shrunk: each bound class writes itself as IR (a virtual Lower); it decides nothing, asks
   the unit nothing and can't fail.  TypeOf is the bound node's type, and the map of remembered types goes.  A
   constant is folded once, in the binder.  The warnings are a pass over bound nodes.  Checking for the IDE is
   binding alone, and Find Usages gets what each name resolved to from the same nodes.  A function's bound tree
   lives in the function's arena and is freed when it is lowered.

   Measure after each kind: as at the checkpoint.
   Measure at the end as well: the IDE's check of a solution (CCPPSemanticPass), its time and memory, since
   checking now takes this path; and error messages against stage 0's.
   Ends when: no Unsupported exit is left; the front end never calls TypeOf or asks the unit a question; the
   expression walks are one; compile CPU is lower than stage 0's front end share by about what the second walk
   cost, and peak memory is no higher.

Stage 7.  The back ends are the same parts.  (L)

   One record for each temporary (its place, slot, folded base, offset and index, uses, whether it is in X) in
   place of nine arrays.  CIRW65C816Backend becomes its parts: CIRW65C816Places (PackTemporaries, PlaceTemporaries,
   GroupTemporaries, AllocateX), CIRW65C816Folds, CIRW65C816Fusion, CIRW65C816Calls (PushArguments, LoadRegisterArguments,
   the register stub, Forwarder), CIRW65C816Selector (an IR instruction to machine instructions) and
   CIRW65C816Runtime.  CIR65Backend becomes the same parts with the same names, which finishes the reshaping
   IR65Reshape.txt began.
   Measure before: the back ends' shares of the compile, by function (on 2026-11-04 the W65C816's was nearly
   half of generation).
   Ends when: the listings are the same (this stage only moves code); compile CPU is within the spread.

Stage 8.  The back ends' code is instructions.  (L-XL)

   The selector adds instructions (mnemonic, operand, source position) to the back end's code instead of
   text.  The passes are classes over the instructions, run from a list; nothing is decoded; a source
   position is a field of an instruction; aligning a frame changes operands.  One printer writes the text
   at the end.  The W65C816 first, the 65C64 after.  The passes then see every instruction: today
   CIR65Code gives up on a function with a line it doesn't know, and the passes leave that function as it
   is.  A pass that does one job on both processors is written once over what their instructions share,
   as the branch passes already are (CIRBranchCode).
   Measure before: the time spent turning text into lines and back (IR816Decode, CIRW65C816Code's and CIR65Code's
   Load and Write, CIRSourceMarkers' Take and Put), and how many times a function's code makes the trip; how
   many 65C64 functions CIR65Code refuses, and their share of the suites' cycles (a profile): that is the
   most the 65C64 can gain here.
   Measure after: that time (it should be gone, several seconds of the serial compile); each machine pass's
   time, from the list, as stage 2 gave for the IR's; the suites' cycles and sizes on each processor, as the
   output will change here; the listings read where they differ.
   Ends when: no text is decoded; the suites pass; cycles and size on each processor are no worse, and the
   65C64's are better by some part of what was measured before.

Stage 9.  The builder is four classes.  (M)

   CCPPBuild is what is being built and its options (a struct, in place of Generate's 14 parameters).
   CCPPUnitCompiler is one unit from source to object, with its stage as its state.  CCPPUnitSchedule is the
   turns, the jobs and compiling again.  CCPPProgramLinker is the objects, the libraries, the missing labels'
   stubs, the lazy image and the listings.
   Measure before and after: wall time on 1, 4 and 16 threads; units compiled again, stale and parked; peak
   memory with the jobs running.  A schedule is easy to make slower without making it wrong.
   Ends when: the listings are the same serial and parallel, as now; wall time and memory are within the
   spread on each thread count.

Stage 10.  The parser and the preprocessor.  (M and M)

   The parser: CCPPTokenCursor (where it is, the half '>', Peek, Is, Expect), a tentative parse as an object,
   and the parsing split into declarations, expressions, statements and lazy headers round one shared context.
   ParseStatement (193 lines, 29 ifs) and ParsePrimaryExpression choose by a table from the token.
   The preprocessor: the stack of sources, the macro expander, the directives (a table by name) and the
   includes become classes, and Preprocessor.cpp is split with them.  Its four scanners (PreprocessorTokeniser,
   PreprocessorLineTokeniser, PreprocessorParser, PreprocessorTokenParser) need reading first: I haven't read
   them closely enough to say which should be one.  This is to be done before raw strings (A1 in
   CppParserTodo.txt), which change how lines are read anyway.
   Measure before and after: parsing's and preprocessing's times (about 20s and 8s of 100 on 2026-11-04);
   tentative parses; lazy declarations skipped, loaded and read; header cache hits; tokens preprocessed; the
   syntax trees' memory.  The highlighter's and the index's times on the IDE's solution, as they read the
   same tree.
   Ends when: the syntax tree is the same node for node (the syntax blocks' dump compares it); the counts are
   the same; the times are within the spread.

Stage 11.  Faster code, with what has been built.  (as long as it is worth it)

   Not reshaping: this is where "ideally faster" is spent, and each change is one commit with its cycles and
   sizes.
   - The pipeline's order, for each target, from stage 2's table: a pass that only tidies after another run
     straight after it; passes that never change anything dropped or moved; fewer rounds if the later ones
     do little.
   - The W65C816's passes tried on the 65C64 and the other way (constant divisions, narrowed counters and
     multiplies, biased indices; the machine passes of stage 8).
   - What the suites' profiles (TEST_PROJECT65_PROFILE_REPORT) show is hot and badly written.
   - The rest of the places that trade speed for size given to the option.
   Measure: the suites' cycles and sizes on both processors and the soft float count, before and after each
   change, preferring speed and preferring size, and the compile's time, as a pass costs time for every
   function.
   Ends when the user says it does.


How a stage is proved
---------------------

That the code works is proved by running it, not by comparing it:
  - Release x64 builds with no warnings and TestCppCompilerLib passes.
  - TestBaseLib65, TestStandardLib65, TestSupportLib65 and TestLibc65 pass on both processors: they compile the
    libraries' own tests and run them on the emulators, which is the widest check there is that compiled code
    does what the C++ says.  TestHCP65Lib (the kernal and drivers) at the end of each stage.
  - Error messages and their positions don't get worse (TestCppErrors and the CPP65 error tests).  Stages 5
    and 6 move where errors are found, so this matters most there.

That it is no slower is measured for each commit that changes what is written, and the numbers go in the
commit: the Lib65 suites' cycles and the soft float cycle count on each processor, and the size of the linked
programs (the W65C816's banks and a ROM's kernal are tight).  Preferring speed, a commit may not make code
slower; preferring size, it may not make it bigger; one that does says why it is worth it, or isn't made.
From stage 1 the suites are run preferring size as well at each stage's end.

The compiler's own time and memory are measured at the end of each stage, and inside a stage whenever a commit
touches something the profile says is hot.  They are watched, not a gate.

The listings (TEST_PROJECT65_LISTINGS, compared section by section with local labels renumbered) are still the
quickest way to see what a commit changed.  Stages 1, 2, 3, 7, 9 and 10 only move code and should change none;
when one does, the difference is read before it is accepted: it is either a bug or something to say in the
commit.  They are a way of looking, not a gate.

Some tests expect exact assembly (TestIR65Backend, TestIR816Backend, TestCPP816Assembly, TestCPP65IR,
TestCPP65ListingIndex).  When the output changes on purpose their expected text is read and updated in the same
commit; a test that only pinned the old text, and not something the code must do, is changed to check what it
does (its result, its cycles, that a call became a jump).

A class that can be tested alone gets tests of its own when it is made: CCPPOverloads, CCPPDeduction,
CCPPClassLayout, CCPPBoundCall's resolution, the back ends' printers and CIRPipeline.  A commit that moves code
and one that changes what is written are still better apart, so that when a suite fails it is clear which kind
did it.


What this makes easier
----------------------

The C++14 list (CppParserTodo.txt section 6) is mostly work in the Meaning layer, so stages 1 to 6 are better
done before it: overload resolution to the standard (B8) is CCPPOverloads; rvalue references (B10) are a bound
node's kind of value; auto and decltype (B11) are a bound node's type; a lambda (B12) is a CCPPClass the binder
makes; constexpr (B13) is evaluating bound nodes or IR; more kinds of pack expansion (B14) have the bound call's
argument list to go into; range-for (B16) is a bound statement.


Decisions
---------

Made by the user, 2026-11-11:
  - The assembly may change; it must work and ideally be faster.
  - Resolving an expression once: bound nodes, reached in stages, with a checkpoint after calls, names and
    members.
  - The plan is run to the end of stage 5.  Then the user comes back to stage 8's question (the back ends'
    code as instructions, or stop at stage 7) and to whether the 65C64 gets its half of it.
  - __inline is a macro on Windows, so TestCppParser.cpp line 268's expected text is what changes.
  - CPP65 becomes CPP in the Meaning layer's names as its classes are reworked.
  - The compiler's own time and memory are only watched for now, not a gate.
  - Speed against size is an option, not a rule: stage 1 starts it.
  - Stages 3 to 6 have the generator, the type checker and the IR front end to themselves: there is no other
    session in them.

For the user, when stage 5 is done:
  - Stage 6: the rest of an expression as bound nodes, on the checkpoint's numbers.
  - Stage 8: the back ends' code as instructions, and the 65C64's half of it.
  - Whether the compiler's own time and memory become a gate.


Left alone

The syntax node classes (already a class each), CIRModule, CIRFunction and CIRBlock, the syntax block disk
format, the highlighter and the index, CIRParser, CIRPrinter and CIRVerifier, and JavaParserLib.  No new C++.

  - Parsing is the biggest single phase on both processors, and the passes over the code the back ends wrote
    (decoding their own text) are next: more than the optimiser, the front end and the types together.
  - A quarter of TypeOf's calls work the type out; the rest are remembered.  A unit makes 1.7 million quiet
    trials on the W65C816, of which 128 fail: nearly all of quiet mode's uses are not trials of anything that
    can fail.
  - Dominators were worked out 37 times for each function optimised (12 since 7134b3000).
  - The 65C64's passes refused 34 functions' code out of 121,235: there was almost nothing for stage 8 to win
    for the 65C64 by reading every function.
  - No Unsupported exit is taken in a build that succeeds: they are all errors.
