CppCompilerLib: consolidation plan
==================================

How the compiler is to be reshaped from five very large classes, full of special cases, into small classes that
each do one job.  Written 2026-11-11, from reading the code and measuring it; nothing here is started.  The library
was CppParserLib until that day.

The rule for every step (the user, 2026-11-11): the code the compiler writes must work, and ideally is faster.
It does not have to be the assembly written before.  So a step is free to take the simpler design where the old
one's special cases were only there to be kept, and to let one way of doing a thing replace two that differed.
A step doesn't add C++ features.


Where it is now
---------------

491 files, 127,000 lines, 3,319 functions.  368 functions are over 50 lines and 101 are over 100.  In the table
the lines are those inside the class's functions.

	Class                Functions   Lines   ifs   What it is
	CCPP65Generator         314      8,909   865   Everything about the C++: 65 fields, 3 friend classes
	CIROptimiser            173      8,438   782   Every pass, 29 fields, the order written out in Optimise
	CIR816Backend           158      6,137   492   Frame, places, instructions, calls, peepholes, runtime
	CCPP65IRFrontEnd        187      5,811   624   Function bodies to IR
	CCPPParser              159      5,496   619   The parser
	CIR65Backend            131      3,484   325   The 65C64's, 30 fields
	CPreprocessor           101      3,174   285   Preprocessor.cpp is 3,557 lines and was never split
	CCPP65TypeChecker        70      2,103   291   Expressions' types
	CCPP65Builder            98      1,296    81   Project, scheduling, linking, listings

The clean-up of 2026-11-04 and 05 split the big files by subject.  The classes were not split: each is still one
class with all its state shared between all its functions, spread over ten files.  That is what is left to do.


What makes the special cases
----------------------------

1. Every decision about an expression is made twice, and some three or four times.

   CCPP65TypeChecker and CCPP65IRFrontEnd walk an expression side by side: 44 of their functions have the same
   name (CallExpression, MemberCall, Construct, Convert, Operate ...).  Each one works out again what the other
   already knew.  CallExpression is the worst: a cascade of a dozen tests (pack expansion, member expression,
   member pointer, qualified by a class, function template, member of this, memcpy, builtin, associated
   namespaces, function pointer, named function) is written out in both, and not in the same order: the checker
   tries a function template before a member and the front end a builtin before a template.  A new special case
   has to be added to both, in the right place in each.  The front end has 165 "Unsupported(__FILE__, __LINE__)"
   exits for things the checker should have settled, asks the generator 285 questions (mpcGenerator->) and calls
   TypeOf again 29 times.  Constant (234 lines) is a third walk, the warnings a fourth, CPP65GeneratorCheck a
   fifth.

2. The C++'s things are structs, and all they can do is in the generator.

   SCPP65Class has 8 flags, SCPP65Function 13, SCPP65Template 4.  Anything asked of one is a generator function
   that takes it as its first argument: IsPolymorphic(psClass), NeedsDestructor(psClass), FindField(psClass, ...),
   AppendClassLabel(psz, psClass, ...).  So the generator has 314 functions and three friends.  A call is resolved
   through twelve ways in (FindFunction, FindNamedFunction, FindAddressedFunction, FindAssociatedFunction,
   FindOperator, FindFreeOperator, FindStaticFunction, FindConversion, FindMemberTemplate, ChooseMemberTemplate,
   ChooseTemplate, GetCallTemplate).  Nine Deduce functions hand the same five arguments to each other.

3. Where the compiler is, is kept in members that are saved and put back by hand.

   mpsBindings is set at 25 places, quiet mode (BeginQuiet, EndQuiet, miQuiet, mbQuietFailed) is
   at 116, and mpsFunction, mbThis, mbStaticLocal, mbCLinkage and mpcPackParameter are the same kind.  A
   function's answer depends on members its arguments don't show.

4. The target is an enum, tested where it matters.

   SCPPTarget has eight numbers.  The rest of what differs between the processors is about 30 tests of
   CPPT_W65C816 in eight files (ten in the builder), InitOptimiser's seven "bW65C816 ?" settings, pairs of
   IR65_INLINE_ and IR816_INLINE_ #defines, szW65C816Only on a builtin, the W65C816's frame in a struct the
   shared front end keeps, and globals: gbIR816RegisterArguments, gbIR816SoftFloatInFrame, gbW65C816Assembly,
   CIR816Backend's static scratch allocator and nine statics on CCPP65IRFrontEnd ("only exact when the units
   are compiled one at a time").

5. Kinds are told apart with GetKind and a cast.

   233 GetKind tests and 333 casts to a syntax class.  The syntax nodes are classes (85
   files) but all they do is print themselves and list their fields.

6. The back ends write text and read it back.

   About 300 places append assembly as text.  The passes after them need to know what a line is, so CIR816Code
   and CIR65Code decode the text again; source positions travel as marker bytes that are taken out and put back
   (CIRSourceMarkers); AlignFrame (254 lines) edits the text a third time.  CIR816Backend has nine passes each
   declared twice (for a CChars and for a CIR816Code), and nine arrays indexed by temporary.

7. The optimiser's passes are functions of one class.

   Optimise calls 32 of them in a row, some behind flags the target set (mbConstantDivisions && ...).  Four
   idiom passes (ReplaceStrchr 211 lines, ReplaceStrlen 146, ReplaceMemchr 129, ReplaceMemcmp 122) each match
   a byte loop for themselves.  ConstantDivisions, ReplaceStrchr and ReplaceStrlen nest eight deep.


The shape to reach
------------------

Eight layers.  A layer uses the ones above it in this list and nothing below.  (CCPPTarget is what the layers
see; the 65C64's and the W65C816's own classes make their back ends and pipelines, so they sit with Machine.)

	Target     CCPPTarget: CCPPTarget65C64, CCPPTargetW65C816, CCPPTargetHost
	Text       CPreprocessor (sources, macro expander, directives, includes), CCPPTokeniser
	Syntax     CCPPParser, the CCPPSyntax classes, CCPPScope, CCPPSymbol, CCPPSyntaxVisitor
	Meaning    CCPPUnit, CCPPTypes, CCPPClass, CCPPFunction, CCPPVariable, CCPPTemplate
	           CCPPBinder, which makes CCPPBound nodes: an expression typed and resolved
	           CCPPOverloads, CCPPDeduction, CCPPDeclarators, CCPPMangler, CCPPWarnings
	Lowering   CCPPLowering (bound nodes to IR), CCPPUnitData (globals, strings, vtables, start up tables)
	IR         CIRModule, CIRFunction; CIRPass and the passes, CIRPipeline; CIRInliner, CIRInterprocedural
	Machine    CIRBackend: CIR65Backend and CIR816Backend, each a frame, places, a selector, calls, its code as
	           instructions, passes over them and a printer
	Build      CCPPBuild, CCPPUnitCompiler, CCPPUnitSchedule, CCPPProgramLinker, CCPPCompileOptions

IR and Machine know no C++, as now.  Text and Syntax know nothing of the target but its macros.  The IDE needs
Text, Syntax and Meaning only: checking is binding without lowering.

The name CPP65 goes from the Meaning layer as its classes are reworked (CCPPType, CCPPClass ...): it serves the
65C64, the W65C816 and the host.  IR65 and IR816 keep theirs.


The steps
---------

Step 1 comes first because everything reads the target.  Steps 2, 3 and 4 are in order.  Steps 5, 6, 7 and 8
don't depend on them or on each other, and can be done between them.  Sizes are relative: S, M, L, XL.

1. The target is a class.  (S-M)

   CCPPTarget has the sizes SCPPTarget has, and virtual functions for the rest: AddDefines, NewBackend,
   BuildPipeline (at first, the optimiser's settings), GetInlineLimits, AppendStartUp, AppendRuntime, the thunks
   (AppendAdjustThunk, AppendVirtualCallThunk), HasBuiltin, the Libc65 and runtime units a program links, and
   the questions now asked as "is it the W65C816": are zeroed globals bss, are indices narrowed, are units
   compiled again after inlining.  What a back end keeps about a function it wrote (the W65C816's frame) is the
   back end's own, and finishing a function's code (AlignFrame) is a CIRBackend virtual.  The globals become a
   CCPPCompileOptions the builder owns and hands down, and the counters a statistics object it adds up under its
   mutex.  When it is done CPPT_W65C816 is named only where a target is chosen.

2. The C++'s things do their own work.  (M)

   SCPP65Class becomes CCPPClass with FindField, IsDerivedFrom, IsPolymorphic, IsAbstract, NeedsConstructor,
   NeedsDestructor, HasCopyConstructor, IsTriviallyCopyable.  Its bComplete, bLayingOut and bBases are one state
   (declared, bases known, laying out, complete).  Its vtables are a CCPPVtable it owns (the primary, the
   secondaries, their entries and thunks).  CCPPClassLayout lays it out (LayoutClass 170 lines, ClassMember 185,
   the alignment and pack rules).  SCPP65Function becomes CCPPFunction (RequiredParameters, SameParameters,
   Overrides, TakesObject; conversion and operator are kinds, not names to test), SCPP65Variable CCPPVariable,
   SCPP65Template and SCPP65Bindings CCPPTemplate and CCPPTemplateArguments.  Every label is made by
   CCPPMangler.  This is nearly all moving code, and takes about a third of the generator.

3. The generator's jobs become classes that hold their own state.  (L)

   CCPPOverloads is a set of candidates: add a class's members, a namespace's functions, the arguments'
   namespaces, templates, operators; Choose picks one with the one ranking there is (RankArguments,
   ConversionRank, CompareRanks, QualificationRank); Report says why none matched.  The twelve ways in become
   one.  "int iConstObject = -1" becomes an enum.
   CCPPDeduction is one deduction: the template, the arguments and what is deduced so far are its fields, not
   five parameters.  Matching a specialisation's pattern is a class beside it.
   CCPPDeclarators turns specifiers and declarators into types (GetType, GetDeclaratorType, GetBaseType 160
   lines, GetTypeIdType).
   CCPPContext is where the compiler is: the template arguments, the function, whether there is a this, the
   pack being expanded, and where errors go.  It is entered and left, not saved and restored by hand.  A trial
   (quiet mode) is a context whose errors go to a list that is thrown away; "it failed" is "its list isn't
   empty".
   CCPPUnitData writes the globals, strings, bss and the init and fini tables.
   What is left is CCPPUnit: it owns these, walks the declarations and queues the functions.  No friends.

4. An expression is resolved once.  (XL: the heart of the plan)

   CCPPBinder is the type checker grown up.  For an expression it makes a tree of CCPPBound nodes.  A bound
   node has its type, whether it is a place, a value or an object in memory, and everything that was decided:
   which function a call calls and how (directly, through the vtable, through a pointer), each argument with
   its conversion and the defaults filled in, which builtin, which field at which offset, which constructor,
   which temporaries are made and when they are destroyed.  There are about 25 kinds (constant, variable, field,
   load, assign, unary, binary, compare, logical, conditional, convert, call, builtin, construct, temporary,
   destroy, new, delete, dynamic cast, function address ...).  Every error is found here, with its message.

   CCPPLowering is the IR front end shrunk.  Each bound class writes itself as IR (a virtual Lower).  It
   decides nothing, asks the unit nothing, and can't fail: the 165 Unsupported exits go.

   Then: TypeOf is the bound node's type, and the map of remembered types goes.  A constant is folded once,
   in the binder.  The warnings are a pass over bound nodes.  Checking for the IDE is binding alone, and Find
   Usages gets what each name resolved to from the same nodes.  A function's bound tree lives in the
   function's arena and is freed when it is lowered, so only one function's is in memory at a time.

   It is done a kind of expression at a time, calls first because they repeat the most: the binder makes the
   kind's bound node; the front end's function for that kind is rewritten to take it; the checker's old
   cascade for it is deleted.  While the two ways live together a kind not yet moved is a bound node that only
   has its type.  Before an old cascade is deleted, a debug check runs both and compares what they chose over
   every test and all three Lib65 projects.  Where they differ, one of them is wrong today: the binder takes
   the right one, by the standard, and the difference gets a test.
   Order: calls; members and places; operators and conversions; objects (construct, copy, destroy,
   temporaries); new and delete; the rest; then statements where the binder decides something (declarations,
   return, switch, range-for).

   CCPPSyntaxVisitor comes in at the start of this step: a virtual for each kind of node, so the binder has no
   switch on GetKind and no casts.  The small questions callers spell out go onto the nodes (an expression
   without its parentheses, a name's template arguments).

5. The back ends are the same parts, and their code is instructions.  (L, then L-XL)

   a. One record for each temporary (its place, slot, folded base, offset and index, uses, whether it is in X)
      in place of nine arrays.  CIR816Backend becomes its parts: CIR816Places (PackTemporaries, PlaceTemporaries,
      GroupTemporaries, AllocateX), CIR816Folds, CIR816Fusion, CIR816Calls (PushArguments, LoadRegisterArguments,
      the register stub, Forwarder), CIR816Selector (an IR instruction to machine instructions) and
      CIR816Runtime.  CIR65Backend becomes the same parts with the same names, which finishes the reshaping
      IR65Reshape.txt began.
   b. The selector adds instructions (mnemonic, operand, source position) to the back end's code instead of
      text.  The passes are classes over the instructions, run from a list; nothing is decoded; a source
      position is a field of an instruction; aligning a frame changes operands.  One printer writes the text
      at the end.  The W65C816 first, the 65C64 after.  The passes then see every instruction: today
      CIR65Code gives up on a function with a line it doesn't know, and the passes leave that function as it
      is.  A pass that does one job on both processors is written once over what their instructions share,
      as the branch passes already are (CIRBranchCode).

6. A pass is a class.  (L, mostly moving code)

   CIRPass has a name and Run.  What passes share is a CIRPassContext: the function, the module, the
   replacements, and the analyses (dominators, loops, liveness, ranges, use counts) worked out when asked for
   and thrown away when a pass says it changed the blocks.  The passes are today's files' groups.  CIRPipeline
   is the list of them, built by the target: the W65C816's adds the passes the 65C64 doesn't run, and the mb
   flags go.  It starts as today's order.  After that the order is the target's to change, a change at a
   time with its cycles measured: passes the 65C64 never ran can be tried on it, and a pass that only tidies
   after another can run straight after it instead of a round later.  A list also gives printing the IR after
   any pass, finding a wrong pass by its number, and each pass's time.  The four byte loop idioms share one
   matcher of the loop's shape.  The longest passes are split into finding, checking and rewriting.

7. The builder is four classes.  (M)

   CCPPBuild is what is being built and its options (a struct, in place of Generate's 14 parameters).
   CCPPUnitCompiler is one unit from source to object, with its stage as its state.  CCPPUnitSchedule is the
   turns, the jobs and compiling again.  CCPPProgramLinker is the objects, the libraries, the missing labels'
   stubs, the lazy image and the listings.

8. The parser and the preprocessor.  (M and M)

   The parser: CCPPTokenCursor (where it is, the half '>', Peek, Is, Expect), a tentative parse as an object,
   and the parsing split into declarations, expressions, statements and lazy headers round one shared context.
   ParseStatement (193 lines, 29 ifs) and ParsePrimaryExpression choose by a table from the token.
   The preprocessor: the stack of sources, the macro expander, the directives (a table by name) and the
   includes become classes, and Preprocessor.cpp is split with them.  Its four scanners (PreprocessorTokeniser,
   PreprocessorLineTokeniser, PreprocessorParser, PreprocessorTokenParser) need reading first: I haven't read
   them closely enough to say which should be one.  This is to be done before raw strings (A1 in
   CppParserTodo.txt), which change how lines are read anyway.


How a step is proved
--------------------

Before anything: TestCppCompilerLib must pass.  On Windows it stops today at TestCppParser.cpp line 268 (see the
note at the end), so nothing after TestCppParser is run.

That the code works is proved by running it, not by comparing it:
  - Release x64 builds with no warnings and TestCppCompilerLib passes.
  - TestBaseLib65, TestStandardLib65, TestSupportLib65 and TestLibc65 pass on both processors: they compile the
    libraries' own tests and run them on the emulators, which is the widest check there is that compiled code
    does what the C++ says.  TestHCP65Lib (the kernal and drivers) at the end of each step.
  - Error messages and their positions don't get worse (TestCppErrors and the CPP65 error tests).  Step 4 moves
    where errors are found, so this matters most there.

That it is no slower is measured for each commit that changes what is written, and the numbers go in the
commit: the Lib65 suites' cycles and the soft float cycle count on each processor, and the size of the linked
programs (the W65C816's banks and a ROM's kernal are tight).  A commit that makes something slower or bigger
says why it is worth it, or isn't made.

The listings (TEST_PROJECT65_LISTINGS, compared section by section with local labels renumbered) are still the
quickest way to see what a commit changed.  A commit meant only to move code should change none, and when one
does the difference is read before it is accepted: it is either a bug or something to say in the commit.  They
are a way of looking, not a gate.

Some tests expect exact assembly (TestIR65Backend, TestIR816Backend, TestCPP816Assembly, TestCPP65IR,
TestCPP65ListingIndex).  When the output changes on purpose their expected text is read and updated in the same
commit; a test that only pinned the old text, and not something the code must do, is changed to check what it
does (its result, its cycles, that a call became a jump).

A class that can be tested alone gets tests of its own when it is made: CCPPOverloads, CCPPDeduction,
CCPPClassLayout, the back ends' printers and CIRPipeline.  A commit that moves code and one that changes what is
written are still better apart, so that when a suite fails it is clear which kind did it.


What this makes easier
----------------------

The C++14 list (CppParserTodo.txt section 6) is mostly work in the Meaning layer, so steps 1 to 4 are better
done before it: overload resolution to the standard (B8) is CCPPOverloads; rvalue references (B10) are a bound
node's kind of value; auto and decltype (B11) are a bound node's type; a lambda (B12) is a CCPPClass the binder
makes; constexpr (B13) is evaluating bound nodes or IR; range-for (B16) is a bound statement.


Decisions for the user
----------------------

  - Step 4: bound nodes, as above (suggested), or a lighter form: the two walkers stay and share a record of
    what was resolved, kept on the syntax node.  The lighter form removes the repeated cascades but keeps both
    walks and the front end's Unsupported exits.
  - Step 5b: the back ends' code as instructions (suggested), or stop at 5a.  With the output free to change it
    is no longer the risky step it was: the printer doesn't have to write today's text, only text that
    assembles to code that passes the suites.
  - CPP65 to CPP in the Meaning layer's names as classes are reworked (suggested), or the names stay.


Left alone
----------

The syntax node classes (already a class each), CIRModule, CIRFunction and CIRBlock, the syntax block disk
format, the highlighter and the index, CIRParser, CIRPrinter and CIRVerifier, and JavaParserLib.  No new C++.
Faster code is welcome where a step's simpler design gives it, and is measured; it isn't what a step is for.
