W65C816 alignment plan
======================

Written 2026-11-22 for the session that builds it, and built the same day (the user: "Complete the entire plan.
Clean up and commit with no co-author as you go.  Keep a list of questions for me as necessary and make sure the code
remains DRY and elegant.").  Sections 1 to 5 are the plan as it was written, for the record; section 6 is what was
built, 7 the count and the survey, 8 step 10's measurement, 9 the questions kept for the user and 10 the user's
answers and what was done about each.


1. What the user decided (2026-11-22)
-------------------------------------

In order, the user's own words:
  - "Make every type's alignment 1 on the W65C816; chat about this.  The 816 doesn't care from the point of view that
    there is no cost to access 1 byte aligned data but there is a cost to acces 1 byte of data if the 816's memory is
    in 16 bit mode"
  - "We're aiming for speed so I'm happy to keep padding structs to two bytes but alignment can stay at 1 byte."
  - "Plan capping the padding at 2 bytes and making the alignof 1."

So, on the W65C816 only (the 65C64 doesn't change at all):
  a. alignof of every type is 1: char, int, long, long long, float, double, pointers, references, member pointers,
     enums, arrays, classes.  alignas still asks for more and gets it: alignof of a class (or variable) with alignas
     is what alignas asked.  alignas(type) is alignof(type), so alignas(long) is 1 there.
  b. A class's members are padded to at most 2: a member of 2 or more bytes (or a class member containing one) goes
     at an even offset; a char-sized one anywhere; a class with an even-aligned member is a whole number of 2 bytes.
     Today 4 byte things go to multiples of 4 and 8 byte things to multiples of 8.  This is a default #pragma pack(2)
     for the target.  #pragma pack(n) only ever lowers alignment, so a member goes at a multiple of the least of its
     type's alignment, 2 and n: pack(1) still packs to 1, pack(4) and pack(8) change nothing.  A class's alignas
     still raises its own alignment past the cap (as it does past #pragma pack today: "It is kept whatever #pragma
     pack says, as MSVC does").
  c. Globals and statics are placed by alignof (so byte aligned) unless alignas says more.  Locals already are: the
     816's frame alignment is 1 (CCPPTargetW65C816::GetFrameAlignment).

Why (from the discussion, for anyone asking):
  - The 65816 has an 8 bit data bus: a 16 bit access is two bus cycles at any address, odd or even.  The only
    address penalty is a cycle per direct page access when D's low byte isn't 0, which is about D, not alignment.
    So byte alignment costs nothing to access.
  - Cpp14CompliancePlan.txt B 7 (open until this is built): a local's place in a 816 frame is D + offset with D
    wherever S was, so today (uintptr_t)&i % alignof(int) can be 1, which C++ doesn't allow.  With alignof 1 that is
    correct, with no cost to any call.  The other choices offered, and not taken: align some or all frames (about
    10 cycles a call), make padding 1 too (smaller structs, no 16 bit store trick), or leave it.
  - The padding is kept for speed: a char followed by a padding byte can be stored with a 16 bit sta (the padding
    takes the junk), instead of sep/lda/sta/rep, which costs 6 cycles more.  The compiler doesn't do that yet; step 10
    only measures what it would save, for the user to decide.

3. The facts, as of 2026-11-22
------------------------------

Today on the W65C816 (measured with TEST_CPP_CONFORMANCE_TRY):
  alignof(int) 2, alignof(long) 4, a pointer 4, long long and double 8; struct { char c; int i; } is 4 bytes;
  struct { char c; int i; char d; } is 6 with i at 2 and d at 4.
  A byte store is written as sep m / lda / sta / rep m (look at a listing: TEST_CPP_CONFORMANCE_LISTINGS=<dir>).

Where alignment comes from (CommonLibraries/Libraries/CppCompilerLib):
  CPPClassLayout.cpp
    CCPPClassLayout::TypeAlignment (line ~71), static and the same for both targets: a class's miAlign, an array's
      element's, 4 for a pointer, reference or member pointer, 8 for 8+ bytes, 4 for 4+, else the size.
    CCPPClassLayout::PackAlignment(iAlign, iPack) (~57): the alignment limited by #pragma pack (0 = none).
    CCPPClassLayout::Init(pcClass, iPack, iPointerBytes) (~28); Align (~103) moves to a multiple and raises miAlign.
    Every placement goes through PackAlignment(x, miPack): bases (~220), virtual bases (~293), the vtable pointer
      (~319), fields (~343), bit-field units (~384).  Layout (~117) applies the class's alignas (iClassAlign) after,
      rounds the size to miAlign, and stores mpcClass->miAlign and miAlignas.
  CPPUnitClasses.cpp
    CCPPUnit::LayoutClass calls cLayout.Init(pcClass, pcSpecifier->miPack, mpcTarget->GetPointerBytes()) (~1008):
      the one place classes are laid out.
    CCPPUnit::VariableAlignment (~216): a variable's alignment, TypeAlignment of its type or more for alignas;
      used for globals and statics (CPPUnit.cpp ~1213) and locals with alignas (CPP65IRFrontEnd.cpp ~1699).
    CCPPUnit::AlignasAlignment (~251): alignas(n) and alignas(type), which uses TypeAlignment (~276).
  CPPUnitExpressions.cpp ~2928: alignof is TypeAlignment.
  CPPClass.h: CCPPClass::miAlign (the class's alignment, used to place it as a member or base) and miAlignas.
  CPPTarget.h: CCPPTarget (GetPointerBytes, GetFrameAlignment ...); CPPTargetW65C816 and CPPTarget65C64 override.
  __STDCPP_DEFAULT_NEW_ALIGNMENT__ is defined per target (CPPTargetW65C816.cpp ~145, 8UL); it is C++17's, and left.
  Libc65's stddef.h: typedef long long max_align_t; so alignof(max_align_t) becomes 1 on the 816 by itself.

What may depend on the 816's layouts (looked at so far; step 3 finds the rest):
  - BaseLib's FAT classes: the FAT assembly (BaseLib/Fat*W65C816.asm) takes their offsets from
    BaseLib/FatW65C816.inc, which TestBaseLib65 generates with the 816 compiler (Tests/TestBaseLib65/TestBaseLib65/
    TestFatW65C816Layout.cpp, writing Output/<target>/FatW65C816.inc).  After the change, copy the new one over
    BaseLib's and read the assembly that uses what moved.  The assembly's F_* frame constants are its own.
  - SKernalInterrupt (HCP65/Kernal/KernalInterrupts.h; KernalInterrupts.asm reads it by offset, 16 bytes a slot):
    4, 4, 4, 2, 2 bytes, so unchanged.
  - HCP65/Libraries/UserLib/HCP65SFT.h's records (SSFTHeader, SSFTImage, SSFTContainer, SSFTPalette), written by
    host tools and read on the 816: unchanged (SSFTPalette's uint32 is at 8 either way).
  - BaseLib's SChunkFileHeader: unchanged.
  - There are 29 hand written .asm files (HCP65: Boot, Kernal, Drivers, Libc65, UserLib; BaseLib's FAT).  Only the
    FAT ones and KernalInterrupts.asm were looked at.


4. Steps
--------

Step 1. The change, behind a switch that is off.
  CCPPTarget gains:
    virtual int  GetMemberAlignmentLimit(void);   0 (no limit) by default; 2 for the W65C816.
    virtual bool IsByteAligned(void);             false by default; true for the W65C816 (alignof is 1).
  For the survey both read a switch (an environment variable, CPP65_ALIGN_816 say, or a CCPPCompileOptions member)
  that is off: off, everything is as today.
  - Layout: LayoutClass passes the pack and the limit together: the least of the #pragma pack (if any) and the limit
    (if any), into CCPPClassLayout::Init as its iPack.  Nothing else in CCPPClassLayout changes: every placement
    already goes through PackAlignment, a class's miAlign comes out at most 2, and a class's alignas still raises it.
  - The object's alignment: a new CCPPUnit (or CCPPClassLayout, given the target) function, ObjectAlignment(type):
    on a byte aligned target, the type's alignas (CCPPClassLayout::TypeAlignas, the class's miAlignas) or 1; else
    TypeAlignment as now.  alignof (CPPUnitExpressions ~2928), alignas(type) (AlignasAlignment ~276) and
    VariableAlignment (~224) use it instead of TypeAlignment.  The layout keeps using TypeAlignment (capped).
  - The semantic pass (the IDE's checker) checks with the same target object, so it says the same; nothing more.
  - A dump for step 2: another switch (CPP65_DUMP_LAYOUTS=<file>) appends, for each class laid out, one line:
    its qualified name, the source file, its size, alignment, and each field's offset (and each base's).  Builds run
    units on threads, so write it under a mutex (or one file per process, joined after).

Step 2. The count.  With the dump on, compile every W65C816 build twice, the switch off and on, and compare:
  - TestBaseLib65, TestStandardLib65 and TestSupportLib65 (their *65 programs compile the libraries for both targets:
    TEST_PROJECT65_ONLY=NoSuchTest compiles without running the tests);
  - TestLibc65;
  - the twenty HCP65 projects (hcp65build <project>.hcp65build -config "Release|W65C816").
  Sort and diff the two dumps: the classes whose 816 layout changes, each once, with where it is declared.

Step 3. The survey, from that list.  For each class that changes, does anything outside the compiler assume its
  layout?
  - hand written assembly: the 29 .asm files and any .inc of offsets (grep the asm for the class's member names and
    for numbers that look like offsets; the FAT .inc is generated, see above);
  - bytes that leave the 816 or arrive as bytes: files written from a struct's memory and read by a host tool or the
    emulator, or the other way; SD card structures; the executable format; host code that reads 816 memory at fixed
    offsets (HCP65-Emulator, HCP65Lib, HCP65-IDE's debugger);
  - static_asserts and tests of sizes or offsets on the 816 (TestCPP816*, TestCPPW65C816*, TestCPP65*, the *65
    library tests, TestLibc65).
  Write the list, with what each needs, into this file, and show it to the user (one question at a time if any
  decision is theirs).  Don't go on until they've seen it.

Step 4. Turn it on: the switch's default becomes on for the W65C816 (or the switch goes, the target just answers).
  The 65C64 is unchanged.

Step 5. Fix what step 3 found.  Each fix gets a test that fails if the two sides drift apart again, as
  TestFatW65C816Layout does for the FAT classes.  Regenerate FatW65C816.inc (copy TestBaseLib65's
  Output/W65C816/FatW65C816.inc over BaseLib's) and read every FAT .asm use of a member that moved.

Step 6. Tests.
  - TestCPPW65C816 (or a new TestCPPW65C816Alignment.cpp; a new source file goes in CppCompilerLib's and the test's
    .vcxproj and .filters, which keep CRLF line endings): on the 816,
      struct { char c; long l; } is 6 bytes with l at 2 (8 with l at 4 on the 65C64);
      struct { char c; } is 1; struct { char a; short b; char c; } is 6; struct { char c; double d; } is 10;
      alignof(int), alignof(long), alignof(double), alignof(void*) and alignof of a class are 1;
      alignas(8) on a class and on a variable still gives 8 (and an 8-aligned address for a global and a local);
      #pragma pack(1) still packs to 1; pack(4) changes nothing;
      a class member containing a long is placed at an even offset;
      bit-fields as before but capped;
    and the same source on the 65C64 unchanged.
  - Conformance: its cases give the same result on both targets and the host, so they compare sizes with sizeof,
    never numbers.  Run them all; look at any that compare an alignment with a number or assume alignof(T) ==
    sizeof(T) (BasicAlignment, BasicAlignasObjects, AlignofRules, SizeofRules, the clause 3 [basic.align] cases):
    such a case is target dependent and must be written so it holds on both (g++ checked, -m32 and -m64).  Add a case
    that a local int's address is a multiple of alignof(int) on both targets (it is, trivially, on the 816).
  - TestCPP65Declarations' counts (class layouts, quiet trials) are unchanged: the change adds no work.

Step 7. Docs: HCP65/Website/docs/compiler/language.md says what the W65C816's alignment and layout are (alignof 1,
  members at most 2, alignas honoured); Cpp14CompliancePlan.txt B 7 is marked done.

Step 8. Verify, as Cpp14CompliancePlan.txt "How a change is checked" says: the whole of TestCppCompilerLib, the
  conformance lists, the three *65 library tests on both targets, TestLibc65, the twenty HCP65 projects; and, if

Step 9. Clean up the switch if it is no longer wanted, and the dump if it isn't worth keeping (ask: a layout dump may

6. What was built (2026-11-22)
------------------------------

The compiler (the whole change is about 110 lines):
  - CCPPTarget::GetObjectAlignmentLimit: the most an object is aligned to unless alignas asks more (0 for no limit).
    1 for the W65C816.  CCPPUnit::ObjectAlignment(type) is a type's alignment under it, which alignof, alignas(type)
    and CCPPUnit::VariableAlignment use; CCPPUnit::DataAlignment (a global's or a static's .align) is limited by it.
  - CCPPTarget::GetMemberAlignmentLimit: the most a class's member is aligned to unless alignas asks more.  2 for
    the W65C816.  CCPPUnit::LayoutClass gives the layout the lesser of it and #pragma pack's bytes as its pack.
  - CCPPClassLayout::LimitedAlignment(type, limit): a type's alignment under a limit, but never less than alignas
    asks of the type.  Both of the above are it, with a different limit; the layout places bases, virtual bases,
    fields and bit-field units with it.
  The plan's IsByteAligned became a limit like the member's, so one function serves both.

Two things the plan didn't say, decided while building (both are in the questions):
  - alignas on a member's or a base's class is kept in a packed class, and so under the W65C816's limit: before,
    struct alignas(8) A; in a #pragma pack(1) class was placed at any byte, and the limit of 2 would have put every
    such member at an even offset only.  MSVC keeps it (its "required alignment"); g++ doesn't.  A field's own
    alignas was already kept.  TestCPPClassLayoutPackAndAlignas.
  - The plan's switch (CPP65_ALIGN_816 in the environment) and dump (CPP65_DUMP_LAYOUTS) were committed with step 1
    (699749946), used for the count, and are gone again: the target just answers.

What depended on the layouts and was changed (step 5):
  - BaseLib/FatW65C816.inc regenerated (39 values moved).  The FAT assembly uses only its names; its word copies
    (ldy SIZEOF_x - 2) need even sizes, which every class with a member of 2 bytes or more still has.  The FAT tests
    pass on the W65C816, and the kernal boots from a card with it.
  - HCP65's TestHCP65Kernal.cpp read SKernalStatus from MPU RAM at offsets with 4 byte alignment written in
    (uiHeapPeak at 52).  It now reads the members one after another (TestKernalRead16, TestKernalRead32), which is
    the W65C816's layout of a struct of 2 and 4 byte members; uiMainBanks, the last, is asserted after a boot, which
    is what notices the two sides drifting apart (it is how this was found: 52428 for 64).
  - The tests' expected sizes: 15 files of TestBaseLib and 9 of TestStandardLib gained a W65C816 branch (about 130
    places) beside the 32 bit and BASELIB_SIZE16 ones, and TestCPPW65C816's alignas(long) case expects 1.  Three
    tests of TestIndexedData.cpp tune a cache to the nodes' size ("a little more than two items"): the W65C816 has
    its own cache size there (3540, 3638 and 3618 for 3580, 3690 and 3670) so the same evictions happen.

The tests (step 6):
  - TestCPPClassLayout: alignas kept for a member, an array member and a base in a packed class.
  - gasTestCPP65Layouts (TestCPP65Context.h, defined in TestCPPW65C816.cpp): 13 programs with what main returns on
    each target, run by TestCPP816Alignment and TestCPP65GeneratorLayouts: members at even offsets, 8 byte members,
    char sized members and classes, member classes and arrays of them, alignof of scalars, pointers, references,
    member pointers, enums, classes and arrays, alignas of a class, a global and a local, #pragma pack 1, 4 and 8,
    bit-field units, bases and the vtable pointer, unions, an array's stride, and globals placed one after another.
  - Conformance case BasicAlignmentLocals (Clause03.txt, g++ checked -m32 and -m64): locals' addresses are multiples
    of their types' alignment at several depths of call.  It returned 0 on the W65C816 before.
  - The cases the plan named (BasicAlignment, BasicAlignasObjects, AlignofRules, SizeofRules) compare with alignof
    and sizeof, never numbers: they pass unchanged.

The docs (step 7): HCP65/Website/docs/compiler/language.md has "Alignment and layout"; Cpp14CompliancePlan.txt B 7 is
done, and B 9 is new (the 65C64's 8 byte locals, question 4).

8. Step 10: what a 16 bit store over a char and its padding would save
----------------------------------------------------------------------

Measured with a compiler instrumented in a scratch copy (nothing of it is in the tree): CCPP65IRFrontEnd::Store wrote
down each one byte store, whether it was to a class's member, and whether that member has a byte of padding after
it; each source line counted once.  Then the libraries' test suites were run on the W65C816 with a profile
(TEST_PROJECT65_PROFILE), which says how often each line was entered.

  Sites, in the twenty HCP65 projects' code (with the Libc65 and BaseLib units they use):
    byte stores 7522; to a member 1763; to a member with padding after it 897
    (the kernal alone: 4043, 1011, 374; modplay: 6320, 1346, 820).
  Run, 6 cycles for each store to a member with padding after it:
    TestBaseLib65       29,341,230,924 cycles run;  68,883 such stores;    413,298 cycles, 0.0014% of the run
    TestStandardLib65   22,405,899,511 cycles run; 137,894 such stores;    827,364 cycles, 0.0037% of the run
    TestSupportLib65    96,569,602,583 cycles run; 104,499 such stores;    626,994 cycles, 0.0006% of the run
  (All byte stores run: 16.8, 16.1 and 92.5 million, so every sep and rep around a byte store together is 0.3% to
  0.6% of those runs.)  The busiest lines are a flag set beside a pointer: LogFile.cpp(532), LifeCycle.h(134),
  ArrayBlockSorted.cpp(55), MemoryFile.cpp(116), FreeList.cpp(50).
  It is an upper bound: a store counts whenever its line is entered, and whether the value is already in a 16 bit
  register isn't asked.

So the optimisation the padding was kept for would save a few thousandths of a percent.  Nothing was built for it
(questions 1 and 2).

What the layout change itself did to the same suites' programs (the same tests, old layout and new, cycles and
linked size, for the tests that pass with either):
    TestBaseLib65       163 tests: cycles 24,437,658,562 to 24,430,656,029 (-0.03%); linked bytes -0.01%
    TestStandardLib65    56 tests: cycles 21,564,425,807 to 21,550,993,145 (-0.06%); linked bytes -0.05%
    TestSupportLib65     72 tests: cycles 96,786,208,488 to 96,569,603,087 (-0.22%); linked bytes -0.01%
  No test moved by more than +1.1% (TestString) or -2.5% (TestIndexAccess, TestMeshEdgeCollapse).  So the change is
  about free in time and in code; what it saves is data (a CObject is 126 bytes for 144).


9. Questions for the user
-------------------------

Nothing below blocks anything: each has what was done meanwhile.

  1. Padding.  It was kept at 2 "for speed", for the 16 bit store of a char and its padding.  Measured (section 8),
     that saves at most 0.004% of a run.  Padding to 2 does still keep a class with a wide member a whole number of
     words, which the FAT assembly's word copies rely on.  Keep 2, or pack to 1?  Done meanwhile: 2, as ruled.  Changing it is CCPPTargetW65C816::GetMemberAlignmentLimit's number, the
     regenerated FAT offsets and the tests' sizes again.
  2. The 16 bit store itself: build it?  Not built; the measurement says it isn't worth its code.
  3. The layout dump (CPP65_DUMP_LAYOUTS=<file>: a line for each class laid out, with its size, alignment and every
     base's and field's offset).  Removed with the switch; it is in 699749946 (CCPPUnit::DumpLayout).  Should it come
     back as a proper option (of CCPPCompileOptions, and hcp65build's command line)?  It found the 865 classes in two
     runs and a diff.
  4. The 65C64 has the fault B 7 was about, for 8 byte types only: its frames' places are multiples of 4, and
     alignof(double) and alignof(long long) say 8 (Cpp14CompliancePlan.txt B 9).  CCPPTarget65C64 answering 4 from
     GetObjectAlignmentLimit would fix it in one line: alignof would say 4, a double global would be at a multiple of
     4, and no class layout would change.  You ruled that the 65C64 doesn't change, so it wasn't done.
  5. alignas on a member's or a base's class is now kept in a #pragma pack class, on both targets (section 6).  No
     class in the libraries or HCP65 is affected (the 65C64's 2352 layouts are the same).  Say if g++'s way (the
     pack wins) is wanted instead.
  6. Raw bytes.  BaseLib writes classes as raw bytes, and the W65C816's now differ from a PC's wherever a PC pads
     to 4 or 8: CIndexedDataDescriptor is 24 bytes for 32, CIndexTreeNodeFile 22 for 24, CFreeList's node 20 for 24.
     (They already differed wherever a size is a member.)  The BASELIB_SIZE16 host build no longer has the W65C816's
     sizes, which is why the tests have a third branch.  Is a file written on a PC and read on the HCP65 (an index,
     a Codabase) wanted?  If so those classes need members that pad the same everywhere; nothing does that today.
  7. SKernalStatus's last three members moved (uiHeapPeak 52 to 50, uiMainHeapPeak 56 to 54, uiMainBanks 60 to 58).
     The emulator's test reads it as laid out now.  Anything else that reads it (a debugger script, a tool on the
     PC) must follow.  Putting uiMainBanks beside uiDriverError would make it the same on a PC and the W65C816; not
     done, as it moves them again.
  8. A kernal built now doesn't run drivers or programs built before, and the other way round (HCP65User.h's
     SKernalBlit, SKernalMemoryInfo and SKernalDirectoryEntry, and CKernalDriver, changed).  Everything in the
     repositories is built together; an SD card image with old programs needs them rebuilt.
  9. Not done: a Microsoft build of the change (Cpp14CompliancePlan.txt C 1 is owed anyway; no file was added).

  1. Padding stays at 2.  Nothing to do.
  2. The 16 bit store isn't built.
  3. The layouts file.  CCPP65Builder::SetLayoutsFile(file): each class the build's sources lay out is a line
     (CCPPUnit::AddLayout: its name, where it is defined, its size, alignment and alignas, then each base's, the
     vtable pointer's and each field's offset), the units' lines merged in order with each once, written when the
     units are compiled and again with each source after (AddSource, LinkWith).  hcp65build -layouts <file>, for a
     solution or a plain command line (CBuild::SetLayoutsFile, CSolutionBuild::Start's last argument), and
     TEST_PROJECT65_LAYOUTS=<file> for the libraries' test programs.  Two builds' files compare with diff, which is
     what the count needed a script for.  It isn't a configuration's attribute or a tick box in the IDE: say if it
     should be.  Tests: TestCPP65GeneratorLayoutsFile (both targets), TestBuildCommandLineLayouts (plain and
     solution).  Docs: compiler/building.md "Class layouts".
  4. CCPPTarget65C64::GetObjectAlignmentLimit answers GetFrameAlignment (4): alignof(double) and alignof(long long)
     are 4 on the 65C64, and alignof of a class that holds one, whose layout is as it was (a double member still at a
     multiple of 8); a global double is at a multiple of 4.  BasicAlignmentLocals has 8 byte locals (31; the 65C64
     returned 19 of it before).  TestBaseLib's TestPrimitiveTypesAlignment expects alignof 4 of the 64 bit vectors
     there.  Cpp14CompliancePlan.txt B 9.
