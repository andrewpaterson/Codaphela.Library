A 16 bit size_t on the W65C816 (CppParserTodo.txt question 14)
================================================================

The user, 2026-11-18: "make Libc65's size_t 16-bit" (sizeof is already a 16 bit unsigned int there), the 32 bit
allocation the special case: "32 suffix please.  Whole banks.  Drop 16 suffixes".  And: "that means size and size_t
are now the same which is great".  On the W65C816 BaseLib's size is uint16, which is unsigned int since Libc65's
uint16_t is (question 13), so size, size_t and sizeof's type are one type.  The 65C64 doesn't change.


What it is when done
--------------------

- size_t is unsigned int on the W65C816; SIZE_MAX is 0xFFFF there.  ptrdiff_t stays long: pointers are 32 bits, and
  a difference of pointers into a block of more than 32KB (malloc32's) must not be cut.  The standard asks no more of
  ptrdiff_t than that it is signed and is pointer - pointer's type ([support.types] 5.2.3): a 16 bit size_t with a 32
  bit ptrdiff_t is allowed (the user, 2026-11-18: "ptrdiff_t as long, agreed").  intptr_t and uintptr_t stay 32 bits.
- malloc, calloc, realloc, operator new and new[], and the string functions (memcpy, memmove, memset, memcmp, memchr,
  strlen, strncpy, strncat, strncmp, snprintf's size, fread and fwrite) take and give 16 bit counts.  Their bodies
  are today's 16 bit ones (stringW65C816_16.asm's memcpy16 and the rest, renamed).
- The 32 bit ones have a 32 suffix: malloc32, calloc32, realloc32, memcpy32, memmove32, memset32, memcmp32,
  memchr32, strlen32 (in string.h and stdlib.h under __W65C816__, uint32_t counts), with today's 32 bit bodies
  (stringW65C816.asm).  There are no 16 suffixed names left: memcpy16, memmove16, memset16, memcmp16, strlen16 and
  BaseLib's MemSwp16 go (MemSwp is 16 bit there, MemSwp32 the 32 bit one).
- malloc's blocks never cross a bank: the heap is a CTrueMallocator region for each 64KB bank, so no block can, and
  Malloc stays constant time.  malloc of more than a bank's room is NULL.
- malloc32 of more than fits a bank takes whole adjacent banks (rounded up to 64KB), as the kernal's main heap takes
  banks (KernalTakeHeapBanks); free gives them back.  malloc32 of what fits a bank is malloc.  free and realloc take
  either kind of block.  A bank the small heap
  holds goes back to the pool when all its blocks are free (IsRegionFree, RemoveRegion), so large allocations can
  have it again.
- BaseLib: SArrayNaturalSize copies with memcpy and the others on every target (no W65C816 branch: size is size_t);
  SArrayLargeSize (lsize) uses memcpy32 and the others on the W65C816 and memcpy elsewhere.  CSystemAllocator's
  Malloc and Realloc (lsize) call malloc32 and realloc32 on the W65C816.  StrLen is strlen everywhere.
- The compiler: what it calls by name with a count passes a size_t where the count fits (memcpy for
  __builtin_memcpy, the loop idioms' memset and memmove when their count is 16 bits) and the 32 suffixed function
  where it may not.

------------------------------------------------

0. Baseline, before anything changes: OS.SYS's code and data (the segment bytes hcp65build prints), modplay.exe's
   size, TestLibc65's and TestHCP65Lib's times, and a profile of a BaseLib-heavy *65 test (TestBaseLib65's
   TestArrayInt, say) for cycles.  Written into this file.
   Done 2026-11-18, on master as rebased onto the Blitter Board work (HCP65 8f76e57, CommonLibraries 6b0b6a32b),
   Release x64 tools, Debug|W65C816 builds (scratchpad s16/measure.sh):
     OS.SYS                                  180258 bytes of segments
     modplay.exe                             788757 bytes
     TestLibc65 65C64                        154774 passed, 13s
     TestLibc65 W65C816                      154790 passed, 18s

     TestBaseLib65 816, TEST_PROJECT65_ONLY=TestArrayInt,TestArrayBlock,TestArrayTemplate,TestChars,TestCharsHelper,
       TestMapString with TEST_PROJECT65_CYCLES: 3164739188 cycles

1. Libc65's heap by banks (HCP65; nothing else changes yet).  InitHeap gives CTrueMallocator one region per bank of
   the heap's memory (0008:0000-000F:FFFF and the high heap the same way), so no block crosses a bank.  A bank pool
   (a bitmap of the heap's banks) hands whole banks to the small heap when it is full and to large allocations;
   malloc of more than a bank's room is refused.  Small banks are taken from the bottom of the heap, large runs from
   the top, so they meet only when memory is short.  A byte for each bank says what it is (free, the small heap's,
   the first of a large run, more of one), as the kernal's gauiKernalBanks does, so free knows which a pointer is.
   The kernal's main heap (KernalMemory.cpp, KernalMainMalloc's explicit uint32 sizes) is its own and stays as it
   is.  Built 2026-11-18: __HeapInit(start, bytes) sets it up, for Libc65's start up and the kernal's
   KernalInitHeap (which called gcHeap.Init itself).  The inliner copied the heap's helpers into each of malloc,
   calloc, realloc and free (7.4KB more kernal); __attribute__((noinline)), which the compiler didn't have, keeps
   HeapMalloc, HeapFree and __HeapInit one copy each (CommonLibraries 5df6a5f17), and the kernal is 2394 bytes
   over the baseline, ending at $03D5CE of $040000.  Tests in TestLibc65: no block crosses
   a bank, freeing a bank's last block returns it, many small allocations then a large one.
   Checks: TestLibc65, TestHCP65Lib (the kernal), the *65 compiles.
   Passed 2026-11-18: TestLibc65 (65C64 154774, W65C816 154804), the *65 compiles on both targets.  TestHCP65Lib was
   stopped for low memory in its kernal tests (Font 271, Machine 795 and Debugger 234 passed, nothing failed); step 4
   runs it whole.

2. The 32 suffixed functions, beside today's (HCP65).  malloc32, calloc32, realloc32 (large ones by whole banks,
   small ones malloc), memcpy32, memmove32, memset32, memcmp32, memchr32, strlen32: today's 32 bit bodies under the
   new names, the old names still there.  TestLibc65's 32 bit tests call the new names.
   Checks: TestLibc65.

3. BaseLib's large paths call them (CommonLibraries): SArrayLargeSize, CSystemAllocator::Malloc and Realloc,
   MemSwp32 (today's MemSwp body: stringW65C816.asm's _MemSwp__FPKvPKvm becomes _MemSwp32), FindFirstSetBitLarge and
   the others stay as they are (already lsize).  Any other lsize count reaching memcpy and the others is found by
   compiling the *65 projects with the narrowing warning (CCPPCompileOptions::mbWarnNarrowing) and with
   TEST_PROJECT65_LISTINGS, and looking at each lsize to size_t warning.  Still with a 32 bit size_t, so nothing
   breaks yet.
   Checks: the *65 compiles (both targets), TestBaseLib65 816 for the array tests only (TEST_PROJECT65_ONLY), the
   host BASELIB_SIZE16 build if it builds today.

4. The switch (HCP65, CommonLibraries, HCP65-IDE in one go: apart, size_t and the asm disagree).
   - stddef.h: size_t unsigned int under __W65C816__; stdint.h SIZE_MAX 0xFFFF there.
   - string.h, stdlib.h, stdio.h: the plain names take size_t (16 bits); the 16 suffixed declarations go.
     stringW65C816_16.asm's bodies become memcpy, memmove, memset, memcmp, strlen (and MemSwp, the FindFirst/Last bit
     ones of size); stringW65C816.asm keeps only the 32 suffixed ones.  memchr, strncpy, strncat and strncmp have no
     16 bit bodies: their plain names become short entries that widen the 16 bit count (in Y, as the register
     convention gives a 16 bit third argument) and go into the 32 bit body (memchr32's; strncpy's, strncat's and
     strncmp's under local names, as no one asked for 32 suffixed ones of those).  malloc and the others in
     stdlib.cpp, and new.cpp's operator new and new[], take 16 bits.
   - BaseLib: SArrayNaturalSize loses its W65C816 branch, StrLen loses its #if, MemSwp16 goes (MemSwp is it),
     StringHelper.h's declarations follow.  PrimitiveTypes.h: on the W65C816 size is size_t (one typedef, as it says);
     BASELIB_SIZE16's host check keeps uint16.
   - Labels with a size_t parameter change on the W65C816 (m to j): the asm (FatFilenameHelper and the other Fat
     ones, stringW65C816*.asm, KernalExports.asm) and the tests that name them, found as question 13's were (the
     linker's missing names, TestCPP816StringRegisters).
   - The compiler: __builtin_memcpy's count is a size_t (CCPP65IRFrontEnd::BuiltinMemcpy, CCPP65TypeChecker's
     CPPB_Memcpy: Size(), not Long(false)); IROptimiserIdioms' memset and memmove get a 16 bit count and the plain
     name when the loop's count is 16 bits, else memset32 and memmove32 with 32 bits (msLibraryInt and the I32
     counts there).  A conformance case or two: sizeof's type is size_t, decltype(p - q) is ptrdiff_t.
   - Docs: language.md (the table's size_t row, the 16 bit int traps), libc65.md (headers, the 32 suffixed
     functions, malloc by banks), w65c816.md where it names memcpy16.
   Checks: TestCppCompilerLib (RunParallel.py), the *65 compiles (both targets), TestLibc65, TestBuildLib,
   TestHCP65Lib, the kernal with hcp65build (OS.SYS fits; against step 0), modplay with hcp65build, the IDE's
   assembly checks.

5. Measure against step 0 and write it here: OS.SYS, modplay.exe, the profile's cycles.  Then the *65 suites
   themselves, run once as the sweep runs them (the user's rule is not to run them for ordinary feature work; this
   changes what every BaseLib array and string call on the W65C816 compiles to, so ask the user first).


Risks
-----

- An lsize count passed to a plain function is cut to 16 bits with no error (narrowing is a warning).  Step 3's
  warnings are the list; anything they miss shows as a wrong result in the *65 suites, which is why step 5 asks to
  run them.
- Code that asks malloc for more than 64KB gets NULL where it got memory.  BaseLib goes through CSystemAllocator
  (malloc32); a program calling malloc directly for a big buffer (modplay's module?) is found by step 4's checks and
  changed to malloc32.
- Rounding a large allocation up to whole banks costs up to 64KB less one each time; the machine's large
  allocations are few and big (modules, images, file buffers).
- gameengine-09's exceptions branch touches CPP65IRFrontEnd*.cpp: tell it before step 4.
