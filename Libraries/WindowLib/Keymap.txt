Keymap Contexts Plan
====================

Keys that mean different things in different parts of a window.  WindowLib's commands (CCommand, CCommandSet) and the
keymap (Settings' Keymap, CKeymapPage) only know keys that work everywhere (CKS_Application, CKS_Window) and keys an
editor takes (CKS_Editor), and only let a user give keys with Ctrl or Alt.  LogiCim's circuit canvas has bare keys
(Logicim's: A places an AND gate, N an inverter, r rotates, m moves), which are hard-coded in
CCircuitCanvas::Printable, outside the commands and the keymap, so they can't be seen or changed.  Its subcircuits
can't be placed by a key at all.


Decided (user, 2026-11-14)
--------------------------

- Contexts are real: what a key does depends on the focused component, and on the component under the pointer.
- Hover and focus: over a context that takes bare keys (the circuit canvas), its keys work wherever the focus is,
  unless the focus is in a text field, which keeps typing.  Elsewhere the focused component decides.
- Fallback: a key not bound in the current context is looked for in the contexts around it, out to the global keys
  (canvas, then window, then global), as IntelliJ IDEA's editor keymap falls back to its main one.  The innermost
  binding wins.
- Subcircuits can be placed by a key.  Every subcircuit that can go in the circuit being edited is a command, with no
  key until one is given (in the component chooser or the keymap).
- A subcircuit's key is kept in the project file, so it goes with the project and follows a rename.  Only
  subcircuits' placement keys are the project's: the library components' (A for an AND gate) and every other key are
  the user's, in their settings (Keymap.xml), the same in every project.
- Conflicts between the two are detected (2026-11-14):
  - Loading a project silently clears any of its subcircuit keys that clash with the user's keymap: the user's keys
    win, and nothing is said.
  - Giving a key that clashes, in the keymap or the component chooser, shows a warning pop up naming the command that
    has it.
- The clash warning (2026-11-14) says who has the key and offers to move it: "Ctrl+Alt+A is Settings' File: Open
  Project.  Give it to AND Gate instead?" with Give and Cancel.  Give moves the key and saves both files it touches
  (the project's and the user's keymap).
- One set of rules for every place keys are given, the keymap page and the component chooser (the keymap's, shared,
  as CheckCommandKeys began to be), applied and saved through one path.  The keymap page reads the keys afresh each
  time it opens; it and the chooser are both modal, so they're never open together.
- Conflicts across contexts (2026-11-14): a key belongs to one command in each context.  R can rotate over the canvas
  while Ctrl+R does something else everywhere, and a context's key shadows a global one only in that context.  The
  keymap says when a context key shadows a global key ("R is Rotate Left over the circuit; elsewhere it's ..."), and
  refuses nothing for it.
- The HCP65 IDE (2026-11-14) moves onto the same contexts: its editor keys (CKS_Editor) become the editor context, with
  the global keys around it, and nothing changes for its users.
- How keys are shown (2026-11-14): a menu item (and a tool button's tip) shows the command's global key if it has one,
  else its context key, plain: Rotate Left shows "R", not "R (circuit)".  The keymap's list says where each key works.


Words
-----

Context     Where a key's binding is looked for: global (the whole window), a window's own, a component's (the circuit
            canvas, a code editor).  Contexts nest; the focused or hovered component's context is the innermost.
Binding     A key given to a command in a context.  A command can have keys in more than one context (R over the
            canvas and Ctrl+R everywhere, say).
Bare key    A key without Ctrl or Alt, which types a character in a text field.  Only a context that takes them (the
            canvas) can bind them.


How keys work now
-----------------

What the design changes, as it is in WindowLib today:

- CComponentInput turns a key press into events.  Its standard keys (CIC_Copy for Control+C, CIC_Tab, the
  printables) come from the keyboards' input files; an application's keys (BindKeys) are a table, masBindings, given
  to every keyboard after the standard ones, so a bound key gives its command (CIC_Command, named by the keys) in
  place of what it gave before.  That's why a key that types can't be bound: it would stop typing everywhere.
- Editors have a second table, masEditorBindings (BindEditorKeys), read instead of the standard keys when the focused
  component uses editor keys (CComponent::UsesEditorKeys: CTextArea) and the window isn't a dialog
  (CFocus::Input passes Translate's bEditorKeys).  A key not in it falls back to the standard keys unless that's an
  editor command (GetEditorCommand).  This is a context with a parent already, wired in as a special case.
- CFocus gives the events to the focused component and up its parents; a CIC_Command nothing took runs the command
  with those keys from the window's CCommandSet, then its owner's (DispatchUnhandledCommand, RunCommand, FindKeys).
- A CCommand has one key scope (ECommandKeyScope: CKS_Application runs it, CKS_Window and CKS_Editor give its standard
  command) and one list of keys, written to Keymap.xml only where they differ from its defaults.
- LogiCim's canvas keys don't go through any of this: a printable reaching the focused CCircuitCanvas is looked up in
  CCircuitCanvas::Printable's switch.


Technical design
----------------

Contexts in CComponentInput

- A context is a named table of bindings with a parent: SComponentInputContext { szName, szParent, asBindings,
  bTyping }.  "Global" is the root (masBindings now); "Editor" is the IDE's editor keys (masEditorBindings now, parent
  Global); LogiCim adds "Circuit" (parent Global, bTyping).  AddContext(szName, szParent, bTyping) makes one;
  BindKeys(szKeys, eCommand, szContext = "Global") and UnbindKeys take the context.
- Translate(psWindowEvent, asDest, szContext) replaces bEditorKeys: it looks the key up in the context, then its
  parent, out to Global, then the standard keys, and the innermost binding wins.  The Editor rule that an editor
  command not bound in Editor gives nothing stays: a context can say its standard commands are its own
  (SetOwnsStandard(CIC_... ) as Editor does for the caret commands), so they don't fall through.
- Only a context with bTyping can bind a key that types.  In it, a bound bare key gives its command instead of the
  printable; an unbound one still types (or reaches the canvas as a printable, as now).
- A binding gives CIC_Command (run a command) or a standard command (CIC_CloseDocument, CIC_Copy), as now, and its
  event carries the context it came from, so the command run is the one bound there.

Which context a key is read in (CFocus)

- A component says its context: virtual const char* CComponent::GetKeyContext(), NULL for its parent's (Global at the
  top).  CTextArea returns "Editor" (UsesEditorKeys goes), CCircuitCanvas "Circuit".
- A component says it takes typing: virtual bool CComponent::TakesTyping() (CTextField, CTextArea, a combo box being
  edited).
- CFocus::Input picks the context, as decided: if the component under the pointer is in a typing context (bTyping)
  and the focused component doesn't take typing, the hovered component's context; otherwise the focused component's.
  In a dialog (modal) it's always Global, so a remap can't break a dialog.
- A key that comes from the hovered context runs its command (CIC_Command) or gives its standard command to the
  hovered component, not the focused one, so A over the circuit places there while the Subcircuits list has the
  focus.

Commands with keys in contexts

- A CCommand's keys each have a context: SCommandKeys { szContext, szKeys }, for its keys, its default keys and its
  bound keys.  ECommandKeyScope goes: a command runs itself, or gives its standard command (SetStandardCommand) in
  whatever context it's bound; CKS_Application is Global and running, CKS_Window Global with a standard command,
  CKS_Editor Editor with one.
- A command says the contexts it may have keys in (AllowContext): LogiCim's placing commands allow Circuit and Global,
  the IDE's caret commands only Editor.  Its keys are given with a context: AddDefaultKeys("R", "Circuit").
- Shown keys (menus, tool tips): the first Global key if it has one, else its first key in any context, plain.
  CCommand::GetShownKeys() does it, and AppendKeysText uses it.
- CCommandSet::FindKeys(szKeys, szContext) finds the command with those keys in that context; RunCommand passes the
  event's context.  A key belongs to one command in each context; giving it to another in the same context moves it.

Keymap.xml

- A <Keys> keeps its text and gains a Context attribute where it isn't the command's first allowed context:

	<Keymap>
		<Command Name="Edit.RotateLeft"><Keys Context="Circuit">R</Keys><Keys>Control+R</Keys></Command>
	</Keymap>

  So today's files (no Context) read as they were written: an IDE command's keys were for its only scope.
- Commands whose keys aren't the user's (a subcircuit's, kept by the project) are never written to it
  (CCommand::SetKeptByKeymap(false)), and a file naming one is ignored for it.

The keymap page

- The keys column shows each key with where it works when it isn't Global: "R (Circuit), Ctrl+R".
- Add Shortcut has a Where choice (a combo box) listing the command's allowed contexts, Global first unless the
  command's first allowed context is another; the keys are checked in the chosen context.
- The rules (CheckCommandKeys, shared): a key that types only in a typing context; a key dialogs and text fields need
  only in Editor; a key the command already has there refused.  A key another command has in the same context: the
  clash pop up (below).  A key a Global command has, given in a context: allowed, and said ("R shadows Global's
  ... over the Circuit").
- Its rows are its copies, as now; OK applies them through the key giver (below) so the clash pop ups and saving are
  the same as the chooser's.

Giving keys: one path

- CKeyGiver (WindowLib) is what every place that changes keys uses: Give(pcCommand, szContext, szKeys, pOwner window)
  checks the rules, shows the clash pop up when another command has the keys there ("Ctrl+Alt+A is File: Open
  Project.  Give it to AND Gate instead?", Give and Cancel), moves them, binds, and tells the application which
  commands changed (a listener) so it saves their homes: Keymap.xml for the user's, the project for a subcircuit's.
  Remove(pcCommand, szContext, szKeys) and Reset likewise.
- The keymap page gathers its changes until OK, then gives them; the chooser gives each straight away.

Subcircuit commands and the project file (LogiCim)

- Each subcircuit that can go in the circuit being edited is a command, Place.Subcircuit.<type name>, caption "Place
  <type name>", allowing Circuit and Global, kept by the project (SetKeptByKeymap(false)), in the keymap's
  Subcircuits group.  They're made, renamed and removed as the circuits are (when the subcircuits are listed), and
  rebuilt when a project is loaded, made new or imported.
- Their keys are the circuit's: <Circuit type="Selector 12bit" placeKeys="Circuit:Shift+Q">, written with the
  circuit, so they follow a rename and undo, and changing one is a change to the project (it has to be saved).
- Loading a project gives each its keys, silently dropping any that clash with a command the user's keymap gives
  them to in the same context.

LogiCim's canvas keys

- CCircuitCanvas::GetKeyContext() is "Circuit"; the context is added with bTyping.  Printable's switch goes.
- Commands for every library component, Place.<XML name> ("Place.AndGate"), caption the library's name, allowing
  Circuit and Global; the toolbar's Add Splitter, Add Tunnel, Add Power and Add Label are those commands for their
  components.  Their defaults are Logicim's: A (Shift+A) AND, O OR, X XOR, N inverter, C clock, P probe, S splitter,
  T tunnel, L label, F D flip flop, and p pin, c constant, g ground, v power.
- Edit.RotateLeft (r), RotateRight (R), FlipHorizontally (x, and its Control+Shift+F, H stays Global), FlipVertically
  (y) and Properties (e and E) get those as Circuit keys, and a new Edit.Move has m.

The component chooser's Shortcut line (LogiCim)

- Above the preview: the selected component's keys as the keymap shows them ("Shift+A (Circuit)", or "None"), with
  Add Shortcut... (the keymap's Add Shortcut, its Where defaulting to Circuit) and Remove, both through the key giver.
  A library's row shows nothing and the buttons are off.

The HCP65 IDE

- Its editor keys are the Editor context; UsesEditorKeys becomes GetKeyContext; its commands' CKS_ scopes become
  contexts as above.  Nothing changes for its users and its keymap checks (keymap-*) must pass as they are.

Plan
----

Each numbered step is built, checked and committed on its own (CommonLibraries on master, HCP65-IDE and LogiCim on
main), so the IDE and LogiCim work after every one.  "Checks" are: TestWindowLib (32-bit Release), the IDE's checks
that touch keys (IDEChecks.py keymap-*, menus, commands; Release x64), and LogiCim's (LogicimChecks.py).  A step that
changes behaviour adds its own tests or checks.

Where it stands (2026-11-14)
----------------------------

Steps 1 to 9 are built, checked and committed.  What was built differs from the plan above in these ways:

- The key giver (KeyGiver.h) gives to key lists (CKeyListSource), not to commands: the keymap page's copies until OK,
  or a command set's own keys (CCommandSetKeys, the chooser's).  It has Describe and Give only; removing and resetting
  stay the page's and the chooser's, and there is no listener: whoever gave the keys binds and keeps them (the IDE's
  CIDESettings, LogiCim's KeepKeymap).  The page gives as keys are added, so a clash asks then, not at OK.
- Shadowing is said both ways: a key given in an inner context that a Global command has ("It shadows Open Project
  there."), and a Global key an inner context's command keeps ("Editor Actions: Duplicate keeps it over the Editor.").
  So in the IDE, Ctrl+D given to Debug: Step Over no longer moves from the editor's Duplicate: Step Over has it
  everywhere but the editor.  The IDE's keymap-refused check was changed to say so; the others pass unchanged.
- The keymap page shows a key's context after it unless it's Global or Editor ("R (Circuit), Ctrl+Shift+F, H").
- LogiCim's Place commands are captioned "Add <component>", as the toolbar's are, and every library component has
  one, the 74 series' too.  The check step is keys:<context>:<keys> (which command those keys run there, falling back
  to Global); real keys over the canvas were tried by hand on an isolated X server (Shift+A places an AND gate, R
  rotates it), and the hover and text field rules are TestWindowLib's (TestKeymapContextFocus).
- The chooser's Shortcut line is blank on a library's row, but its buttons stay (components can't be hidden or
  disabled yet); with nothing to give to they say "Select a component first.".  Its scripted step is chooser, with
  LOGICIM_CHOOSER_EDITS.
- Subcircuit commands are made for every circuit of the project, not only those that can go in the one being edited,
  and are in the Place group.  They follow the project whenever its information is updated (CLogicimWindowContent::
  FollowSubcircuitCommands), which covers loads, new projects, imports, undo and new subcircuits.  A key dropped on
  loading because another command has it is dropped from the project too.  placeKeys is "<context>:<keys>" separated
  by semicolons.
- Along the way: CDialog::Show measures its body (a message dialog's long message was cut off), and CCommandSet::Remove.

Left open:

- A subcircuit rename keeping its keys isn't checked (the keys are on the circuit, so they should follow it).
- Add Shortcut's Where combo box is centred in its row rather than left aligned.
