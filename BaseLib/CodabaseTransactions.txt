Codabase Transactions
=====================

Design for ACID transactions on top of CCodabase.  Decided 2026-10-17 and 2026-10-18.  All five steps of the build order are implemented.


Goal and guarantee
------------------

Fully ACID transactions in CCodabase.

The version 1 guarantee is strict serialisability for everything read or written by OIndex.  Strict means the serial order agrees with real time: if T1 committed before T2 started then T1 comes first.

Two things are deliberately NOT covered by version 1:
  - Name lookups by write transactions that find nothing.  A write transaction that calls GetIndex("Alpha"), gets "not found" and acts on it is not protected against another transaction creating "Alpha".
  - Phantoms when write transactions iterate.  An index or name iteration in a write transaction can miss an object another write transaction inserts.

Read-only transactions are fully covered, including names and iteration, because they read a snapshot.


Scope
-----

In scope:   CCodabase and the classes beneath it (CNamedIndexedData, CDurableFileController).
Not in scope for version 1:
  - CObjects.  It keeps using the direct (non-transactional) API.
  - Nested / sub-transactions.  Not planned.
  - Name edge cases inside a transaction, e.g. removing a named object and re-adding the same name, or one transaction removing a name while another creates it.
  - Locking and iteration gaps listed under "Goal and guarantee".

Threads only.  Exactly one process owns a Codabase; other processes reach it by IPC into that process.  All transaction structures live in ordinary memory, not shared memory.


Transaction kinds
-----------------

Read-only transactions
  - Take a snapshot when they start: the last published commit number.
  - Read the base Codabase, plus older versions from the version store where an object or name has been committed since the snapshot.
  - Take no locks, never wait, never abort.
  - Have no write set.  Ending one just releases its snapshot.

Write transactions
  - Use pessimistic locking through a per-object lock manager (see "Lock manager").
  - Read the LATEST committed version, never a snapshot, after taking a lock.  This is required for serialisability; reading a snapshot would allow write skew.
  - Hold every lock (shared, update and exclusive) until the commit is durable (rigorous two-phase locking).  This makes commit order a valid serial order.
  - Keep all changes private in a write set until commit.
  - Write transactions run at the same time.  BeginWriteTransaction never waits; transactions wait, or die, when they lock objects.  Read-only transactions never wait.
  - A transaction that dies has its changes discarded and its locks and name reservations released; the call that found the conflict returns false and HasDied() is true.  Restart() begins it again with its original start number.

Why this is strictly serialisable: write transactions are serialised in commit order.  The state at any commit number is therefore a prefix of that serial order, and a read-only transaction reading it fits into the order at exactly that point.  Because write transactions never read snapshots, the snapshot isolation anomalies (write skew and the read-only anomaly) cannot occur.


API
---

  CCodabase::BeginReadTransaction()   returns CReadTransaction*
  CCodabase::BeginWriteTransaction()  returns CWriteTransaction*

CReadTransaction implements CDataReader: Get, GetName, GetIndex, Contains, StartIndexIteration / IndexIterate, StartNameIteration / NameIterate.  CDataConnection is CDataReader plus writing, so CCodabase and CWriteTransaction are CDataReaders too.

CWriteTransaction implements CDataConnection (Add, Set, Put, Remove, Get, ...) and adds Commit and Abort.  Code written against CDataConnection can therefore run on a write transaction unchanged.

The transactions only use CCodabase through its methods (Stored..., Snapshot..., LockObject, ReserveName, CommitWriteSet), never its members.

Ownership follows BaseLib conventions: the Codabase allocates transactions and Kill() releases them.  Killing a write transaction that has not committed aborts it.

Direct (non-transactional) API
  - CObjects and other existing callers keep calling CCodabase's Add / Set / Put / Remove / Get directly.
  - Open starts an implicit write transaction with start number 0, so it is always the oldest: under wait-die it waits but never dies.  Only one session is open at a time; a second Open waits.  Close commits it.
  - Direct calls between Open and Close go through the session from any thread (a session mutex serialises them).  Its changes are not in the store until Close.  Direct reads without a session read the committed store; direct writes without one fail.
  - NumIndices, NumNames and the cache statistics (NumIndicesCached, NumDataCached, NumNamesCached) count the session's own changes while it is open.
  - A thread with a session cannot begin a write transaction, and a thread with a write transaction cannot Open, because the session could wait for that transaction for ever.
  - A durable bracket is always open while the Codabase is started, because reading the store needs one.  Start opens it; every commit is flush, End(), Begin().  Kill aborts the open bracket (CDurableFileController::Abort throws the logged changes away), so nothing uncommitted reaches disk, as in a crash.


Write set
---------

Each write transaction holds a private map of its changes:
  - by OIndex:  the new record (CNamedIndexedHeader + data) or "deleted".
  - by name:    the OIndex the name now refers to, or "deleted".

The name entries are needed so that GetIndex / Contains(name) inside the transaction see the transaction's own uncommitted Adds.

Reads in a write transaction check the write set first, then the base Codabase.

Abort discards the write set.  Nothing has touched disk, so nothing needs undoing.


Commit
------

CWriteTransaction::Commit hands its write set to CCodabase::CommitWriteSet, which holds the store mutex for the whole commit, so commits run one at a time.

  1. Nothing can fail on a name: names were checked against the committed names and reserved when they were added (see "Name reservations").  This matters because CDurableSet has no rollback; anything written inside a Begin/End bracket is committed by End().
  2. Removals are applied first, then additions and changes, so a name removed from one object can be given to another.  Before each change, if a read transaction is open, the store's current version (or "did not exist") is pushed into the version store, tagged "valid until C" where C is the new commit number.
  3. Flush, End(), and Begin() the next bracket.  After a commit the cache holds no unwritten changes, so eviction only ever drops clean data.
  4. Publish C as the latest commit number.
  5. Release the transaction's name reservations and locks, and return to the caller.

Publishing C only after End() returns, and returning only after publishing, gives the real-time part of strict serialisability: any transaction started after the commit returns sees it.

The store mutex is held for the whole commit, End()'s fsyncs included, so read transactions and stored reads wait while a commit is in progress (never for an uncommitted writer).  Holding it for one object at a time instead would let readers read through a commit, because they would find the pushed versions; that is not done in version 1.

Every commit costs fsyncs (milliseconds, more on Windows).  That is correct behaviour.  A write-ahead log could make commits cheaper later if needed.  Tests that do not need durability turn the fsyncs off with DS_No (see "Durability").

If a commit fails part way (a full disk, a failed write), the files are left mid-commit with marks on disk and the caches may not match them.  The transaction reports the failure and the Codabase goes read-only: it refuses further writes until it is closed and started again, and Start then recovers from the marks.


Name reservations
-----------------

If two transactions create objects with the same name, the one that creates SECOND fails, at create time.

A name reservation table maps a name to the write transaction that owns it.
  - Add with a name fails immediately if the name is already committed, or reserved by another transaction.  It never waits, so it cannot deadlock and is not part of the lock manager.
  - On commit the name moves into mcNames and the reservation is removed.
  - On abort the reservation is removed, freeing the name.

If the first creator later aborts, the second has already failed even though the name turned out to be free.  That is correct under create-time rules; the second can retry.


Lock manager
------------

Locks are keyed by OIndex only.  Names are not locked (see name reservations).

Newly created objects need no lock: their OIndex comes fresh from CSequence and no other transaction knows it.

Modes:

  Requested \ Held   S   U   X
  S (shared)         y   y   n
  U (update)         y   n   n
  X (exclusive)      n   n   n

  S  "I read it."
  U  "I read it and will probably write it."  Readers may continue, but only one transaction at a time may hold U.  Prevents two shared holders both upgrading and deadlocking.
  X  "I am writing it."  Required to write, reached from U or directly.

The caller chooses the mode.  Defaults: S on read, X on write, U when the caller knows it will modify.

Deadlock handling: wait-die, using each transaction's start number (lower is older).
  - A requester older than EVERY conflicting holder waits.  Otherwise it dies: aborts, releases everything and restarts.
  - A restarted transaction keeps its original start number, so it eventually becomes the oldest and cannot starve.
  - An upgrade (U or S to X) checks only the OTHER holders, not itself.
  - Incompatible waiters already queued count as conflicts for a new request, so a waiting X cannot be overtaken forever by new S requests.  A waiting upgrade goes to the front of the queue.
  - Dying is an ordinary false return ("transaction aborted"), not an exception.  The transaction layer frees the transaction's locks and reservations and wakes their waiters; the caller decides whether to retry.

Structure: a map from OIndex to lock entry (granted mode, holder list, FIFO wait queue), guarded by one CMutex, with a CConditionVariable per waiting transaction.  Entries exist only while held or waited on.  Locks are keyed by transaction, not thread, so a thread pool can serve one IPC session's requests on any thread.

Read-only transactions never enter the lock manager.


Version store (snapshots)
-------------------------

Old versions are kept in two in-memory maps beside the base CNamedIndexedData.  A second IndexedStore / NamedIndexStore is not used: those are durable (Begin/End, primary and backup, recovery) and CIndexedData keys are fixed to OIndex, while old versions are temporary.

  CMapLongTemplate<CVersion*>           OIndex -> chain of CVersion
  CMapStringTemplate<SNameVersion*>     name   -> chain of SNameVersion

Each chain is a linked list of malloc'd nodes, oldest first:

  class CVersion
  {
      int64       iValidUntil;    // Commit number that replaced this version.
      CVersion*   pcNext;
      bool        bExists;        // False: the object did not exist before iValidUntil.
      int32       iNameLength;
      uint32      uiDataSize;
      // The name with its terminating zero, then the data, follow.
  };

  struct SNameVersion { int64 iValidUntil; SNameVersion* psNext; OIndex oi; };   // oi is INVALID_O_INDEX if the name did not exist.

Because write transactions hold X locks, an object has at most one uncommitted version, in its writer's write set.

Reading at snapshot S:
  - No chain for the key (the usual case): the base store's version is valid for every open snapshot.
  - Otherwise take the first version whose iValidUntil is greater than S.  If none qualifies, read the base store.

Clean-up: when a commit is published or a read transaction ends, versions whose iValidUntil is not after the oldest open snapshot (or the last commit when none is open) are dropped, and empty chains removed.  This scans the two maps rather than keeping a list per commit; the maps only hold objects changed while a reader was open, so the scan is cheap.

When versions are saved:
  - A write transaction commit saves them only if a read transaction is open.  None can begin while the commit holds the store mutex.
  - A direct session is a write transaction too, so it changes nothing in the store before it commits and saves versions the same way.

Implemented in CodabaseVersions.h/.cpp (step 4).  CReadTransaction reads through CCodabase's Snapshot methods (SnapshotGet, SnapshotGetIndex, SnapshotIndices, ...).

Iteration (step 4): CReadTransaction and CWriteTransaction build the list of indices (or names) visible to them when iteration starts, sorted by index (or name) without duplicates in a CTransactionIteration, and return the data as of their snapshot (or with their changes) one step at a time.  Only one index and one name iteration can be in progress per transaction; the iterator argument is not used.

The version store is not durable.  After a crash or restart no transactions are open, so it starts empty.

A long-running read-only transaction alongside heavy writing makes the version store grow.  If that becomes a problem, chain storage can move to a CIndexTreeEvicting with composite keys ([oi][~iValidUntil], big-endian) in a temporary directory deleted at startup, outside the durable set.  The read, commit and clean-up rules stay the same.


Threading
---------

The logger is not thread safe: __METHOD__ builds the method name in a shared buffer, so it must only be evaluated when an error is logged, and errors logged by several threads at once can still collide.

Nothing in CNamedIndexedData or CIndexedData is thread-safe, and even Get changes state (it loads into the cache).  CCodabase holds one store mutex (mcMutex) for each public operation, not for a whole transaction (done, step 2).  The commit mutex can be the same mutex.

Iteration (StartIndexIteration / IndexIterate, StartNameIteration / NameIterate) keeps its position between calls.  Each call is locked, but an iteration may miss or see changes other threads make between its calls.  This is documented as unsafe until read-only transactions give snapshot iteration.

CNativeThread and CConditionVariable were moved from ThreadLib into BaseLib (as CMutex was) so the transaction code and its tests can use them.

IPC sessions: every transaction is tied to the session that started it.  Closing or losing the session aborts its transactions, so a client that dies cannot hold locks or name reservations forever.  Remote lock requests should have a wait timeout.

Only one process may open a Codabase directory.  It is worth enforcing this with an exclusive lock on the directory at Init (see the flock code in NamedSharedObject_Linux); it is not known whether anything prevents it today.


Durability
----------

CDurableSet::End is a double-write commit: Mark1.Write, write and fsync the primary files, Mark2.Rewrite, write the backup files, delete the marks.  Recover uses the marks to copy primary to backup or backup to primary.  Done (step 1):
  - Written files, the mark files and their directories are fsynced, and every result is checked.
  - MarkFinish deletes the rewrite mark first, so a crash between the deletes leaves a state Recover accepts.
  - The start mark lists the primary and rewrite name of every file in the commit, ending with "#End".  Recover copies those files (plus any passed in, each once), so it needs no other file list.  A start mark without "#End" was cut short by a crash before any primary file was written.
  - CCodabase::Init does no disk work.  CCodabase::Start recovers an interrupted commit and then loads the store.  CSequence::Init recovers too, so an interrupted sequence write can never hand out indices twice.
  - CLogFile::Truncate works (it was a no-op) and is committed with the other log commands.
  - Crash tests stop End() at every step and check Recover gives either the old files or the new ones.

EDurableSync (DS_No / DS_Yes) is passed to CCodabaseFactory::Create and CSequenceFactory::Create.  DS_No skips the fsyncs, but not the marks or recovery; it is only for tests that do not need durability.

Not done: Windows has no documented way to flush a directory, so SyncDirectory does nothing there.  A newly created directory is not synced into its parent.


Write-through (IWT) modes
-------------------------

Under transactions the IWT modes do not matter to Codabase itself, because commit flushes either way.  CObjects still depends on them: with IWT_Yes, CObjects::LogicalDirty flushes each object as soon as it is dirtied.  IWT is left untouched in version 1.  Whether to remove it is decided when CObjects moves to transactions.


Open questions
--------------

  - How read-only transactions get an object view in CObjects that writers' uncommitted in-memory changes do not affect.  MVCC gives them the right bytes, but they must deserialise from their snapshot into their own read-only view rather than share the live object graph.  Not needed until CObjects is in scope.
  - Whether to remove the IWT modes.
  - Name lookup and iteration protection for write transactions (version 2).


Build order
-----------

  1. Durability (done): see "Durability".
  2. Thread safety (done): store mutex in CCodabase, CNativeThread and CConditionVariable moved into BaseLib, multi-threaded Codabase test.
  3. Write transactions, one at a time (done): CWriteTransaction (WriteTransaction.h/.cpp) with its write set, commit (removals before additions, so a removed name can be reused), abort, and the read-only state after a failed commit.  One writer at a time, waiting on a CConditionVariable.  The name reservation table is deferred to step 5 (with one writer nothing can race), and iterating a write transaction to step 4 (it fails with an error until then).
  4. Version store and read-only transactions (done): CCodabaseVersions, CReadTransaction (ReadTransaction.h/.cpp) from CCodabase::BeginReadTransaction, commit numbers published after End(), clean-up, snapshot iteration and write-transaction iteration.
  5. Lock manager (done): CLockManager (LockManager.h/.cpp) with S / U / X modes and wait-die, write transactions locking every object they read or write, name reservations, and the direct session as an implicit oldest transaction.


History
-------

An earlier transaction implementation in CoreLib (Transaction, SubTransaction, TransactionController, TransactionIndexedData, IndexedMemory, TransientIndexedFile, TransientIndexedFileDescriptor) was removed in commits b17537b5 and fa534136 (2016-05-02).  It created a separate database per transaction holding copies of objects other transactions wrote.  That approach made writers copy old values into every concurrent reader's database and could not prevent phantoms.  This design reverses it: one shared store of old versions per key, and private write sets per transaction.
