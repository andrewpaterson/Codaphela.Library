Making the tests faster (planned 2026-11-18, the user: "Plan out making the tests faster 1 to 5 please")
==========================================================================================================

The rule the sweep follows from now on (the user, 2026-11-18): Release|x64, Release|Win32 and Debug|x64 are run; Debug|Win32
only if a Release build fails.

What was measured (2026-11-18, this machine: 16 cores, 7.9 GB, shared with other sessions)
  - TestCppCompilerLib: Release|x64 460-630 s, Release|Win32 675 s, Debug|x64 2507 s, Debug|Win32 5660 s.  Per file in
    Release|x64 (its Time: lines since ad367fada): TestCPPW65C816 309 s (103 test functions, 180 programs built and run),
    TestIRW65C816Backend 83 s, TestCPPConformance 73 s, TestCPP65Generator 72 s, TestCPP65IR 28 s, TestCPP65ForwardingReferences
    15 s, TestCPP65Spill 15 s; the other 24 files 30 s together.  A process peaks at about 300 MB in Release.
  - A trivial program built and run on both targets (start up, math tables, Libc65's string routines): 0.3 s with the
    process's start.  TestCPPW65C816's programs take 1.7 s each, so its time is its own programs and runs, not that.
  - IDE checks (392, one IDE process each, one after another): 290 light checks took 187 s together; 50 heavy ones 2212 s,
    about 44 s each.  The heavy ones (usages-*, find-*, nav-*, rename-*, gotosource-*) open ModPlay, wait for BaseLib to be
    indexed (WAIT_INDEX) and then do a second's work.  An IDE with ModPlay indexed is about 2.3 GB.
  - TestSupportLib65 Release|x64: 495 s.  It compiles TestSupportLib and its libraries once (in parallel since 2026-11-02:
    ~37 s on the 816), then links and runs its programs one after another on one emulator.
  - The sweep of the CommonLibraries suites other than TestCppCompilerLib: about 35 minutes for the four configurations.

Each step is its own commit, and is checked against what it replaces: the same suites pass with the same totals (and for the
IDE checks the same passes and failures) as a run in one process.


1. TestCppCompilerLib in parallel processes                                        Release|x64 627 s -> ~150 s, Debug|x64 2507 s -> ~700 s
   a. TestLib: the log file's name from the environment (TESTLIB_LOG, Log.txt if unset), so processes in one working folder
      don't write over each other's Log.txt.
   b. TestCppCompilerLib's main: its files in a table ({name, function}) instead of a list of calls, and arguments -only <file>[,<file>]
      and -list (prints the names, for the driver).  With neither it runs everything as now.
   c. The long files split by test function: TestCPPW65C816 (103 functions), TestIRW65C816Backend (45), TestCPP65Generator (44),
      TestCPPConformance (its groups and targets).  Their entry points take a part (-part 2/4: every 4th function from the
      second), with BeginTests/TestStatistics around each part.  Before splitting, check that no two functions of a file
      write the same Output path (TestCPPW65C816 has 14 Output references, TestCPP65Spill 13: Spill stays whole).
   d. Tests/TestCppCompilerLib/RunParallel.py: runs the parts as processes, longest first (from the last run's Time: lines,
      kept in a file beside it), at most N at once (default 4; fewer while free memory is under 2 GB), then adds up their
      logs into Log.txt with the same per-file sections and totals as one process writes.  sweep.py runs it for
      TestCppCompilerLib.
   e. Check: the totals and every file's count equal a one-process run's in Release|x64 and Debug|x64.
   Questions: none.
   Done 2026-11-18.  RunParallel.py; TESTLIB_LOG; main's -list, -only, -part p/n and -calls; TEST_PART in the four long
   files, each call's time and tests printed with TEST_PART_TIMES and kept in Output/RunParallel.times, from which the
   next run shares a file's calls out by time (the longest first, to the part with least).  Release|x64: 168 s with 4
   processes, against ~460 s in one.  Every call's tests are the same in parts as in a whole run (checked file by
   file); a total can differ by what a process does once, the first time a test needs it (TestIRW65C816Backend
   assembles its runtime libraries in each process that needs them: 203623 run alone, 203611 after the other files in
   one process).  The floor is two of TestCPPW65C816's functions, which can't be split by function:
   TestCPP816TestBaseLibBugs 168 s and TestCPP816SizeLsizeBugs 103 s, of its 294 s: step 4 starts with them.

2. IDE checks in parallel, and the heavy checks lighter                              ~50 min -> ~15-20 min
   a. Measure where a heavy check's 44 s goes (indexing BaseLib, starting, the check), with the IDE's timings printed for
      one check (HCP65_IDE_WAIT_INDEX already waits; add how long the index took).
   b. Isolation, so checks can run side by side: each worker gets its own APPDATA (the IDE keeps RecentSolutions.xml and
      Keymap.xml there) and its own copies of ModPlay and Kernal, made beside them at the same depth (HCP65\ModPlay-check1,
      ignored by git) so their relative paths still reach CommonLibraries and Libc65; IDEChecks.py takes MODPLAY and KERNAL
      from the worker and builds expectations that print those paths from them.  The checks that edit BaseLib's Calc files
      never save them (WATCHED says so), so they can share them.  The copies and the APPDATA folders go when the run ends,
      and RestoreUserFiles has nothing left to put back.
   c. A scheduler in checks.py: light checks 4 at a time, heavy ones (WAIT_INDEX on ModPlay) at most 2 at a time because of
      their 2.3 GB, both by free memory.  Each check's output goes to its own file and the report is in CHECKS order.
      With the heavy checks as they are this gives ~40 min -> ~20 min.
   d. Then the heavy checks themselves, depending on (a): if indexing is most of it, a solution of its own for them with the
      Calc files and what they need (Checks/Input, as the 28 Make*Copy checks have), so they index a few files, not BaseLib;
      their expected counts are checked against the ModPlay run before the switch.  A few that are about scale (the index
      off the UI thread, reindexing while typing) keep ModPlay.  Expected: the heavy checks ~44 s -> a few seconds each.
   Questions for the user: (d) changes what the usages/find checks run against, from the real ModPlay to a small copy, so
   they no longer check the IDE on a big solution.  Keep a handful on ModPlay (as above), or keep them all and accept ~20 min?
   The user, 2026-11-18: "2d, run on a small solution".

4. TestCPPW65C816: where its 309 s goes, then the biggest costs                       (unknown until measured)
   The plan said "compile Libc65 once per process", but a trivial build is 0.15 s a target, so that is small.  Instead:
   a. Time each of its 103 test functions (TestLib's timer around each, printed with TEST_CPP816_TIMES) and each program's

   c. Check: the same 3203 tests pass; nothing is tested less (a lockstep run removed is listed in the commit with why).
   Questions: any lockstep run to drop goes to the user first.

5. The sweep: build while the last suite runs                                        ~3.5 h -> ~1.5 h with 1 and 6
   Planned in detail 2026-11-19 (the user: "Plan step 5 please").

   Where it is now.  The sweep is a script in a session's scratchpad (getters/sweep.py, 88 lines), so it is lost when the
   scratchpad is: an item is a solution in one configuration, built (MSBuild -m:2) and then its suites run, one item after
   another, each result a line in sweep_results.txt (an item already there is skipped, so a stopped sweep goes on).  Its
   last results (2026-11-17/18, stopped after TestSupportLib65 Release|x64, the power cut) add up to, per configuration:
     Release|x64    builds  427 s, runs 1201 s (TestCppCompilerLib 599 s of them)
     Release|Win32  builds  359 s, runs  782 s (675 s)
     Debug|x64      builds  527 s, runs 2963 s (2507 s)
     Debug|Win32    builds  496 s, runs 6651 s (5660 s)
   for the twelve CommonLibraries solutions; the *65 suites, LogiCim's, HCP65's, the IDE's and TestHCP65Lib (29 minutes in
   Release|x64 since the Blitter Board work) come on top.  Nothing overlaps: a build waits for the run before it.

   a. The script into the repository: Tests/Sweep.py beside RunParallel.py, with the list of what is tested (the memory's
      "only list", test-sweep-howto) as its table: each solution, the suites it builds and how each runs (directory,
      arguments, which configurations).  So the list and the way it runs are in one place that every session can read.
   b. Two lanes.  A builder builds the items in order, one at a time (one MSBuild -m:2 -nodeReuse:false); a runner runs each
      built item's suites, one at a time, in the same order.  The builder may be at most one item ahead of the runner, and
      starts a build alongside a run only when free memory is over 3 GB (else it waits for the run to end), as RunParallel
      does.  An item's suites run only after its build has ended, and no build is of the item that is running (MSBuild would
      relink its exe): the builder's next item is always a later one.  The CommonLibraries libraries are built into shared
      folders by many solutions, but only by the builder, so never twice at once; what a run reads (its exe, BaseLib's and
      Libc65's sources for the compiler suites) no build writes.
   c. The order within a configuration: the longest runs first (TestCppCompilerLib, TestHCP65Lib, the *65 suites, then the
      rest by their last time, kept in sweep_results.txt), so the short items' builds are done while the long ones run, and
      the configurations one after another (Release|x64, Release|Win32, Debug|x64).  TestCppCompilerLib runs through
      RunParallel.py (step 1: 4 processes), and while it runs the builder waits (four processes and a build don't fit
      in 7.9 GB with another session's work).
   d. Debug|Win32: an item in it only when that solution's build or a suite failed in Release|x64 or Release|Win32 (the
      user's rule, 2026-11-18), added once both Release configurations are done.
   e. Sharing the machine.  Before each build and each run the sweep looks for Tests/Output/Sweep.pause and waits while it
      is there, so another session (or the user) can hold it between items without stopping it; the session running the
      sweep relays each long run's start and end to the others (the sweep prints them).  A run is never started under
      2 GB free.  The sweep is one process for hours, so it runs in the background, and if it is stopped (low memory, a
      power cut) it is started again: sweep_results.txt says what is done, and an item half done is done again.
   f. sweep_results.txt as now (an item, the build's result and time, each suite's exit, totals, first failure and time),
      plus when each began, so how much overlapped can be seen; a summary at the end: the failures, the totals per
      configuration, the wall time.
   g. Check: one sweep with Sweep.py gives the same results as the last one item by item (the same totals, allowing the
      known platform differences in test-sweep-howto), and its wall time is compared with the sum of the old one's.

   Expected: per configuration about the longest of (all builds, all runs), as the builds hide behind the runs; with step
   1's RunParallel (TestCppCompilerLib 599 s -> ~165 s in Release|x64, 2507 s -> ~700 s in Debug|x64) and no Debug|Win32
   unless a Release one fails, the sweep goes from ~3.5 h to about 1-1.5 h, most of it TestHCP65Lib and Debug|x64's runs.

   2. TestHCP65Lib in every configuration?  It is 29 minutes in Release|x64 (more in Debug), runs the kernal on the
      emulator and has been reaped for low memory here before; the *65 suites run only in Release|x64 (the user,

      ~13 minutes), now that it is the target most work is for?
